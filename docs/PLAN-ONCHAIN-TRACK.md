# §0. 먼저 읽을 것 — 이 플랜이 아이디어 문서를 뒤집은 지점

아이디어 문서 §⑤는 **고객이 먼저 펀딩하고 오더북에 올린다**를 권했다.
플랜을 짜면서 그게 **암호학적으로 불가능**하다는 걸 확인했다. §2가 그 설명이다.

바뀐 것 하나만 먼저 말하면: **펀딩은 후원자가 붙은 뒤에 한다.** 스팸 방어는
온체인 펀딩이 아니라 **라이트닝 보증금**이 맡는다(이미 설계돼 있다 — DESIGN-DEPOSIT).

# §1. 합칠까 가를까 — 결론

| | 결정 |
|---|---|
| **FSM** | ⬜ **완전 별도.** 상태 집합이 거의 안 겹친다 |
| **페이지/탭** | ⬜ **별도 탭.** 라이트닝 트랙은 실서비스 중이다 |
| **Nostr 전송·릴레이·구독 배관** | ✅ 공유 |
| **`CLIENT_TAG`** | ⬜ **반드시 분리.** 안 하면 배포 사고 (§1.3) |
| **보증금(LN 홀드 인보이스)** | ✅ 공유 |
| **분쟁 채팅·Web Push·시세 트래커** | ✅ 공유 |
| **진행도 표시 *기구*** | ✅ 공유 / **단계 표는 별도** |

## §1.1 FSM을 가르는 이유

세 가지가 구조적으로 다르다.

**① 순서가 뒤집힌다.** 라이트닝은 후원자가 매칭된 **뒤** 고객이 에스크로를 건다
(`verified → escrowed`). 온체인은 주소가 세 키에 묶여 있어 순서가 강제된다(§2).

**② 어드민의 역할이 다르다.** 라이트닝에서 어드민은 **자금을 들고 있는 수탁자**다
(홀드 인보이스를 settle/cancel한다). 온체인에서는 **공동 서명자**일 뿐 자금을
만지지 않는다. `settle`·`cancel`에 해당하는 동작 자체가 없다.

**③ 종결이 공짜가 아니다.** 라이트닝은 상태 발행 한 번이면 끝난다. 온체인은
**모든 종결에 tx 브로드캐스트와 컨펌이 필요**하고, 그 사이에 멤풀 이탈·RBF·리오그가
있다. 그래서 "종결 직전" 상태가 필수다(`settling`).

합치면 모든 핸들러가 `if (track === 'onchain')`로 갈라진다. FSM은 이 앱의 보안
핵심이고 전이 하나하나가 THREAT-MODEL의 공격에 대응한다 — 거기에 분기를 심는 건
가장 위험한 자리에 복잡도를 넣는 것이다.

> 오늘만 상태 추가가 **알림·문서·진행도·배지 네 곳**으로 번지는 걸 세 번 봤다.
> 전이 행렬을 두 배로 만들면 그 파급도 두 배가 된다.

## §1.2 탭을 가르는 이유

고객 플로우가 완전히 다르다 — 라이트닝은 등록이 무료, 온체인은 온체인 tx를 쏴야
한다. 한 목록에 섞으면 카드마다 "이건 어느 쪽"을 설명해야 하고 액션 버튼이 갈린다.

더 큰 이유는 **실서비스 보호**다. 라이트닝 트랙은 지금 실제 돈이 돈다. 온체인
트랙은 독립적으로 붙였다 뗐다 할 수 있어야 한다.

유저 앱 탭: `사주기 | 의뢰하기 | 내 거래` → **`사주기 | 의뢰하기 | 온체인 | 내 거래`**
- `내 거래`는 **양쪽을 다 보여준다** (구독 필터 두 벌, §5.4)

## §1.3 ⚠️ `CLIENT_TAG`를 안 가르면 배포 사고가 난다

현재 유저 앱의 오더 구독은 이렇다 — [customer/src/nostr/subscribe.ts:45](customer/src/nostr/subscribe.ts#L45):

```ts
{ kinds: [30402], authors: [APP_PUBKEY], '#t': [CLIENT_TAG] }
```

**이미 배포된 prd 클라이언트가 지금 이 필터로 돌고 있다.** 온체인 오더를 같은
`CLIENT_TAG`로 발행하면 **구버전 앱이 그걸 라이트닝 오더로 렌더링한다.**

그 결과가 어떤지는 이미 봤다 — `payoutSat`이 없으면 후원자 화면에 **"0 sat을
등록하세요"**가 뜬다(2026-09-19 실측). 클레임까지 하면 어드민 FSM이 모르는
오더에 요청이 쌓인다.

**조치**: 온체인 트랙은 별도 태그를 쓴다.

```ts
// shared/src/constants.ts
export const CLIENT_TAG_ONCHAIN = import.meta.env.DEV
  ? 'sajwo-tracker-onchain-dev'
  : 'sajwo-tracker-onchain';
```

배포된 클라이언트는 이 태그를 **절대 구독하지 않으므로** 온체인 오더를 아예 못 본다.
클라이언트 업데이트 순서에 의존하지 않는 유일한 안전한 방법이다.

> `track` 태그를 달고 클라이언트에서 거르는 방법도 있지만, **모든 클라이언트가
> 업데이트된 뒤에야** 첫 오더를 발행할 수 있다. 정적 PWA라 캐시된 구버전이
> 언제까지 남아 있는지 알 수 없다. 태그 분리가 맞다.

# §2. 펀딩 시점 — 아이디어 문서를 뒤집는다

## §2.1 "펀딩 먼저"가 불가능한 이유

taproot 주소는 **스크립트 트리 전체에 커밋**한다. 즉 주소를 만들려면 세 pubkey가
전부 필요하다. 그런데 후원자가 붙기 전에는 `S`가 없다.

"그럼 `{C,A}` 2-of-2로 먼저 받고 나중에 옮기면?"을 따져봤는데 안 된다:

| 방법 | 왜 안 되나 |
|---|---|
| `{C,A}`로 받고 클레임 때 2-of-3으로 이동 | **온체인 tx가 하나 더 든다** + 고객이 클레임 시점에 온라인이어야 한다 (= "올려두고 잊기"가 깨진다, 애초의 목적) |
| `{C,A}` 그대로 쓰고 분쟁은 어드민 재량 | **후원자 보호가 사라진다.** 고객이 서명을 거부하면 후원자에게 줄 방법이 `A` 단독뿐인데, 그게 가능하면 **어드민이 아무 때나 훔칠 수 있다** |
| 나중에 키를 추가 | taproot 주소가 트리에 커밋하므로 불가능 |

두 번째 줄이 핵심이다. **"후원자를 보호할 수 있다" ⟺ "C 없이도 자금이 움직인다"**
이고, `{C,A}`에서 그건 `A` 단독을 뜻한다. 그래서 `S`의 키는 스크립트에 **반드시**
있어야 하고, 따라서 **펀딩은 `S`를 안 뒤**다.

## §2.2 그럼 스팸 방어는 — 라이트닝 보증금이 한다

원래 "펀딩 먼저"가 주려던 것은 둘이었다:

1. 고객 스팸 차단 → **고객 LN 보증금**이 대신한다 (S-001, [DESIGN-DEPOSIT.md](DESIGN-DEPOSIT.md))
2. "진짜 있는 물량" 신호 → 보증금이 걸린 의뢰라는 표시로 대신한다

보증금이 온체인 펀딩보다 **더 낫다**: 즉시·수수료 0·몰수 가능. 온체인 펀딩은
스팸을 막아도 고객이 진짜일 때조차 수수료를 물린다.

> ⚠️ **온체인 트랙은 보증금이 켜져 있어야 성립한다.** 라이트닝 트랙은 지금
> 보증금을 끄고 돌리지만(유저가 없어서), 온체인 트랙은 켜는 것이 전제다.
> 안 켜면 고객이 클레임만 받아놓고 펀딩을 안 하는 걸 막을 수단이 없다.

### ⚠️ 그래서 온체인 의뢰 만료에 상한이 생긴다 (리뷰 R1-H4)

보증금은 LN 홀드 인보이스이고, 그 CLTV는 채널 상한(보통 2016블록)을 넘을 수 없다.
현재 코드는 의뢰 만료를 그대로 CLTV로 쓴다 — [service.ts:807](../admin/src/nostr/service.ts#L807):

```
cltvBlocks = (의뢰만료 − now + 24h) / 600  <  2016
→ 의뢰만료 < 2016×600 − 86400 = 1,123,200초 ≈ 13일
```

**13일을 넘는 의뢰는 보증금 인보이스를 아예 만들 수 없다.** 그리고 코드는
보증금 결제 후에야 오더를 만들므로, 그런 의뢰는 **등록 자체가 실패**한다.

인보이스 수명을 24h로 자르면(에스크로가 그렇게 한다) 이번엔 **보증금이 하루 만에
타임아웃 환불돼 오더가 무담보로 남는다.** 둘 중 하나는 반드시 걸린다.

**결정: 온체인 트랙의 의뢰 만료 상한 = 7일** (v3.1에서 3일→7일로 재조정)

용례가 둘이다:

1. **둘이 이미 합의하고 에스크로만 받는다** — 유저 피드백의 원래 요청. 몇 시간이면 된다
2. **오더북에 올리고 익명의 후원자를 기다린다** — 원래 기획. 며칠은 필요하다

v3에서 1번만 보고 3일로 잡았는데, **2번을 버리면 안 된다.** 오더북이 이 앱의
차별점이고, 매칭이 붙으려면 물량이 며칠은 떠 있어야 한다.

7일이면 둘 다 덮는다. 그래도 **CLTV 천장(13일)에 여유가 크고** 장점은 그대로다:

- 보증금 CLTV 상한(13일)이 **아예 제약이 아니게 된다** — 리뷰 R1-H4가 소멸
- 무담보 구간이 없다
- 시세 노출 구간이 짧다

> 아래는 상한이 왜 13일인지의 기록이다 — 값을 3일로 정한 지금은 여유가 크지만,
> 나중에 늘리자는 말이 나오면 여기가 천장이다.

- 보증금 HTLC가 의뢰 수명 **전체**를 덮는다 → 무담보 구간이 없다
- 자르기·갱신 같은 추가 기구가 필요 없다
- ⚠️ 2016은 관례일 뿐이므로 **런타임에 채널 상한을 읽어 유도**한다. 하드코딩 금지

> 라이트닝 트랙(최대 3개월)은 **바꾸지 않는다.** 거기는 보증금이 꺼져 있고,
> 별도 버그로 따로 다룬다(§14 R1-H4 답변).

## §2.3 "올려두고 잊기"는 푸시 알림이 살린다

고객이 클레임 시점에 온라인이어야 한다는 건 사실이다. 그런데 **Web Push를 이미
만들어 뒀다.** "올려두고 → 알림 오면 → 펀딩"이 되고, 이건 라이트닝 트랙에서
고객이 홀드 인보이스를 결제해야 하는 것과 정확히 같은 부담이다.

## §2.4 가격은 **펀딩 컨펌 시점**에 고정한다

아이디어 문서는 클레임 시점 고정을 말했는데, 펀딩이 뒤로 가면서 바뀐다.

문제는 **누가 옵션을 쥐느냐**다. 가격을 클레임 때 고정하면 그 뒤 컨펌까지
10~60분 동안 **고객이** 옵션을 쥔다 — 시세가 불리해지면 그냥 펀딩을 안 하면 된다.

**컨펌 시점에 고정하면 아무도 옵션을 못 쥔다:**

```
클레임 (후원자 보증금) → 고객 펀딩 → N컨펌
                                      └─ T0: KRW 확정
   T0 ──15분── presigned ──5분── 계좌공개 ──30분── 원화 마감
                │                    │                  └ 최대 T0+50분
                │                    └ 고객 마감 (O-013)
                └ 후원자 사전서명 마감
```

- 고객은 가격을 모르는 채로 펀딩한다 → 컨펌 대기 중 옵션 없음
- 그 대신 **최저가(reserve)** 로 보호한다. 컨펌 시점 시세가 reserve 미만이면
  자동으로 환불 경로(§4 `settling`→`refund:reserve`)
- 후원자의 옵션 창은 **최대 T0+50분으로 묶이고**, 버리면 보증금을 잃는다.
  단 **후원자 마감은 계좌공개부터** 센다 — 고객 지연이 후원자를 치지 않게(O-013)

### ⚠️ 마감은 둘 다 `funded`(T0)에 건다 — 쌓이면 안 된다 (리뷰 R1-H1)

v1에는 `funded → presigned` 마감이 **아예 없었다.** 가격이 고정된 뒤 후원자가
사전서명을 미루며 시장을 무한정 지켜볼 수 있었다 — 유리하면 진행, 불리하면
보증금만 버리고 이탈. 그동안 고객 자금은 온체인에 잠긴 채다. 명백한 구멍이었다.

고치면서 **마감의 기준점도 바꿨다.** 각 단계에 상대 마감을 걸면(사전서명 15분 →
그때부터 송금 30분) 후원자가 사전서명을 14:59에 내는 것으로 **총 창을 늘릴 수 있다.**
두 마감을 모두 T0에 걸면 총 옵션 창이 45분으로 **고정**된다.

> 사전서명은 사람의 판단이 필요 없다 — 받을 주소는 `bonded`에서, **금액과 수수료는
> T0에 어드민이 확정해 발행**하므로 앱은 그 값을 검증하고 서명만 하면 된다.
> 15분은 앱이 깨어나는 데 드는 시간이지 고민할 시간이 아니다.
>
> (v2 초안은 "수수료도 `bonded`에서 정해진다"고 적었는데 틀렸다 — 사전서명은
> 펀딩 txid에 커밋하므로 **펀딩 이후에만** 가능하고, 수수료도 그때 정해진다.)

**보증금은 이 45분의 변동폭을 덮어야 한다.** 창이 유한해야 "보증금 = 옵션 프리미엄"이
성립한다 — 창이 무한하면 보증금을 아무리 키워도 언젠가 넘는다. 수치는 §12 R-Q1.

# §3. 스크립트 · 키 · 주소

## §3.1 스크립트 트리

```
내부키(key path)   BIP-341 NUMS 점 (증명 가능하게 소모 불가)
                   x = 50929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0

leaf 1  happy      <C> OP_CHECKSIGVERIFY <S> OP_CHECKSIG
leaf 2  고객 승     <A> OP_CHECKSIGVERIFY <C> OP_CHECKSIG
leaf 3  후원자 승   <A> OP_CHECKSIGVERIFY <S> OP_CHECKSIG
leaf 4  타임락      <N> OP_CSV OP_DROP <C> OP_CHECKSIG
```

- 전부 x-only 32바이트 pubkey, BIP-342 tapscript, `OP_CHECKSIG`는 Schnorr
- `N` = **8064 블록**(약 8주) 상대 타임락(`OP_CHECKSEQUENCEVERIFY`) — v3.3에서 4032→8064
- **MuSig2는 v1에서 안 쓴다** — 논스 재사용이 키 유출이고, 브라우저 비동기
  환경에서 재시도·새로고침·다기기가 전부 재사용 경로다. 근거는 아이디어 문서 §권고.

> **상대 타임락(CSV)** 인 이유: 절대(CLTV)는 펀딩이 늦어지면 창이 짧아진다.
> CSV는 펀딩 컨펌부터 세므로 항상 같은 길이가 보장된다.

## §3.2 키 파생

**고객·후원자** (로컬에 nostr 개인키가 있음):

```
orderKey = HMAC-SHA256(key = nostrPrivkey, msg = "pairbuy-onchain/v1/" + orderId)
```

- nostr 신원과 온체인이 연결되지 않는다 (오더북에 pubkey가 공개로 박힌다)
- 주문마다 새 키 → 주소 재사용 없음
- nostr 키 하나로 **결정론적 복원** → 추가 백업 부담 0
- 결과가 secp256k1 범위 밖이면(확률 ~2⁻¹²⁸) msg에 `/1`, `/2`를 붙여 재시도

**어드민** (NIP-46이라 로컬에 개인키가 없음):

- 주문별 키를 `crypto.getRandomValues`로 생성
- **NIP-78 + NIP-44 암호화 백업**에 즉시 저장 (프리이미지·VAPID가 쓰는 그 경로)
- ⚠️ **백업 성공을 확인하기 전에는 주소를 발행하지 않는다.** 이 키를 잃으면
  그 주문의 분쟁 중재가 영구 불가다

## §3.3 세 키가 서로 달라야 한다

`{A,S}` 리프는 두 키가 **다른 주체**에 있다는 전제 위에 있다. 같은 곳에 모이면
단독 서명이 되어 2-of-3 보장이 사라진다.

→ 주소를 파생하기 전에 **세 x-only pubkey가 전부 다른지 검사**하고, 하나라도
겹치면 진행을 막는다. **클라이언트와 어드민 양쪽에서** 본다.

## §3.4 주소 검증은 클라이언트가 스스로

어드민이 알려준 주소를 그냥 믿으면, 어드민이 악의적이거나 침해당했을 때 전액을 잃는다.

→ 세 pubkey를 **전부 오더 이벤트에 싣고**, 각 클라이언트가 주소를 **직접 파생해
대조**한다. 불일치면 진행 차단. **타협 대상이 아니다.**

## §3.5 라이브러리

**`@scure/btc-signer`** (noble/scure 계열). 이유:

- 순수 JS·의존성 최소·감사 이력 — 이미 쓰는 `@noble/*`와 같은 계열
- taproot 스크립트 패스 서명과 PSBT를 지원
- `bitcoinjs-lib`는 Buffer 폴리필이 필요해 브라우저 번들에 불리하다

⚠️ `update-deps.sh`가 latest를 따라가므로, **서명 경로 라이브러리가 조용히 갈리지
않게** `pnpm why`로 단일 인스턴스를 확인한다 (ark SDK crypto 3종에서 겪은 그 문제).

# §4. FSM

## §4.1 상태

```
listed      의뢰 등록됨 (고객 LN 보증금 결제 완료). 오더북 노출
claimed     후원자가 클레임. 후원자 보증금 인보이스 발행됨, 결제 대기
bonded      후원자 보증금 accepted. 세 키 확정 → 에스크로 주소 발행됨
funding     고객 펀딩 tx가 멤풀에 있음 (컨펌 대기)
funded      펀딩 N컨펌. **KRW 가격 확정.** 후원자의 주소+사전서명 대기
presigned   후원자 사전서명 검증됨. 고객이 **5분 내 계좌 공개** → 그 시점부터
            **후원자 원화 송금 창 30분** (O-013)
remitted    후원자가 원화 송금 주장. 고객이 은행을 확인하고 cosign해야 한다
disputed    **어드민 판정 대기.** 고객이 마감 내 cosign도 이의제기도 안 했거나
            어느 한쪽이 분쟁을 걸었다. **고객 의사와 무관하게 진입한다**
settling    종결 tx 브로드캐스트됨 (멤풀). settlementKind가 어느 종결인지 지정
```

**터미널** (전부 컨펌된 tx가 근거):

```
released        {C,S} 릴리스 컨펌 — 정상 완료
refunded        {A,C} 환불 컨펌 — 분쟁 아닌 사유. **사유별로 보증금 처리가 다르다**
sponsor_wins    {A,S} 컨펌 — 분쟁 판정
customer_wins   {A,C} 컨펌 — 분쟁 판정 (tx는 refunded와 같은 모양, 사유와 보증금 처리가 다름)
cancelled       펀딩 전 취소 — 온체인 tx 없음
swept           타임락으로 고객이 일방 회수 (어드민 고장). 어드민이 관측만 한다
```

> `settling` 하나로 네 종결을 모두 처리하고 `settlementKind`로 구분한다.
> 종결마다 "…ing" 상태를 따로 두면 상태가 넷 더 늘어난다.
>
> `refunded`와 `customer_wins`는 tx 모양이 같지만 **분리한다** — 보증금 처리가
> 다르고(분쟁이면 몰수/중재료), 통계에서 "분쟁률"이 섞이면 안 된다.

**`settlementKind`는 사유까지 갈라야 한다** (리뷰 R1-M1). `refunded` 하나에
보증금 처리가 정반대인 사례가 섞여 있었다:

| `settlementKind` | 사유 | 후원자 보증금 | 고객 보증금 |
|---|---|---|---|
| `release` | 정상 완료 | 환불 | 환불 |
| `refund:reserve` | 시세가 고객 reserve 미만 | **환불** (무과실) | 환불 |
| `refund:sponsor-timeout` | 사전서명·원화송금 마감 초과 | **몰수** → 고객 수수료 보상 | 환불 |
| `refund:customer-late` | 고객이 5분 내 계좌 미공개 | **환불** (무과실) | **몰수** |
| `refund:bond-expired` | `funded` 시 후원자 보증금 사망 (O-015) | (이미 만료 환불됨) | 환불 |
| `swept` | 어드민 고장 → 타임락 회수 | **CLTV 자동 환불** | **CLTV 자동 환불** | 
| `sponsor_win` | 분쟁 판정 | 환불 | **몰수** → 중재료 충당 |
| `customer_win` | 분쟁 판정 | **몰수** → 중재료 충당 | 환불 |

**중재료는 패소자의 몰수 보증금에서 나간다**(리뷰 R3-M1). v4까지 §4.1은 "패소자가
낸다"로, §6.1은 "분쟁 tx의 어드민 출력"(= 에스크로에서 차감 = **승자가 낸다**)으로
**정반대**였다.

**몰수 보증금에서 충당하는 쪽이 맞다**:
- **패소자가 실제로 부담**한다 — 직관과 맞는다
- 분쟁 tx에 출력이 하나 줄어 **tx가 작아지고 수수료가 싸진다**
- 승자가 받을 금액이 중재료만큼 깎이지 않는다
- 별도 자금 이동이 없다 — 어드민이 이미 settle한 돈이다

> ⚠️ **분쟁에서는 "몰수금 50% 피해자 충당"(§6.0)을 적용하지 않는다.** 그 정책은
> 어드민 노동이 없는 **타임아웃 경로**용이다. 분쟁은 중재료가 우선이다.
>
> 몰수액 < 중재료면 어드민이 모자란 만큼 못 받는다. 보증금 1~3% 대비 합리적 중재료면
> 대개 덮이고, 안 덮이면 그건 보증금이 작다는 신호다(R-Q1).

> `swept`은 **어드민이 처리하지 못하는** 유일한 종결이다. 보증금은 어드민이 settle도
> cancel도 못 하므로 **홀드 인보이스 CLTV 타임아웃으로 양쪽 다 자동 환불**된다.
> 어드민이 죽은 상황이라 그게 맞는 결과다 (리뷰 R2-L3).

전이만 보고 판단하면 어드민이 정반대로 처리한다. **사유가 곧 보증금 처리**다.

> ⚠️ `refund:customer-timeout`은 **존재할 수 없어 지웠다.** 고객이 펀딩을 안 하는 건
> `bonded` 단계이고 그때는 온체인 자금이 없다 → `bonded → cancelled`(tx 없음)이지
> `settling → refunded`가 아니다. 그 경우 보증금 처리는 `cancelled` 쪽에서 한다
> (고객 몰수 / 후원자 환불). v2 표가 전이표와 어긋나 있었다.

## §4.2 전이표

```ts
const ONCHAIN_TRANSITIONS: Record<OnchainState, readonly OnchainState[]> = {
  listed:    ['claimed', 'cancelled'],
  claimed:   ['listed', 'bonded', 'cancelled'],   // listed = 보증금 미결제 타임아웃(30분)
  bonded:    ['funding', 'cancelled'],            // cancelled = 6h 내 펀딩 없음
  funding:   ['funded', 'bonded', 'cancelled'],   // cancelled = **펀딩 tx 부재가 확인된 경우만**
  funded:    ['presigned', 'settling', 'funding'],  // settling = reserve 미달 / **O-015 보증금 사망 → fold**
  presigned: ['remitted', 'settling', 'funding'],   // **분쟁 진입 없음** — 계좌 이의는 시계를 안 멈춘다 (§7.6)
  remitted:  ['settling', 'disputed'],            // disputed = 24h 내 고객 무응답 **또는** 이의제기
  disputed:  ['settling'],                        // 어드민 판정 **또는 양쪽 동의 릴리스** (O-011)
  settling:  ['released', 'refunded', 'sponsor_wins', 'customer_wins'],
  //           **되돌아가지 않는다.** 멤풀 이탈은 재브로드캐스트로 대응한다 (O-005)

  released: [], refunded: [], sponsor_wins: [], customer_wins: [],
  cancelled: [], swept: [],
};
```

**핵심 불변조건** (각각 테스트로 박는다):

| ID | 불변조건 | 막는 것 |
|---|---|---|
| O-001 | **`funded`** 이후에는 `cancelled`로 못 간다. `funding`에서는 **펀딩 tx 부재가 확인될 때만** 갈 수 있다 | 확정된 자금이 tx 없이 "취소"되는 회계 구멍 (리뷰 R2-H2) |
| O-002 | `funded` 이전에는 계좌 정보가 안 나간다 | 에스크로 없이 원화가 오가는 것 |
| O-003 | `presigned` 이전에는 계좌 정보가 안 나간다 | 후원자가 사전서명 없이 계좌만 받고 튀는 것 |
| O-004 | 모든 터미널은 **컨펌된 txid**를 근거로 가진다 | 어드민이 tx 없이 상태만 발행하는 것 |
| O-005 | **`settling`은 되돌아가지 않는다.** 멤풀 이탈은 **같은 tx 재브로드캐스트**로 대응한다 | 환불·분쟁 종결이 `remitted`로 돌아가는 무의미한 전이 (리뷰 R2-H4) |
| O-006 | `swept`는 어드민이 **관측**만 하고 만들지 않는다 | 타임락 회수를 어드민이 대신 주장하는 것 |
| **O-007** | **릴리스는 고객이 원화 수령을 확인해야만 나간다. `remitted` 이벤트는 트리거가 아니다** | **후원자가 원화를 안 보내고 `remitted`만 발행해 BTC를 가져가는 것** (리뷰 R1-H3) |
| **O-008** | **가격은 확정된 N컨펌 위에서만 유효하다. 컨펌이 N 아래로 내려가면 `funded` 판정과 가격을 함께 폐기한다** | 리오그로 사라진 펀딩 위에 가격이 고정된 채 남는 것 (리뷰 R1-H2) |
| **O-009** | **어떤 상태에서도 한쪽이 무기한 유리한 옵션을 쥐지 못한다.** 마감이 없는 상태는 **머무는 것으로 아무도 이득을 못 보는 상태**뿐이고, 그 근거를 명시한다 | 한쪽이 무기한 옵션을 쥐는 것 (리뷰 R1-H1, R3-H1·H3에서 정밀화) |
| **O-010** | **`remitted` 마감을 넘기면 `disputed`로 강제 전이한다. 고객의 동의를 묻지 않는다** | **고객이 원화를 받고 침묵으로 버티다 타임락으로 전액 회수하는 것** (§7 T) |
| **O-011** | **`disputed`에서 한쪽이 단독으로 나갈 수 없다.** 출구는 ① 어드민 판정 ② **릴리스**(`{C,S}`) 둘뿐이고, ②는 **`remitted` 유래 분쟁에서만** 앱이 돕는다 | 분쟁을 건 쪽이 슬쩍 빠지는 것 (R3-H1) + 릴리스 출구를 옵션으로 쓰는 것 (R4-H1) |
| **O-012** | **원화가 오간 뒤 고객 cosign 없이 타임락까지 끌리는 경로는 존재하지 않는다.** 모든 마감의 합이 타임락보다 한참 안쪽이다 | 침묵으로 시간만 벌어 타임락을 부르는 것 (리뷰 R2-H1) |
| **O-013** | **후원자의 마감은 후원자가 통제할 수 있는 시점부터 센다** | 고객 지연 탓에 후원자가 몰수당하는 비대칭 (리뷰 R2-H3) |
| **O-014** | **`bonded` 이후 `cancelled`로 가려면 "주소에 컨펌 UTXO 없음 + 펀딩 tx 멤풀에 없음"을 확인해야 한다** | 취소 직후 펀딩이 컨펌돼 **아무도 안 보는 주소에 자금이 갇히는 것** (리뷰 R3-H2) |
| **O-016** | **고객 앱은 T0 가격이 낡은 릴리스에 cosign하지 않는다.** 경고 후 명시적 우회만 허용한다 | 후원자가 늦게 원화를 보내 **낡은 가격으로 체결**시키는 것 (리뷰 R4-H1·L2) |
| **O-015** | **`funded` 진입 시 후원자 보증금이 살아 있는지 확인한다.** 죽었으면 가격을 고정하지 않는다 | 펀딩이 늦게 컨펌되는 사이 보증금 CLTV가 만료돼 **무담보 옵션 창**이 열리는 것 (리뷰 R3-H3) |

## §4.3 라이트닝 FSM과의 대응

일부러 같은 모양으로 맞췄다 — 리뷰와 재사용이 쉬워진다.

| 라이트닝 | 온체인 | 공통점 |
|---|---|---|
| `escrowed` | `funded` | 고객 자금이 잠겼다 |
| `invoiced` | `presigned` | **후원자가 받을 준비를 마쳐야 계좌가 나간다** |
| `remitted` | `remitted` | 후원자가 송금을 주장했다 |
| `paid` | `released` | 후원자가 받았다 |

`invoiced ↔ presigned`가 특히 중요하다. 라이트닝에서 "인보이스를 내야 계좌를
본다"로 고친 그 설계가 온체인에서는 "사전서명을 내야 계좌를 본다"가 된다.
[DESIGN-LATE-INVOICE.md](DESIGN-LATE-INVOICE.md)의 공격 분석이 **그대로 적용된다.**

| `timelock-blocks` | `8064` | 스크립트에 들어간 실제 값 |
| `funding-txid` | 펀딩 txid:vout | `funding` 이후 |
| `funding-confs` | 관측된 컨펌 수 | `funded` 판정 근거 |
| `price-krw` | 확정된 총 KRW | `funded`에서 고정 |
| `payout-sat` | 후원자가 받을 sat (수수료 차감 후) | `funded`에서 고정 |
| `release-fee-sat` | 릴리스 tx 수수료 (고정) | `funded`에서 고정 |
| `krw-deadline` | 원화 송금 마감 unix초 | **계좌정보 공개 시점**에 설정 (O-013) |
| `settlement-kind` | `release\|refund\|sponsor_win\|customer_win` | `settling` |
| `settlement-txid` | 종결 txid | `settling` 이후 |

## §5.2 새 `REQUEST_ACTIONS`

```ts
ONCHAIN_ORDER_REQUEST: 'onchain-order-request',  // 고객 → 어드민: 의뢰 등록
ONCHAIN_CLAIM:         'onchain-claim',          // 후원자 → 어드민: 클레임
ONCHAIN_FUNDED:        'onchain-funded',         // 고객 → 어드민: 펀딩 txid 신고
ONCHAIN_PRESIG:        'onchain-presig',         // 후원자 → 어드민: 주소 + 사전서명
ONCHAIN_COSIGN:        'onchain-cosign',         // 고객 → 어드민: 최종 서명 + 브로드캐스트 결과
ONCHAIN_DISPUTE:       'onchain-dispute',        // 양쪽 → 어드민: 분쟁 제기
                                                 // 유효 상태 = presigned, remitted (§5.2b)
```

⚠️ **파서에 반드시 등록한다.** 이 자리에서 두 번 빠뜨렸다(`push-subscription`,
`sponsor-invoice` — 둘 다 발행은 되는데 파서가 버려서 조용히 실패했다).
[parse-request.test.ts](admin/src/tests/parse-request.test.ts)의 **전수 census
테스트가 이미 있으므로**, 액션을 추가하면 그 테스트가 먼저 깨진다. 그게 정상이다.

### ⚠️ `ONCHAIN_COSIGN`은 릴리스 전용이 아니다 (리뷰 R1-M4)

`{A,C}`를 쓰는 종결은 **전부 고객 서명이 필요**하다 — 환불(`refund:*`)과
고객승 분쟁(`customer_win`)까지. 즉 **어드민 혼자서는 환불도 못 한다.**

그래서 액션 하나에 `purpose`를 실어 재사용한다:

```ts
{ action: 'onchain-cosign', purpose: 'release' | 'refund' | 'dispute-customer', psbt, txid? }
```

**UX에 미치는 영향이 크다**: "마감 초과 → 자동 환불"이 진짜 자동이 아니다.
어드민이 환불 tx를 만들어 서명해두고 **고객이 돌아와 서명할 때까지 기다린다.**
그동안 고객 자금은 잠긴 채다(자기 돈이라 감수 가능하고, 최후에는 타임락이 있다).

→ 고객에게 **Web Push로 "환불 서명이 필요합니다"** 를 보낸다. 안 오면 타임락이 받는다.

## §5.2b `ONCHAIN_DISPUTE`가 유효한 상태 (리뷰 R3-L5 / R4-H1·M1)

| 상태 | 분쟁 **상태 진입** | 비고 |
|---|---|---|
| `bonded`·`funding`·`funded` | ❌ | 자금 미확정. 타임아웃이 처리한다 |
| `presigned` | ❌ — **시계를 멈추지 않는다** | 계좌 이의는 **증거 첨부**로만 (아래) |
| `remitted` | ✅ 양쪽 | 원화 수령 여부 다툼 |
| `disputed` | — | 이미 분쟁 중 |

### 계좌 이의는 상태가 아니라 증거다

후원자가 "계좌를 못 쓴다"고 할 때 **`disputed`로 보내지 않는다.** 그러면 원화 마감
시계가 멈추고 **무한 옵션이 열린다**(§7.6 R4-H1).

```
후원자 → 어드민: { action:'onchain-dispute', stage:'account-unusable', 증거 }
  → 주문에 증거로 붙는다. **원화 마감은 그대로 흐른다**
  → 마감이 차면 refund:sponsor-timeout — 에스크로가 소모되고 사전서명이 죽는다
  → 그 증거는 **후원자 보증금을 몰수할지 환불할지만** 가른다
```

- 증거가 정당하면 → `refund:sponsor-timeout`이되 **보증금 환불** (사실상 `refund:customer-late`)
- 근거가 없으면 → **몰수**. 무고한 이의 제기 자체가 몰수 사유다

> R3-L5가 지키려던 것(나쁜 계좌를 만난 후원자 구제)은 **그대로 유지된다** —
> 정당하면 보증금을 돌려받는다. 잃는 건 "거래를 살려보는" 선택지뿐인데,
> 계좌가 정말 나쁘면 애초에 살릴 수 없다.

## §5.3 계좌 정보

기존 `ACCOUNT_INFO` + NIP-44를 **그대로 재사용**한다. 전송 계층을 새로 만들 이유가
없고, 게이트(`canSendAccountInfo`)만 온체인 FSM 버전을 추가한다.

# §6. 금액 · 시간 규약

## §6.0 돈의 흐름 한눈에 (v3 신설)

전 경로를 따라가며 **누가·언제·얼마를·누구에게** 내는지 한 표로 고정한다.
v2에는 이게 없어서 수수료 부담자가 경로마다 빠져 있었다.

### 정상 경로

| 단계 | 내는 쪽 | 금액 | 받는 쪽 | 성격 |
|---|---|---|---|---|
| `listed` | 고객 | 보증금 `1%` (§12 R-Q1) | 어드민 (LN accepted) | **잠김** — 성공 시 환불 |
| `bonded` | 후원자 | 보증금 **`3%`** (§12 R-Q1) | 어드민 (LN accepted) | **잠김** — 성공 시 환불 |
| `funding` | 고객 | `amountSat` | 에스크로 주소 | 이동 |
| `funding` | 고객 | **펀딩 tx 수수료** | 채굴자 | **소각** (지갑이 정함, 우리 회계 밖) |
| `remitted` | 후원자 | `priceKrw` | **고객 은행 계좌** | 이동 |
| `settling` | (에스크로에서 차감) | `releaseFeeSat` | 채굴자 | **소각 — 실질 후원자 부담** |
| `released` | — | `payoutSat` | 후원자 주소 | 이동 |

```
priceKrw  = round(amountSat × T0 시점 시세)     ← 후원자는 에스크로 전액을 산다
payoutSat = amountSat − releaseFeeSat           ← 받는 건 수수료를 뗀 뒤
```

### 온체인 tx는 한 쪽에 하나씩

**고객은 펀딩 tx를, 후원자는 릴리스 tx를 문다.** 서비스 수수료가 0인 트랙이라
온체인 수수료만 있고, 그걸 **각자 자기 tx로 나눠 내는** 구조다.

- 고객: "`amountSat`을 팔았고 `amountSat`어치 원화를 받았다" — 펀딩 수수료는 자기 지갑에서
- 후원자: "`amountSat`을 샀고 네트워크 수수료를 뗀 만큼 받았다" — 거래소 출금과 같은 모양

어드민은 정상 경로에서 **한 푼도 안 받는다**(중재료는 분쟁에만).

> ⚠️ **v2는 반대로 적었다**(`priceKrw = payoutSat × 시세` → 고객이 양쪽 부담).
> 메커니즘은 같다 — 수수료는 어느 쪽이든 UTXO에서 나간다. **갈리는 건 KRW를
> 무엇에 곱하느냐**이고, `amountSat`에 곱하는 쪽이 맞다.
> 자세한 경위는 §14 답변 #3.

> **라이트닝 트랙과 방향이 다른 건 의도된 것이다.** 거기는 전달 레그가 하나뿐이고
> (어드민 → 후원자 결제) 고객이 `payout × 1.005`로 그걸 덮는다. 온체인은 tx가
> **양쪽에 하나씩**이라 각자 자기 것을 무는 게 자연스럽다.

### 온체인 수수료 부담자 — 전 경로

| 경로 | 펀딩 tx | 종결 tx | 실질 부담 | 비고 |
|---|---|---|---|---|
| `released` | 고객 | `releaseFeeSat` | **고객 1 / 후원자 1** | 설계대로, 한 쪽에 하나씩 |
| `refund:reserve` | 고객 | 환불액에서 차감 | **고객 2회** | 아무도 과실이 없다 — reserve를 건 대가 |
| `refund:sponsor-timeout` | 고객 | 환불액에서 차감 | **고객 2회** | ⚠️ 후원자 과실인데 고객이 문다 → 몰수금 충당 |
| `sponsor_wins` | 고객 | 에스크로에서 차감 | 후원자가 덜 받음 | 분쟁 |
| `customer_wins` | 고객 | 에스크로에서 차감 | **고객 2회** | 분쟁 → 몰수금 충당 |
| `cancelled` | — | — | **0** | 펀딩 전이라 tx 없음 |
| `swept` | 고객 | 고객 지갑 | **고객 2회** | 어드민 고장 |

정상 경로만 한 쪽에 하나씩이고, **되돌아가는 경로는 전부 고객이 2회 문다.**
종결 tx 입력이 에스크로 UTXO 하나뿐이라 받는 쪽에서 깎이는데, 되돌아갈 때
받는 쪽은 언제나 고객이기 때문이다. 후원자 과실인 경우는 아래 몰수금으로 메운다.

**구조적 사실**: 종결 tx의 입력은 언제나 에스크로 UTXO 하나뿐이므로 **수수료는
받는 쪽의 출력에서 깎인다.** 어드민이 자기 UTXO를 입력으로 얹지 않는 한 "과실 있는
쪽이 수수료를 문다"를 만들 수 없다. v1에서는 그걸 안 넣기로 했다(어드민이 온체인
자금을 운용하면 트랙의 단순함이 무너진다).

⚠️ **그래서 `refund:sponsor-timeout`이 불편하다** — 후원자가 버렸는데 고객이
수수료 2회를 문다. 아래 보증금 몰수와 묶어서 봐야 한다.

### 몰수된 보증금은 어디로 가나 — **어드민이 받고, 충당은 운영 재량**

v2 §7 C는 "후원자 보증금이 고객의 2회 수수료를 **보상**한다"고 적었는데
**그 배선이 없었다.** 몰수 = 어드민이 홀드 인보이스를 settle = **어드민이 갖는다.**

**결정: 자동화하지 않는다. 어드민의 운영 재량으로 처리한다.**

| | |
|---|---|
| **몰수금 수취** | 어드민 (LN settle) |
| **피해자 충당** | **몰수금의 50%** 를 내부 기본값으로 어드민이 수동 송금 |
| **경로** | 이미 있는 분쟁 채팅으로 인보이스를 받아서 보낸다 |

자동화하면 **"피해자가 인보이스를 낼 때까지 대기"라는 상태가 FSM에 하나 더**
생긴다. 드물게 도는 경로에 그건 과하다. 채팅은 이미 있고 어드민은 어차피 불려 나온다.

### ⚠️ 고지할 것과 안 할 것

**고지한다 — 몰수의 조건**: 어떤 마감을 어기면 보증금을 잃는지, 그 마감이 언제인지.
이건 설계의 공정성 자체다. 모르고 잃으면 안 된다.

**고지한다 — 환불 시 수수료 2회는 고객 부담이고 보상이 보장되지 않는다.**
`refund:sponsor-timeout`처럼 후원자 과실이어도 고객이 문다(§6.0 수수료 표).
충당은 재량이므로 **"보상받는다"가 아니라 "보장되지 않는다"** 로 적는다 (리뷰 R2-M3).

**고지하지 않는다 — 몰수금의 행방.** 보증금은 애초에 "트롤하면 이걸 가져간다"는
뜻이고, 몰수됐다는 건 트롤을 했다는 뜻이다. **어드민이 그 돈을 어디 쓰는지는
몰수당한 쪽이 따질 자리가 아니다.**

같은 이유로 **피해자에게도 약속하지 않는다.** 충당은 운영자의 재량이지 권리가
아니다. UI에 "보상받습니다"를 띄우면 그 순간 권리가 되고, 못 줄 사정이 생겼을 때
(몰수가 없었거나, 양쪽 과실이거나) 새 분쟁이 된다. **내부 운영 정책으로만 둔다.**

### 보증금을 얼마로 — **덮어야 할 것에서 유도한다**

"넉넉히"가 맞는 방향이다. **정상 경로에서 보증금은 공짜**이기 때문이다 — 홀드
인보이스가 cancel되면 HTLC가 실패하고 **라우팅 수수료가 0**이다. 성실한 사용자는
아무것도 안 낸다. 이게 보증금을 LN으로 하는 이유다.

다만 "최대한 많이"는 아니다. 보증금은 **덮어야 할 것 둘**에서 유도된다:

```
후원자 보증금 ≥ max( 45분 옵션 프리미엄,  충당 하한 )
                     └ 비율(%)              └ 절대 sats
```

**① 옵션 프리미엄 (비율)** — T0부터 ~50분간 후원자가 쥐는 창(§2.4). 그 구간의
**하락 꼬리를 덮어야** "버리는 게 이득"이 안 된다. 제안 **3%**.

> 근거를 "2σ(≈0.9%)"로 적지 않는다 — 옵션 억제는 평균이 아니라 **꼬리**가 정한다.
> "50분 하락 꼬리(≤3%)를 덮는다"로 잡아야 나중에 "2σ면 1%로 충분하지 않나"라는
> 잘못된 근거가 안 생긴다 (리뷰 R2-L4).

**② 충당 하한 (절대 sats)** — 후원자가 버리면 고객은 온체인 수수료 **2회**를 잃는다.
충당이 몰수금의 50%이므로, 그 50%가 2회분을 덮으려면:

```
하한 = 4 × (현재 feerate 기준 종결 tx 수수료)
```

⚠️ **하한은 상수로 박으면 안 된다.** 수수료가 1 sat/vB일 때와 50 sat/vB일 때
100배가 난다. **클레임 시점 feerate로 계산**한다. 비율만 두면 소액 거래에서
억제력이 0이 된다(1만 sats의 3% = 300 sats < tx 수수료 1회분).

### 고객 보증금은 더 작아야 한다 — 잠기는 시간이 다르다

| | 잠기는 구간 | 최장 |
|---|---|---|
| 고객 보증금 | `listed` → 종결 | **의뢰 만료(7일) + 거래 43시간** |
| 후원자 보증금 | `bonded` → 종결 | **약 43시간** |

고객 보증금이 **4배 가까이 오래 잠긴다.** 그런데 역할은 더 가볍다 —
**등록 시점 스팸 차단**이고 그 일은 등록하는 순간 끝난다.

→ 고객 **1%**, 후원자 **3%**. 같은 숫자를 쓰면 안 된다.

> ⚠️ **올릴 때 잊지 말 것**: IDEA 문서가 이 앱을 만드는 이유로 든 게
> *"운영자가 허들을 올린다 → 신규 배척 → 유동성 더 마름"* 이었다.
> 보증금은 허들이다. **덮어야 할 것을 덮는 선**에서 멈춰야지, 많을수록 좋은 게 아니다.

### 라이트닝 수수료는 누가 무나

보증금은 LN 홀드 인보이스다. **환불(cancel)되면 라우팅 수수료가 0**이다 —
HTLC가 실패하면 수수료가 안 붙는다. 몰수(settle)되면 낸 쪽이 라우팅 수수료까지
잃는다. 정상 경로에서는 **양쪽 다 0**이다.

### 최악 소요 시간

```
claimed 30분 + bonded 6h + funding 12h + (T0+45분) + settling 24h ≈ 43시간
```

그동안 **후원자 보증금이 계속 잠긴다.** 그리고 **가격은 클레임 최대 18시간 뒤**에
정해진다 — 후원자는 가격을 모르는 채 커밋한다.

후원자가 시세 환전이 목적이면 레벨 자체엔 무관심하므로 불리하지 않다(그게 §2.4가
성립하는 이유다). 다만 **유동성이 묶이는 비용은 실재**하므로, `bonded`·`funding`
마감을 더 줄일 수 있는지는 §12 Q10으로 연다.

## §6.1 금액

```
amountSat        고객이 파는 수량 (고객 입력, 펀딩 금액과 정확히 일치)
releaseFeeSat    릴리스 tx 수수료 — funded에서 고정
payoutSat        = amountSat − releaseFeeSat        (후원자가 실제 받는 sat)
priceKrw         = round(payoutSat × 시세)           (후원자가 보낼 원화)
arbitrationFeeSat **몰수된 보증금에서 충당한다.** 분쟁 tx에 어드민 출력을 달지 않는다
settleFeeSat     환불·분쟁 tx의 온체인 수수료 — **종결 시점에 새로 추정**
fundingFeeSat    고객 지갑이 정한다. 우리가 관여하지 않는다 (§6.0)
```

- **후원자는 받는 만큼만 낸다** → KRW는 `amountSat`이 아니라 `payoutSat` 기준.
  즉 **릴리스 수수료는 고객(매도자) 부담**이다 — 고객은 `amountSat`을 넣고
  `payoutSat`어치 원화만 받는다. 라이트닝 트랙에서 고객이 `payout × 1.005`를
  거는 것과 **같은 방향**이다(매도자가 레일 비용을 낸다).
  ⚠️ 아이디어 문서 §⑥은 "후원자 부담"이라고 썼는데 **그쪽이 틀렸다**(리뷰 R1-M2).
  화면에 `받을 원화 = (판매량 − 수수료) × 시세`를 그대로 보여준다
- **분쟁 tx는 수수료를 새로 추정한다.** `releaseFeeSat`은 T0에 고정되는데 분쟁은
  몇 주 뒤에 끝날 수 있다. 그때 고정값을 쓰면 tx가 멤풀에서 썩는다
- 릴리스 수수료를 `funded`에 **고정**해서, 이후 수수료가 튀어도 금액이 안 흔들린다.
  튀어서 tx가 막히면 **후원자가 자기 출력으로 CPFP** (§7 L)
- 펀딩 금액은 **정확 일치**만 받는다. 라이트닝에서 ±5% 근사를 없애고
  `isPayoutAmountExact`로 바꾼 것과 같은 이유 — 금액을 정한 게 우리다
- `payoutSat`이 dust(taproot 330 sat) 이하면 주문 자체를 거부한다

## §6.2 시간

**원칙 (O-009): 마감 없는 상태는 없다.** v1에서 `funded`와 `funding`에 마감이
빠져 있었다(리뷰 R1-H1·R1-M3). 아래 표에 **모든 비터미널 상태가 나온다.**

| 상태 | 마감 | 초과 시 | 근거 |
|---|---|---|---|
| `listed` | 의뢰 만료 (**최대 7일**) | `cancelled` | 익명 오더북 매칭 시간 + CLTV 천장 여유 (§2.2) |
| `claimed` | 30분 | `listed` 복귀 | 보증금 결제는 즉시 가능 |
| `bonded` | 6시간 | `cancelled`, **고객 보증금 몰수** | 고객이 펀딩할 시간 |
| `funding` | **하드 마감 없음.** 12h는 **경고 시점** | 고객에게 RBF 취소/CPFP 안내 + 후원자 지연 고지 | §7.4 — 멤풀 tx는 나중에 컨펌된다 |
| `funded` | **T0+15분** | `settling`(`refund:sponsor-timeout`) | 앱 자동 서명이라 넉넉 |
| `presigned` (고객) | **계좌정보 공개 = `presigned`+5분** | `settling`(`refund:customer-late`), **후원자 보증금 환불** | 발행 버튼 한 번 |
| `presigned` (후원자) | 원화 송금 = **계좌공개+30분** | `settling`(`refund:sponsor-timeout`) | **고객 지연이 후원자 창을 깎지 않는다** (O-013) |
| `remitted` | **24시간** | **`disputed` 강제 전이** (O-010) | 자는 고객이 헛분쟁을 안 만들 정도 |
| `disputed` | **하드 마감 없음** (에스컬레이션만) | 7일: 반복 Push + 대시보드 최상단 / 14일: 이중화 경로 호출 | **자동 해소는 어느 방향이든 탈취다** (§7.5) |
| `settling` | 24시간 | 수수료 부족으로 보고 CPFP 안내 | 컨펌 대기 |

**T0 = `funded` 진입 시각.** 리오그로 `funding`에 돌아갔다 다시 오면 **T0를 새로 잡고
가격도 새 T0 시세로 재고정한다**(O-008, 리뷰 R2-M1).

**후원자 마감만 계좌공개를 기준으로 삼는다**(O-013). 고객 마감이 `presigned`+5분으로
묶여 있으므로 후원자 마감은 늦어도 **T0+50분**을 넘지 않는다 — R1-H1의 "창이 쌓이면
안 된다"는 그대로 지켜진다.

```
T0 ──15분── presigned ──5분── 계좌공개 ──30분── 원화 마감
                                                └ 최대 T0+50분
```

| 그 외 값 | 크기 | 근거 |
|---|---|---|
| 보증금 인보이스 수명 | 의뢰 만료 전체 | 무담보 구간을 없애려고 (§2.2) |
| **펀딩 컨펌 요구 `N`** | **금액별 (§12-Q1)** | 리오그 = 후원자 원화 손실 |
| 타임락 `N` | **8064블록 (~8주)** | 어드민 판정 시간 ≫ 확보 (§7.3, §12 Q2) |
| **후원자 송금 차단 임계** | **1008블록 잔여 (§12-Q2)** | 분쟁 최장의 2배 여유 |

## §6.3 지켜야 할 부등식

```
타임락 잔여        >  분쟁 최장 소요          ← 안 지키면 후원자가 털린다 (§7 F)
의뢰 만료          >  펀딩 대기 + 컨펌 + 송금창
보증금 CLTV        >  보증금 인보이스 수명
payoutSat          >  dust(330)
```

라이트닝 트랙의 [AUDIT-EXPIRY.md](AUDIT-EXPIRY.md)와 **같은 형식**으로 유지한다.
구현이 끝나면 온체인용 만료 전수조사를 한 번 돌린다(§11 P6).

## §7.0 Q가 제일 크다 — 자동화의 유혹 (리뷰 R1-H3)

`remitted`는 **후원자의 일방적 주장**이다. 릴리스가 그 이벤트에 자동 반응하면
후원자는 원화를 한 푼도 안 보내고 BTC를 가져간다.

§9에서 어드민 동작을 대거 자동화하는데, 그 흐름에 휩쓸려 cosign까지 자동화하기
쉽다. **O-007이 그걸 막는 유일한 방어선**이다.

라이트닝 트랙에서 이 역할은 고객의 `payment-confirm`이 한다 —
[OrderRow.tsx:83](../customer/src/buyer/components/OrderRow.tsx#L83)에서 **고객
앱이** 발행한다. 온체인도 동일하게 **고객이 은행 입금을 눈으로 확인하고 버튼을
누른다.**

## §7.2 ~~한국 은행의 지연이체~~ — **철회** (v3)

v2에서 "지연이체 서비스를 켜둔 후원자는 45분 창을 구조적으로 못 맞춘다"며 클레임 전
사전 점검 문항을 넣자고 했다. **과했다. 철회한다.**

- **옵트인이고 드물다.** 일반 즉시이체를 쓰면 몇 초다
- **후원자 과실이다.** 그런 이체 수단을 고른 건 본인이고, 늦게 도착하면 분쟁에서
  고객 편을 들면 끝난다
- **새 범주가 아니다.** 라이트닝 트랙의 F5(후원자가 늦게 보내 에스크로가 먼저 죽음)와
  같은 부류이고, 거기서 "후원자가 버튼을 안 누른 불성실함"으로 이미 정리했다

45분 창의 근거를 "실시간 이체는 몇 초"로 적어놓고 그 전제를 깨는 반례를 찾다가
나온 것인데, **반례의 무게를 안 재고 바로 설계에 넣은 게 잘못**이다.

→ 남기는 것은 **송금 화면의 경고 한 줄**뿐이다: "즉시 이체만 사용하세요.
   지연 도착 시 시간 안에 완료되지 않아 보증금을 잃습니다."
   사전 점검 문항도, 클레임 차단도 없다.

## §7.6 사전서명은 만료되지 않는다 — 그래서 UTXO를 써서 죽인다 (리뷰 R4-H1)

### 공격 (R1-H1의 재발)

v5가 `presigned → disputed`와 분쟁 중 릴리스를 **동시에** 열면서 구멍이 났다:

```
presigned → 후원자가 "계좌가 이상하다" 분쟁 제기 → disputed (마감 없음, 최장 8주)
→ 시장을 본다
   유리하면: 원화를 보낸다 → 고객이 확인·cosign → T0 가격으로 체결
   불리하면: 가만히 있는다 → 보증금 3%만 잃는다
```

**비용은 고정 3%, 창은 최장 8주.** 8주 변동폭이 3%를 훌쩍 넘으니 **기대값이 양수**다.
R1-H1이 막았던 그 구멍이다.

### ⚠️ 리뷰어 조치안 둘 다로는 안 닫힌다

리뷰는 "`presigned → disputed` 제거" 또는 "fold-only"를 제안하며
*"mutual-release는 `remitted` 유래 분쟁에만 — 거기는 원화가 이미 흘렀으니 옵션이 없다"*
고 했다. **그 전제가 틀렸다. `remitted`는 후원자의 미검증 주장이다.**

```
presigned → 후원자가 원화를 안 보내고 remit-request만 발행 → remitted
→ 고객이 은행 확인, 아무것도 없음 → cosign 안 함
→ 24h 후 자동 disputed (O-010)
→ 똑같이 무한 창. 유리해지면 그때 원화를 보낸다
```

**입구를 막는 걸로는 못 닫는다.** 후원자는 언제든 `remitted`를 거짓 발행해 `disputed`에
들어갈 수 있다.

### 근본 원인 — 사전서명은 영원히 유효하다

`{C,S}` 릴리스에 필요한 후원자 서명은 **`presigned`에서 이미 나왔다.** 그래서
"양쪽 동의 릴리스"의 실체는 **고객이 사전서명을 완성하는 것**이고, 후원자의 재동의가
필요 없다(리뷰 R4-L2 지적이 정확하다).

**비트코인에서 서명은 만료되지 않는다.** nLockTime은 실행을 늦출 뿐 무효화하지 못한다.
FSM 규칙으로 막아도 **양쪽이 서명을 들고 있으면 앱 없이 직접 브로드캐스트**할 수 있다.

### 그래서 막는 법은 하나뿐 — **입력을 써버린다**

사전서명은 특정 UTXO를 소모한다. **그 UTXO가 다른 tx로 쓰이면 사전서명은 즉시 무효**다.

→ **후원자에게 불리한 종결(`refund:*`, `customer_win`)은 전부 `{A,C}`로 에스크로를
소모한다. 그게 옵션을 죽이는 실제 집행이다.** FSM 규칙이 아니라 체인이 집행한다.

**따라서 옵션 창의 실제 길이 = 그 종결 tx가 컨펌되기까지의 시간**이다. 8주가 아니다.

### 조치 셋

**① `presigned → disputed`를 없앤다. 계좌 이의는 시계를 멈추지 않는다.**

후원자의 "계좌 사용 불가" 주장은 **상태 전이가 아니라 주문에 붙는 증거**다.
원화 마감은 그대로 흐르고, 마감이 차면 `refund:sponsor-timeout`으로 **에스크로가
소모되며 사전서명이 죽는다.** 그 주장은 **보증금을 몰수할지 환불할지만** 가른다.

> 이러면 R3-L5(나쁜 계좌를 만난 후원자 구제)도 유지된다 — 정당하면 보증금을 돌려받는다.
> 잃는 건 "거래를 살려보는" 선택지뿐인데, 애초에 계좌가 나쁘면 살릴 수도 없다.

**② `remitted` 유래 분쟁은 빠르게 판정한다.**

"원화 증거가 없는 `remitted`"는 사실상 기계적 판정이다 → **`customer_win` → `{A,C}` 소모
→ 사전서명 사망.** 거짓 `remitted`를 발행한 후원자는 보증금도 잃는다.
어드민이 지체할수록 창이 길어지므로 §7.5 에스컬레이션이 여기서도 작동한다.

**③ 고객 앱이 낡은 가격을 거부한다 (O-016).**

①②를 해도 **어드민이 느리면 창이 남고**, 앱 규칙은 직접 브로드캐스트를 못 막는다.
마지막 방어선은 **손해를 보는 당사자 자신**이다.

고객 앱은 **T0 가격 유효창을 넘긴 릴리스에 cosign하지 않는다.** 화면에 "이 가격은
N시간 전 시세입니다. 지금 시세로는 X원 손해입니다"를 띄우고 **명시적 우회만** 허용한다.

> O-007("고객이 원화 수령을 확인해야 릴리스")은 **분쟁 중에도 그대로**다.
> O-016은 거기에 "가격도 확인해야 한다"를 더한 것이다.

## §7.5 마감 없는 상태 둘 — 왜 예외인가 (리뷰 R3-H1·H3)

O-009가 "마감 없는 상태는 없다"였는데 **`disputed`와 `funding`이 예외**가 됐다.
예외를 숨기지 말고 **왜 머물러도 안전한지**를 적는다. O-009도 그렇게 고쳤다.

### `disputed` — 자동 해소가 어느 방향이든 탈취다

| 자동 해소 | 결과 |
|---|---|
| 시간 지나면 `sponsor_win` | **공격 U** — 후원자가 영수증 위조 후 기다리기만 하면 된다 |
| 시간 지나면 `customer_win` | **공격 T** — 고객이 원화 받고 버티기만 하면 된다 |

**판정은 사람만 할 수 있다.** 그래서 하드 마감 대신 **에스컬레이션**을 둔다:

- 진입 즉시 Push + 대시보드 **타임락 잔여 오름차순** 정렬
- **7일**: 반복 Push + 최상단 고정
- **14일**: 이중화 경로(별도 기기·연락 수단) 호출
- **최종 백스톱**: 타임락(8주). 어드민이 끝내 안 오면 고객이 회수 — §7.3의 수용된 한계

### 느리지만 정직한 고객을 처벌하지 않는다 (R3-H1 b)

24시간을 조금 넘겨 돌아온 고객이 "돈 받았으니 끝내자"고 해도, O-011이
**어드민 판정만** 허용하면 출구가 `sponsor_win`/`customer_win`뿐이라 **보증금 몰수 +
중재료**가 붙는다. 늦었을 뿐인데 과하다.

→ **`disputed`에서 양쪽이 서명한 릴리스(`{C,S}`)로 나가는 길을 연다.**

O-011의 의도("한쪽이 단독으로 슬쩍 빠지는 것을 막는다")와 **충돌하지 않는다** —
`{C,S}`는 **정의상 양쪽 합의**이고, 한쪽이 침묵해 타임락을 부르는 탈취는 그대로 막힌다.
처리는 **정상 `release`와 동일**하다: 양쪽 보증금 환불, 중재료 없음.

> 악용 가능성을 따져봤다. 후원자가 동의를 거부해 `sponsor_win`으로 몰아가도
> **받는 BTC는 같고** 고객 몰수분은 어드민에게 가므로 후원자가 얻는 게 없다.
> 고객이 일부러 늦춰 `disputed`를 거쳐 릴리스해도 얻는 게 없다.

**그리고 그 앞에 유예 경고를 둔다** — `remitted` 마감 2시간 전에 고객에게
"곧 분쟁으로 넘어갑니다" Push. 느린 고객 대부분이 여기서 스스로 끝낸다.

### `funding` — 머물러도 아무도 이득을 못 본다

§7.4 때문에 하드 마감이 없어졌다(멤풀에 있으면 취소 불가). 그래도 안전한 이유:

- **고객**: 자기 돈이 멤풀에 묶여 있다. 끌수록 손해다
- **후원자**: 보증금이 묶이지만 **자체 LN 만료로 환불**된다. 영구 인질이 아니다
- **상한**: 멤풀이 보통 2주면 tx를 떨군다 → 그때 부재가 확인돼 `cancelled`

⚠️ **다만 그 사이 후원자 보증금이 먼저 죽을 수 있다**(리뷰 R3-H3). 그 상태로
펀딩이 컨펌돼 `funded`가 되면 **T0+50분 옵션 창이 무담보**다.
→ **O-015**: `funded` 진입 시 후원자 보증금 생존을 확인하고, 죽었으면 **가격을
고정하지 않고 접는다** — `funded → settling`(`refund:bond-expired`).

> **"재발행"은 안 한다**(리뷰 R4-M2). `funded → bonded` 전이를 새로 만들어야 하고,
> 그 사이 가격이 또 흔들린다. fold 하나로 통일한다.
>
> 이때 후원자 보증금은 **이미 LN 만료로 환불된 상태**라 따로 처리할 게 없고,
> **고객은 펀딩 수수료를 잃는다.** 누구 과실도 아니라 몰수도 없다 — `refund:reserve`와
> 같은 성격이다.

## §7.4 `funding`에서의 취소는 "tx가 없다"를 증명해야 한다 (리뷰 R2-H2)

O-001을 `funded`로 좁혔지만, **리뷰어의 "자금이 확정 안 됐으니 취소가 안전하다"는
그대로 받으면 안 된다.**

멤풀 tx는 **몇 시간 뒤에도 컨펌될 수 있다.** 12시간 지났다고 `cancelled`로 보내면,
그 뒤 펀딩이 컨펌됐을 때 **취소된 주문의 2-of-3 주소에 자금이 갇힌다.** 어드민도
후원자도 그 주문을 더 안 보고 있다.

**규칙**: `funding → cancelled`는 **펀딩 tx가 멤풀에도 없고 컨펌도 안 된 것을 확인한
뒤에만** 간다(RBF로 교체됐거나 충돌 tx가 컨펌된 경우).

**12시간이 지났는데 아직 멤풀에 있으면 `funding`에 머문다.** 대신:
- 고객에게 "수수료가 낮아 안 잡힙니다. 취소(RBF)하거나 CPFP하세요" 안내
- 후원자에게 지연 고지. 후원자 보증금은 **자체 LN 만료로 환불**되므로 영구 인질은 아니다

> 멤풀은 보통 2주면 tx를 떨군다. 그때 부재가 확인되고 `cancelled`로 간다.

## §7.3 T — 고객이 침묵으로 양쪽을 먹는 경로 (리뷰 #2)

### 공격

```
presigned → 계좌 전달 → 후원자 원화 송금 → remitted
→ 고객이 cosign을 안 한다. 이의도 안 낸다. 그냥 가만히 있는다
→ 아무 상태 변화 없이 정지 (v3.2 FSM은 remitted → settling뿐)
→ 타임락 만기 → 고객이 혼자 회수. 원화 + BTC 양쪽 획득
```

**타임락 리프는 원래 "어드민이 증발해도 고객은 되찾는다"는 보험**인데, 고객이
그걸 **능동적으로 유도**할 수 있다. 가만히 있기만 하면 된다.

### 시계를 먼저 정확히 하자

`OP_CSV`는 **상대** 타임락이라 **펀딩 UTXO 컨펌**부터 센다. 마감 구조상 원화는
항상 `T0+45분`에 흐르므로:

```
T0        펀딩 컨펌 = 타임락 시계 시작
T0+45분   원화 송금          ← 타임락이 거의 전량 남아 있다
T0+N블록  고객 단독 회수 가능
```

→ **어드민에게 사실상 타임락 전체가 주어진다.** 리뷰 #1이 "미정으로 두면 안 된다"고
한 Q2(후원자 송금 차단 임계)는 **거의 발동하지 않는다** — 원화를 보내는 시점에
타임락은 언제나 만기 전량이다. 안전망으로 남기되 주 방어선이 아니다.

**진짜 방어선은 "타임락 길이 > 어드민 판정 시간"이다.**

### 막는 법 — 침묵이 아무것도 안 하게

**① `remitted`에 마감을 건다 (O-010).** 24시간 내 고객이 cosign도 이의제기도 안 하면
**`disputed`로 강제 전이**한다. **고객 동의를 묻지 않는다.**

> 값은 리뷰 #2의 제안(24h)을 받았다. 은행 확인 자체는 몇 분이지만, 6시간으로 조이면
> **자는 고객이 헛분쟁을 만들어** 어드민이 불려 나온다 — "분쟁 때만 부른다"는 목표와
> 어긋난다. 강제 전이는 손실이 아니라 심판 요청이므로 넉넉해도 안전하다.

**② `disputed`의 출구는 어드민 판정뿐이다 (O-011).** 그리고 판정은 **고객 없이
집행된다** — `sponsor_win`은 `{A,S}`라 어드민과 후원자만으로 서명이 된다.
**이게 강제 분쟁이 실효를 갖는 이유다.**

**③ 어드민을 강하게 부른다.** 침묵 공격은 어드민이 와야만 깨진다.
- `disputed` 진입 즉시 어드민에게 Web Push
- 어드민 대시보드가 `disputed`를 **타임락 잔여 블록 오름차순**으로 정렬
- 잔여가 임계 아래면 최상단 고정 + 반복 알림

**④ 타임락을 길게.** 4032블록(4주) → **8064블록(8주)** 을 제안한다.
어드민이 정상이면 며칠이면 끝나므로, 긴 값은 휴가·질병·기기분실을 덮는 여유다.

> **대가**: 어드민이 진짜로 죽었을 때 **고객이 자기 돈을 되찾는 시간도 그만큼 길어진다.**
> 후원자가 아예 안 붙어 환불(`{A,C}`)만 필요한 경우까지 8주를 기다린다.
> 그래서 무한정 늘릴 수는 없다 — §12 Q2에서 확정한다.

### ⚠️ 못 막는 경로는 정직하게 적는다

**어드민이 판정 전에 영구히 사라지면 T는 못 막는다.** 타임락 리프는 스크립트에
박혀 있어 앱이 무슨 상태를 쓰든 체인은 고객의 서명을 받아준다.

이건 **설계상 받아들인 것**이다. 타임락을 빼면 어드민 증발 시 고객 자금이 영구
동결되고(§타임락 절), 그건 "비수탁"이라는 말 자체를 부정한다. **어드민 급사에
대비하면서 동시에 어드민 급사 중 악의적 고객을 막을 수는 없다.**

남는 건 확률을 줄이는 것뿐이다 — 긴 타임락 + 강한 호출 + 어드민 운영 이중화.

### ⚠️ 이 수정이 만든 새 위험 — 공격 U

강제 분쟁은 **어드민이 한쪽 증거만 들고 판정하는 상황**을 만든다. 고객이 침묵하니
후원자의 이체 영수증만 있다. 그러면 **후원자가 영수증을 위조해 부재중인 honest
고객을 칠 수 있다**(기기 분실, 입원 등).

→ **침묵을 곧바로 패소로 보지 않는다.** 판정 원칙:

- 후원자 증거는 **금액·수취인명·시각이 주문과 맞아야** 한다. 스크린샷 한 장은 부족
- 고객에게 **Push + 앱 내 최상단 경고**를 반복하고, **판정 전 최소 대기**를 둔다
- 고객이 끝내 무응답이고 증거가 정합하면 그때 `sponsor_win`
- 증거가 부실하면 **판정을 보류**한다 — 보류는 타임락이 고객에게 유리하게 끝난다는
  뜻이므로, 어드민은 "확신이 없으면 후원자에게 주지 않는다"가 기본값이다

> 라이트닝 트랙의 원칙과 같다: **받지 못했으면 주지 않는다**(F3).
> 여기서는 "받았다는 증거가 부실하면 주지 않는다"가 된다.

## §7.1 F가 제일 무섭다 — 라이트닝에서 이미 겪었다

F는 **F2와 정확히 같은 모양**이다([AUDIT-EXPIRY.md](AUDIT-EXPIRY.md)):
*에스크로가 2시간 남았는데 6시간짜리 인보이스를 받아줘서, 후원자가 원화를 보낸 뒤
HTLC가 타임아웃으로 환불된다 — 후원자만 잃는다.*

온체인에서는 "에스크로 만료"가 "타임락 만료"로 바뀔 뿐 구조가 같다. 조치도 같다:
**되돌릴 수 없는 행동(원화 송금) 직전에 내 보호 창이 살아 있는지 확인시킨다.**

# §9. 어드민이 자동으로 하는 것 / 사람이 하는 것

라이트닝 트랙에서 "판단이 필요 없는 블로커는 자동화"로 정리한 것과 같은 기준.

| 동작 | 자동 | 이유 |
|---|---|---|
| 클레임 승인 | ✅ | 판단 없음 |
| 보증금 인보이스 발행 | ✅ | |
| 에스크로 주소 발행 | ✅ | 키 파생 + 백업 확인이 전부 |
| 펀딩 컨펌 감시 → `funded` | ✅ | 체인이 진실 |
| 가격 확정 | ✅ | 시세 스냅샷 |
| 사전서명 검증 → `presigned` | ✅ | 순수 검증 |
| 창 만료 → 환불 tx **어드민 서명** | ✅ | 시계가 진실 |
| 환불 tx **고객 서명** | ❌ **고객** | `{A,C}`라 어드민 혼자 못 한다 (R1-M4) |
| **릴리스 cosign** | ❌ **고객** | **O-007 — 자동화 절대 금지** (R1-H3) |
| 종결 tx 컨펌 감시 | ✅ | |
| `remitted` 마감 → `disputed` 전이 | ✅ | 시계가 진실. **고객 동의 불필요** (O-010) |
| **분쟁 판정** | ❌ **사람** | 은행 증빙 판단. **증거 부실이면 보류가 기본값** (§7.3) |
| **어드민 키 백업 실패 대응** | ❌ **사람** | |

즉 **분쟁 때만 사람이 불려 나온다.** 라이트닝 트랙과 같은 목표다.

# §10. 재발 방지 — 오늘 배운 것 반영

1. **상태 표는 전부 `Record<OnchainState, …>`.** 폴백(`?? state`)을 쓰지 않는다.
   오늘 그 폴백 때문에 영어 "invoiced"가 다섯 군데 중 넷에서 샜다.
2. **FSM을 고치면 네 곳이 세트**: 전이 맵 → 알림 문구 → 문서 → 진행도 → 배지.
   온체인 FSM도 처음부터 이 다섯을 같이 만든다.
3. **새 액션은 파서 census 테스트가 먼저 깬다.** 깨지는 게 정상이고, 거기서
   파서 등록을 빠뜨렸는지 잡힌다.
4. **터미널 목록은 전이 맵에서 유도**한다. 손으로 나열하지 않는다
   ("나가는 전이가 없는 상태 = 종결" 테스트를 온체인에도 복제).
   ⚠️ **`swept`은 예외다** — 어드민이 만드는 상태가 아니라 **체인에서 관측**하는
   결과다(O-006). 전이 맵에 들어오는 화살표가 없으므로 유도 테스트에 명시적
   예외로 박는다. **펀딩 컨펌 이후 어느 상태에서든** 타임락이 차면 `swept`으로
   관측될 수 있다 (리뷰 R3-L4).
5. **금액 근사 매칭 금지.** txid·주소·금액 정확 일치만. 바인딩 불가면 defer.

# §12. 리뷰 세션이 답해야 할 질문

구현 착수 전 여기가 전부 닫혀야 한다.

**Q1. 펀딩 컨펌 수** 🔴 **HIGH로 승격** (리뷰 R1-LOW) — 리오그는 후원자의 원화
손실로 직결되므로 미정으로 둘 수 없다.
**제안**: `< 100k sat → 1conf`, `< 1M sat → 2conf`, 그 이상 `3conf`.
근거: 깊은 리오그 비용이 거래액을 넘으면 공격 동기가 사라진다. **확인 필요.**

**Q2. 타임락 길이와 송금 차단 임계** — **v3.3에서 성격이 바뀌었다**(§7.3).

CSV는 **펀딩 컨펌**부터 세고 원화는 항상 `T0+45분`에 흐르므로, **송금 시점에
타임락은 언제나 만기 전량**이다. 리뷰 #1이 "유일한 방어"라고 본 차단 임계는
**거의 발동하지 않는다** — 안전망으로만 남긴다(잔여 1/4 미만이면 경고).

바뀐 질문: **타임락을 얼마로 두나.** 제안 **8064블록(8주)**.
- 길수록 → 어드민이 침묵 공격(§7.3 T)을 깰 시간이 는다
- 길수록 → **어드민이 진짜 죽었을 때 고객이 자기 돈을 되찾는 시간도 는다**
- 8주가 이 둘의 접점으로 맞나? **어드민 최장 부재 추정치가 필요하다**

**Q3. 창 만료 직전 송금의 판정 기준**(§7 P) — 은행 입금 시각인가, 버튼 시각인가?
입금 시각이면 증빙을 어떻게 신뢰하나. 라이트닝 트랙 F5(`invoiced` 안전망 없음)와
같은 성격의 문제다.

**Q4. 중재료 징수** — 분쟁 tx에 어드민 출력을 다는 방식이면 판정과 동시에 금액이
확정되고 **사후 청구가 불가능**하다. 정액인가 정률인가? 패소자 부담인가 분담인가?

**Q5. 고객 보증금 몰수 기준**(§7 B) — 펀딩을 안 한 게 악의인지 사고인지 구분 불가다.
전액 몰수는 가혹하고 무조건 환불은 억제가 안 된다.

**Q6. `swept` 관측** — 타임락 회수는 어드민 없이 일어난다. 어드민이 주소를 계속
감시해야 하나, 아니면 종결로 안 두고 영구 `settling`으로 남기나?

**Q7. 부분 체결** — ✅ **지원 안 함으로 확정**(유저 확인 완료). 이 문서 전체가 그 전제다.

**Q8. 최소 거래 금액** — ✅ **보증금 하한에서 유도한다**(리뷰 R2-M2):

```
최소 amountSat = (4 × 종결 tx 수수료) / 0.03
```

**근거**: 하한이 비율(3%)을 이기는 구간에서는 실효 보증금이 3%를 넘는다. 그 지점을
최소 거래액으로 잡으면 **어떤 거래도 실효 보증금이 3%를 안 넘는다.**

2-of-3 script-path 종결 tx ≈ **170 vB**
(비증인 94 B + 증인 ≈300 wu: 서명 2×65 + 스크립트 ~71 + control block 98):

| feerate | 종결 수수료 | 보증금 하한 | **최소 거래액** |
|---|---|---|---|
| 2 sat/vB | 340 | 1,360 | **~45k sats** |
| 10 sat/vB | 1,700 | 6,800 | **~227k sats** |
| 50 sat/vB | 8,500 | 34,000 | **~1.13M sats** |

⚠️ **고수수료 장세에서 최소 거래액이 폭등한다.** 이게 온체인 트랙의 실질 한계다 —
수수료가 비쌀 땐 소액이 아예 불가능하고, 그건 **라이트닝 트랙이 할 일**이다.
UI에서 "지금은 최소 N sats" 를 실시간으로 보여준다.

> 리뷰어는 종결 tx를 250~400 vB로 봤는데 **170 vB가 맞다**(taproot script-path는
> 4-leaf 트리라 control block이 98 B). 결론과 공식은 그대로 유효하다.

## 리뷰 #1이 연 질문

**R-Q1. 온체인 보증금 %를 수치로** 🔴 [HIGH] — **v3.2에서 산정 방식을 확정했다**(§6.0):
`max(비율, 4 × 클레임 시점 feerate 기준 tx 수수료)`, 후원자 **3%** / 고객 **1%**
(잠기는 시간이 4배 다르다).
**남은 것**: ① 3%가 45분 변동폭 2σ를 실제로 덮는지 — 장세에 따라 몇 배로 뛴다
② 하한 계수 `4`가 맞는지(충당 50% × 고객 손실 2회분에서 유도했다)
③ 그 액수에서 오더북이 마르지 않는지 — **허들을 올리면 이 앱의 존재 이유와 싸운다**

**R-Q2. `funded → presigned` 마감** — ✅ **T0+15분으로 답함**(§6.2).
송금 마감도 T0 기준(T0+45분)이라 창이 안 쌓인다. **값 자체는 확인 필요.**

**R-Q3. `funding` 타임아웃** — ✅ **12시간으로 답함**(§6.2). **확인 필요.**

**R-Q4. 보증금이 의뢰 수명을 못 덮는 문제** — ✅ **온체인 의뢰 만료 상한
7일로 답함**(§2.2). 자르기·갱신 없이 무담보 구간을 없앤다.
(v3.1에서 3→7일로 재조정했는데 이 항목만 10일로 남아 있었다 — 리뷰 R2-L1.)
⚠️ 라이트닝 트랙의 같은 버그는 **별건**이다(§14 참조).

**Q9. 몰수 보증금 충당의 자동화** — ✅ **v1은 수동으로 답함**(§6.0). 몰수금 50%를
어드민이 분쟁 채팅으로 수동 송금한다. 자동화는 "인보이스 발행 대기" 상태를 FSM에
추가해야 해서 드문 경로에 과하다. **남은 것: 50%가 적정 기본값인지.**

**Q10. `bonded`·`funding` 마감을 더 줄일 수 있나** (v3에서 열림) — 최악 43시간 동안
후원자 보증금이 잠긴다. 6h/12h가 과한가? 컨펌 대기가 대부분이라 줄이기 어려울 수 있다.

**R2-Q5b. 분쟁 후 릴리스의 낡은 수수료** (리뷰 R4-L3) — `releaseFeeSat`은 T0 고정인데
분쟁이 길어지면 낡아 tx가 멤풀에서 썩는다. 재추정하려면 **사전서명을 다시 받아야** 한다
(금액이 바뀌므로). 그런데 §7.6이 밝혔듯 사전서명은 만료되지 않으므로 **새 서명은
후원자의 새 동의**다 — 그게 곧 새 가격 합의가 된다. 깔끔하지만 후원자가 거부하면
CPFP뿐이다. R2-Q5와 함께 닫는다.

> 리뷰 R4-L4(분쟁 중 리오그로 사전서명 무효화)는 §7.6 조치로 **자연히 사라진다** —
> 리오그는 UTXO를 바꿔 사전서명을 죽이는데, 그게 바로 우리가 원하는 집행 방향이다.
> 그 경우 `{A,C}`/`{A,S}`로만 종결한다.

**R2-Q5. 종결 tx 무한 정체 시 에스컬레이션** (리뷰 R2-L5, R-Q5와 병합) —
`settling`이 되돌아가지 않으므로(O-005) 멤풀 정체는 **재브로드캐스트 + 에스컬레이션**으로
푼다. 릴리스는 RBF 비활성이라 **CPFP만** 가능한데 **후원자가 안 하면 자기 손해**다.
환불·분쟁 tx는 RBF를 열어 어드민이 올릴 수 있게 할지가 남았다 — **재서명에 상대
서명이 또 필요하다**는 게 걸린다.

**R-Q5. `settling` 장기 정체** (플래너 추가) — 수수료 급등으로 종결 tx가 24시간
넘게 안 잡히면? CPFP 안내가 전부인가, 어드민이 RBF로 올려줄 수단이 필요한가.
릴리스는 RBF 비활성(§7 O)이라 **CPFP만 가능**하다.

## 리뷰 #1 — 비판적 검토 (2026-09-19)

### R1-0. 종합 결론

설계의 뼈대는 건전하다. 이 안의 좋은 결정들:

- **`funded` 앵커 가격 고정**(§2.4): 클레임 시점 고정은 고객에게도 공짜 옵션을 주므로
  (고객이 고정 가격 보고 6시간 펀딩 창 동안 도망갈 수 있음), `funded`에서 고정해
  **고객 옵션을 제거**한 건 옳다. 이 결정을 되돌리지 말 것.
- **`invoiced ↔ presigned` 대응 + 사전서명 게이트**(O-002/O-003): DESIGN-LATE-INVOICE의
  공격 분석을 그대로 이식 — 계좌가 나가기 전에 후원자가 먼저 커밋하게 한다. 맞다.
- **0-conf 신뢰 금지**(§7 D), **릴리스 RBF 비활성**(§7 O), **터미널 = 컨펌 txid 근거**
  (O-004), **`funding` 이후 `cancelled` 금지**(O-001), **`swept` 관측만**(O-006): 모두 옳다.
- **펀딩 뒤 펀딩 구조**(§2): taproot 주소가 세 키에 커밋하므로 후원자 먼저인 결정은
  암호학적으로 강제. 타당.

핵심 리스크는 한 곳에 모인다: **`funded`(가격 고정) → 원화 송금 사이 후원자가 쥐는
일방적 옵션.** 나머지는 그 주변의 시간 경계 누락과 보증금 처리 모호성이다.
어드민은 에스크로에 원금을 넣지 않으므로 **어드민이 "뜯기는" 경로는 사실상 없다** —
어드민의 노출은 키 유실·판정 같은 운영 리스크다.

아래는 우선순위별. **[HIGH]** 는 착수 전 닫아야 한다.

### R1-H1. `funded → presigned` 마감 없음 → 후원자 무기한 공짜 옵션 [HIGH]

#### 상황

가격은 `funded`(펀딩 컨펌)에서 고정된다. 그 순간부터 후원자가 원화를 보내기 전까지가
**후원자의 옵션 창**이다. 플랜의 시간 제한은 이렇게만 배치돼 있다:

```
funded → presigned : 마감 없음          ← 구멍
presigned → remitted : 30분             ← 여기만 30분
```

`funded`에서 `presigned`(사전서명 제출)로 넘어가는 데 마감이 없어, **후원자가 가격
고정된 뒤 시장을 무한정 지켜보며 유리하면 진행·불리하면 보증금만 버리고 이탈**할 수
있다. 고객 자금은 그동안 무기한 잠긴다.

전이표의 `funded → settling`("후원자 이탈")이 있지만, **"언제 이탈로 간주하나"의 시계가
정의돼 있지 않다.** §6.2 표에도 `funded→presigned` 마감 항목이 없다.

#### 왜 보증금만으로는 안 되나 (리뷰어·플래너 합의 내용)

"보증금 = 옵션 프리미엄"이라는 직감은 **맞다.** 보증금은 몰수라는 억제를 통해 스톨/이탈
사례를 정확히 처리하는 올바른 도구다. 그러나 보증금이 제 역할을 하려면 **옵션 창이
유한해야** 한다. "가격이 보증금 이상으로 급변하면 어쩔 수 없다"는 꼬리 리스크 논리는
**창이 유한할 때만** 성립한다 — 무한 창이면 보증금 %가 아무리 커도 언젠가 넘는다.

따라서 해소 조건은 둘이다:

1. **`funded → presigned`에 마감을 건다.** (예: `presigned`의 30분과 같은 값, 또는 그보다
   여유 있게) 넘으면 후원자 보증금 몰수로 `settling → refunded`.
2. **온체인 보증금 %를 수치로 명시하고, 그 유한 창 `[funded → 원화송금]`의 예상 변동폭보다
   크게** 잡는다. 라이트닝 트랙 기본값(0, 꺼짐)을 그대로 가져오면 치명적이다 — §2.2가
   "온체인은 보증금 켜는 게 전제"라고만 했지 %를 안 적었다. **이건 §12에 새 질문으로 열어야
   한다.**

#### 이게 악용으로 확대되는 경로

후원자가 보증금만큼만 걸고 **여러 오더를 동시에 클레임** → 각각 `funded`까지 오면
유리한 것만 체결, 불리한 건 몰수금으로 버림 = sybil 옵션 증폭. 창이 유한하고 %가
커버되면 평균적으로 손해라 억제되지만, 창이 무한하면 그 경계가 무너진다.

#### 조치

- §6.2에 `funded → presigned` 마감 추가
- §4.2 전이표 `funded`·`presigned` 행에 시계 명시 ("마감 초과 시 이탈로 간주")
- §12에 온체인 보증금 % + 그 창 산정 근거 추가
- 재발방지 테스트: 마감 초과 시 몰수·`refunded`·고객 자금 해제 확인

### R1-H2. `funded`에 리오그 복귀 전이 없음 (FSM 전이표 구멍) [HIGH]

`funded`의 전이 대상은 `['presigned', 'settling']`뿐. 펀딩 tx가 N컨펌으로 `funded`에
도달한 뒤 **체인 리오그로 N컨펌 아래로 내려가면**, 이를 되돌릴 전이가 없다. 오더가
`funded`에 붙어 가격은 (더는 확인되지 않은) 기반 위에 고정된 채 남는다.

공격표 E(T-105)는 "금액별 컨펌 수 차등"으로 완화만 하고, **상태 회복 경로 자체는 설계에
없다.** §4.3의 불변조건 중 어느 것도 "탈-확정"을 다루지 않는다.

- **조치**: `funded → funding`(또는 `bonded`) 복귀 전이 추가. 불변조건 신설:
  "가격은 **확정된 N컨펌 위에서만** 고정된다. 컨펌이 N 아래로 내려가면 가격·`funded`
  판정을 함께 폐기한다."

### R1-H3. 릴리스가 `remitted`만으로 자동 붙으면 후원자가 고객을 뜯는다 [HIGH]

`remitted`는 **후원자의 단독 주장**이다(원화 보냈다고). 만약 `remitted → settling →
released`가 자동으로 이어져 릴리스 tx가 브로드캐스트된다면, **후원자가 원화를 안 보내고
`remitted`만 발행해도 BTC를 받아가는** 후원자→고객 탈취 벡터가 된다.

라이트닝에서 이 역할은 `paid` 전이의 **고객 payment-confirm(수동 확인)** 이 한다. 온체인에는
그에 대응하는 **고객 수동 확인 게이트가 불변조건으로 명시돼 있지 않다.** `ONCHAIN_COSIGN`이
"고객 → 어드민: 최종 서명 + 브로드캐스트"로 서술돼 있지만, "릴리스가 `remitted` 수신에
자동 반응하면 안 된다"는 원칙이 못박혀 있지 않다.

- **조치**: 불변조건 신설 — **"릴리스(cosign)는 고객이 원화 수령을 확인한 뒤에만.
  `remitted` 이벤트 자체는 트리거가 아니다."** 실제로는 고객이 은행 입금을 확인하고 cosign
  버튼을 눌러야 한다. 재발방지 테스트: `remitted` 단독으로 릴리스가 발사되지 않음을 고정.

### R1-H4. 고객 LN 보증금이 장기 의뢰를 담보하지 못한다 (§2.2 전제의 부분 붕괴) [HIGH]

코드 확인([admin/src/escrow-window.ts](../admin/src/escrow-window.ts),
[admin/src/nostr/service.ts](../admin/src/nostr/service.ts) 보증금 CLTV 로직):

```
보증금 인보이스 수명 = min(orderExpiration, 24h)
보증금 CLTV = (수명 + 24h)/600 블록 ≈ 2일
```

고객이 보증금을 내도 그 BTC는 **약 2일 뒤 CLTV 타임아웃으로 자동 환불**된다. 그런데 플랜은
의뢰 만료를 최대 3개월로 허용한다 → **2일 뒤부터 오더는 보증금이 빠진 채 `listed`로 남는다.**
§2.2의 "온체인은 보증금 켜는 게 전제 / LN 보증금이 스팸 방어" 논리는 **의뢰 수명의 처음
2일만** 유효하다. 이후로는 보증금 없는 스팸 오더가 3개월 내내 오더북에 떠 있을 수 있다
(라이트닝 F6·F7과 같은 문제가, 보증금 ON이 전제인 온체인에서 더 심각).

- **조치 (택일)**: ① 온체인 의뢰 만료를 보증금 CLTV 상한 이하(예: ≤ 2일)로 제한, 또는
  ② 보증금을 **기간 갱신(주기 재결제)** 으로 바꾸고 미갱신 시 `listed → cancelled`.
- **§12에 새 질문으로 추가** — R1-H1의 보증금 %와 함께 닫아야 한다.

### R1-M1. `refunded`가 보증금 처리가 다른 사례를 합친다 [MEDIUM]

`refunded`는 "분쟁 아닌 사유(후원자 이탈, reserve 미달, 창 만료)"를 모두 담는데 **보증금
처리가 서로 다르다**:
- **reserve 미달**(고객 reserve 아래로 가격 고정): 후원자 과실 아님 → 후원자 보증금 **환불**
- **후원자 이탈 / 창 만료**: 후원자 과실 → 후원자 보증금 **몰수**(고객 2회 수수료 보상, §7 C)

플랜은 `refunded`/`customer_wins`를 "보증금 처리가 달라서" 분리한다고 하면서(§4.1), **`refunded`
내부의 이 둘을 settlement-kind나 별도 플래그로 구분하는 규정이 없다.** 전이만 보고 어드민이
보증금을 잘못 환불/몰수할 수 있다.

- **조치**: `settling`→`refunded`를 태울 때 사유(settlement-kind)에 따라 보증금 처리 로직을
  못박고, 재발방지 테스트로 각 사유별 환불/몰수 분기를 고정.

### R1-M2. 릴리스 수수료 부담 주체가 IDEA와 플랜에서 뒤집혀 있다 [MEDIUM]

- **IDEA §⑥**: "후원자가 받는 건 X−F다. 즉 **릴리스 수수료는 후원자 부담**"
- **플랜 §6.1**: "후원자는 받는 만큼만 낸다 → KRW는 **payoutSat 기준**" = KRW =
  (amountSat − releaseFeeSat) × spot

플랜의 식대로면 고객이 받는 KRW가 이미 릴리스 수수료만큼 차감돼 있어, **실제로는 고객이
수수료를 부담**한다(고객이 amountSat을 넣고 payoutSat치의 KRW만 받음). 두 문서가 정면으로
다르다. 이 플랜의 "0.5%→0 수수료" 판매 포지션과 "누가 불리한지"가 이 결정에 달려 있다.

- **조치**: 부담 주체를 결정하고 IDEA·플랜 문구를 한쪽으로 정리. 화면에 명시할 것
  (고객이 받는 KRW = (amountSat − fee) × spot임을).

### R1-M3. `funding` 상태에 타임아웃이 없다 [MEDIUM]

고객이 수수료를 너무 낮게 잡아 펀딩 tx를 멤풀에 쌓아두면 `funding`에 계속 머문다(멤풀에서
안 떨어지면 `funding → bonded`로도 안 감). `bonded`(6h)는 있는데 **`funding` 타임아웃이 없어**
후원자 보증금이 무기한 잠기고 오더가 붙는다. (R1-H1의 `funded→presigned` 무마감과 별개로,
더 앞 단계의 무마감.)

- **조치**: `funding`에 마감 + 멤풀 잔류 시 강제 취소/보증금 처리 규칙 추가.

---

### R1-M4. 환불/분쟁 tx의 고객 서명 수집 경로가 명시되지 않았다 [MEDIUM]

`ONCHAIN_COSIGN`은 릴리스(고객 최종서명+브로드캐스트) 지향으로 서술돼 있다. 그런데 reserve
미달/창 만료 환불(`settling → refunded`)과 고객승 분쟁(`customer_wins`)도 **{A,C}로 고객
서명이 필요**하다. 이때 고객 서명을 어디서 어떻게 모으는지(어떤 액션, 어떤 게이트)가 플랜에
없다.

- **조치**: `ONCHAIN_COSIGN`을 재사용한다면 환불/분쟁용 고객 서명 수집을 명시하고,
  `funded→presigned` 마감(R1-H1) 시 환불이 진행되려면 고객이 온라인이어야 한다는 점을 UX에 반영.

### R1-LOW. 관찰 사항

- **펀딩 출처 미검증**: 에스크로 주소는 공개라 누구나 보낼 수 있다. `funded` 판정은 "주소에
  정확히 1 UTXO·정확한 금액"만 본다. 제3자 자금도 `funded`로 취급되지만 제3자는 그 BTC를 못
  씀(2-of-3) → 자기해라 실질 공격은 아님. 다만 "고객이 직접 펀딩했는지"는 보장되지 않는다.
  낮은 심각도.
- **Q1 컨펌 수**: 공격표 E(T-105)가 지적하듯 1컨펌 리오그는 실재한다. 금액별 스케일링이
  §12 Q1에 남아 있는 건 맞지만, **non-kyc 대금에 컨펌 수가 안 맞으면 후원자 원화만 날아가므로
  HIGH 급으로 봐야 한다.**
- **Q3 창 만료 직전 송금 경합**: `presigned` 30분 경과로 자동 환불(`settling→refunded`)이
  발사되는 것과, 후원자가 29:59에 보낸 `remitted` 이벤트의 처리 순서 경합이 있다. 은행 입금
  시각 vs 버튼 시각 기준이 정해지기 전까지 실제 손실로 이어질 수 있다. 라이트닝 F5와 같은 성격.
- **어드민 장기 다운**: 타임락 리프({C} 단독)는 어드민이 4주+ 다운이면 진행 중/원화 지급 후
  오더도 고객이 일방 회수할 수 있다. 의도된 최후수단이지만, **후원자 보호가 전적으로
  "어드민이 4주 안에 돌아온다"에 걸려 있다.** Q2의 송금 차단 임계가 사실상 유일한 방어이므로
  분쟁 최장 소요보다 여유 있게 잡아야 한다. **Q2는 미정으로 두면 안 되는 수준.**
- **온체인 트랙도 결국 LN 인프라에 의존**: 보증금이 LN 홀드 인보이스라 "happy path 어드민
  무개입·인프라 비용 0" 서사는 부분적으로만 참 — 보증금 발행/환불/몰수는 어드민 LN 노드가
  항상 필요.

### R1-1. §12에 추가할 리뷰 질문 (플래너가 닫을 것)

기존 Q1~Q8에 더해:

- **R-Q1**: 온체인 보증금 %(고객/후원자 각각)를 **수치로** 몇으로 하나. 옵션 창
  `[funded → 원화송금]`의 예상 변동폭과의 관계를 명시하라. (라이트닝 기본값 0을 그대로 쓰면
  안 됨 — R1-H1)
- **R-Q2**: `funded → presigned` 마감을 몇으로 두나. `presigned`의 30분과의 관계. (R1-H1)
- **R-Q3**: `funding` 타임아웃을 몇으로 두나. (R1-M3)
- **R-Q4**: 고객 보증금이 의뢰 수명을 담보하지 못하는 문제 — 의뢰 만료를 CLTV 상한 이하로
  제한할지, 보증금 갱신으로 갈지. (R1-H4)

### R1-2. 플래너가 받아야 할 최소 변경 묶음

1. R1-H1 해소: `funded→presigned` 마감 + 온체인 보증금 % 수치 명시 (§6.2, §4.2, §12)
2. R1-H2 해소: `funded` 리오그 복귀 전이 + 탈-확정 불변조건 (§4.2)
3. R1-H3 해소: 릴리스 = 고객 수동 확인 게이트 불변조건 (§4.3)
4. R1-H4 해소: 의뢰 만료 상한 또는 보증금 갱신 (§6.2)
5. R1-M1 해소: `refunded` 사유별 보증금 처리 규정 (§4.2/§9)
6. R1-M2 해소: 릴리스 수수료 부담 주체 결정 (IDEA·플랜 정리)
7. R1-M3 해소: `funding` 타임아웃 (§6.2)

## 플래너 답변 #2 (2026-09-20) — 플랜 v3

리뷰가 아니라 **유저 질문에서 나왔다**: "정상 경로를 따라가며 언제 누가 얼마를
누구에게 내는지, 온체인 수수료는 전 경로에서 누가 부담하는지 짚어달라."

따라가 보니 **v2에 구멍이 6개 있었다.** 리뷰 #1이 못 본 것들이다.

### 🔴 P1. 수수료 확정 시점이 두 절에서 달랐다

- §2.4: "주소·금액·**수수료**가 이미 `bonded`에서 정해져 있어 앱이 자동 서명"
- §6.1: "`releaseFeeSat` — 릴리스 tx 수수료 — **`funded`에서 고정**"

**§6.1이 맞다.** 사전서명은 펀딩 txid에 커밋하므로 펀딩 **이후**에만 가능하고,
수수료도 그때 정해진다. §2.4를 고쳤다.

### 🔴 P2. `refund:customer-timeout`은 존재할 수 없는 조합이었다

§4.1 표에 넣어놨는데, 고객이 펀딩을 안 하는 건 `bonded` 단계라 **온체인 자금이
없다.** 전이표는 `bonded → cancelled`(tx 없음)이지 `settling → refunded`가 아니다.
**내가 리뷰 R1-M1을 반영하면서 전이표를 안 보고 표를 채웠다.** 지웠다.

### 🔴 P3. "보증금이 고객 수수료를 보상한다"는 메커니즘이 없었다

§7 C가 "후원자 보증금이 고객의 2회 수수료를 **덮는다**"고 적었는데,
**몰수 = 어드민이 settle = 어드민이 갖는다.** 고객에게 갈 배선이 없다.

**v1 결정: 보상하지 않는다.** 보상하려면 "고객이 인보이스를 낼 때까지 대기"라는
상태가 새로 필요하고, 안 내면 결국 어드민에게 남아 같은 곳이다. 대신 §7 C의
**"보상" 문구를 지우고** 보증금 하한의 근거를 "후원자가 버리는 게 손해가 되게
한다"로 바꿨다. 보상 배선은 **Q9**로 열었다.

### 🔴 P4. 환불·분쟁 tx 수수료 부담자가 아예 없었다

`releaseFeeSat`만 정의돼 있고 환불·분쟁 tx 수수료는 문서에 없었다.
`settleFeeSat`을 §6.1에 추가하고 **종결 시점에 새로 추정**하게 했다.

그리고 **구조적 사실을 §6.0에 명시**했다: 종결 tx의 입력은 에스크로 UTXO 하나뿐이라
**수수료는 받는 쪽 출력에서 깎인다.** 어드민이 자기 UTXO를 입력으로 얹지 않는 한
"과실 있는 쪽이 문다"를 만들 수 없고, v1은 그걸 안 넣는다.

⚠️ 그 결과 **`refund:sponsor-timeout`에서 후원자가 버렸는데 고객이 수수료 2회를
문다.** 불편하지만 구조적이고, P3에서 보상을 안 하기로 했으니 **정직하게 적어뒀다.**

### 🟡 P5. 펀딩 tx 수수료가 회계에 없었다

버그는 아니지만 표에 안 잡혀 있었다. **고객 지갑이 정하고 우리는 관여하지 않는다**를
`fundingFeeSat`으로 명시했다.

### 🟡 P6. CPFP 추가 수수료는 후원자 부담인데 "릴리스 수수료는 고객 부담"과 나란히 있었다

모순은 아니다(기본 수수료는 고객, 빨리 받고 싶어 더 내는 건 후원자). §6.0 표에서
갈라 적었다.

### 관찰 — 최악 43시간, 가격은 클레임 18시간 뒤

```
claimed 30분 + bonded 6h + funding 12h + (T0+45분) + settling 24h ≈ 43시간
```

후원자 보증금이 그동안 잠긴다. 그리고 **가격은 클레임 최대 18시간 뒤**에 정해져
후원자는 가격을 모르는 채 커밋한다.

시세 환전이 목적이면 레벨엔 무관심하므로 불리하지 않다 — 그게 §2.4가 성립하는
이유다(고정된 가격이 없으면 차익거래 대상도 없다). 다만 **유동성이 묶이는 비용은

### 🔴 수수료 부담자를 잘못 정했다 — **후원자로 되돌린다**

유저 지적: *"거래가 성사돼서 후원자에게 가는 경우는 에스크로 UTXO를 소모해서
후원자 주소로 보내는 것이고 수수료도 그 UTXO에서 나가니, 의미상 후원자가 지불하는
방식일 수밖에 없지 않나?"*

**메커니즘 관찰은 맞지만 그것만으로는 부담자가 안 정해진다.** 수수료는 어느 안에서든
UTXO에서 나간다. **갈리는 건 KRW를 무엇에 곱하느냐**다:

```
A (v2):  priceKrw = (amountSat − fee) × 시세   → 후원자는 받는 만큼만 낸다 → 고객 부담
B (v3.1): priceKrw = amountSat × 시세          → 후원자가 전액을 사고 덜 받는다 → 후원자 부담
```

**B가 맞다.** 근거 셋:

1. **온체인 tx가 한 쪽에 하나씩** — 고객은 펀딩, 후원자는 릴리스. 서비스 수수료 0인
   트랙에서 이게 가장 설명하기 쉽고 공평하다
2. **직관적이다** — 고객 "`amountSat` 팔고 그만큼 원화 받았다" / 후원자
   "`amountSat` 사고 네트워크 수수료 떼고 받았다"(거래소 출금과 같은 모양)
3. **v3에서 내가 P6로 지적한 모순이 사라진다** — A에서는 기본 수수료는 고객,
   CPFP 추가분은 후원자로 갈려 있었다. B는 **릴리스 쪽 수수료를 후원자가 통째로**
   가지므로 부담자와 CPFP 결정권이 일치한다

### 그리고 이건 IDEA 문서가 원래 맞았던 것이다

IDEA §⑥이 "후원자가 받는 건 X − F, 즉 릴리스 수수료는 후원자 부담"이라고
적어뒀는데, **내가 리뷰 R1-M2에서 "그쪽이 틀렸다"며 반대로 확정하고 IDEA까지

## 플래너 답변 #4 (2026-09-20) — 플랜 v3.2

유저 지적: *"클레임 화면에 미리 고지할 필요는 없다. 보증금이라는 게 트롤하면
몰수한다는 의미고, 몰수됐다는 건 트롤을 했다는 말인데, 어드민이 그걸 어디 쓸지는
트롤러가 따질 게 아니다. 그거 고려하면 보증금을 좀 넉넉히 받는 게 좋겠다."*

### ✅ 고지 범위를 둘로 갈랐다

v3.1은 "몰수되면 **일부가 상대에게 갈 수 있습니다**"를 클레임 화면에 띄우자고 했다.
**뒷부분이 불필요하다.**

- **고지한다 — 몰수의 조건.** 어떤 마감을 어기면 잃는지, 그 마감이 언제인지.
  이건 설계의 공정성 자체다. 모르고 잃으면 안 된다
- **고지한다 — 환불 시 수수료 2회는 고객 부담이고 보상이 보장되지 않는다.**
`refund:sponsor-timeout`처럼 후원자 과실이어도 고객이 문다(§6.0 수수료 표).
충당은 재량이므로 **"보상받는다"가 아니라 "보장되지 않는다"** 로 적는다 (리뷰 R2-M3).

**고지하지 않는다 — 몰수금의 행방.** 몰수당한 쪽이 따질 자리가 아니다

**그리고 피해자에게도 약속하지 않는다**(유저 지적에서 따라 나온다). 충당이 운영
재량이면 UI에 띄우는 순간 **권리가 된다.** 못 주는 사정이 생겼을 때 — 몰수가
없었거나 양쪽 과실이거나 — 그게 새 분쟁이 된다. **내부 운영 정책으로만 둔다.**

### ✅ "넉넉히"에 근거를 붙였다 — 덮어야 할 것에서 유도

방향은 맞다. **정상 경로에서 보증금은 공짜**니까 — cancel된 HTLC는 라우팅 수수료가
0이다. 성실한 사용자는 아무것도 안 낸다.

다만 "최대한 많이"는 아니라서, 덮어야 할 것 둘로 나눴다:

```
후원자 보증금 ≥ max( 45분 옵션 프리미엄(3%),  4 × 종결 tx 수수료 )
```

**하한을 절대 sats로 둔 게 핵심이다.** 비율만 두면 소액에서 억제력이 0이 된다 —
1만 sats의 3%는 300 sats로 tx 수수료 한 번도 안 된다. 그리고 **상수로 박으면 안 된다**:
1 sat/vB와 50 sat/vB가 100배 차이라 **클레임 시점 feerate로 계산**해야 한다.

계수 `4`의 유도: 고객 손실이 tx 수수료 **2회**분, 충당이 몰수금의 **50%** 이므로
`2 ÷ 0.5 = 4`.

### 🔴 그러다 발견 — 고객과 후원자 보증금을 같은 크기로 두면 안 된다

| | 잠기는 구간 | 최장 |
|---|---|---|
| 고객 | `listed` → 종결 | **의뢰 만료(7일) + 거래 43시간** |
| 후원자 | `bonded` → 종결 | **약 43시간** |

**고객 보증금이 4배 가까이 오래 잠긴다.** 그런데 역할은 더 가볍다 — 등록 시점
스팸 차단이고 그 일은 등록하는 순간 끝난다. 후원자 보증금은 반대로 **짧게 잠기고
할 일이 많다**(옵션 프리미엄 + 충당 재원).

→ 고객 **1%**, 후원자 **3%**. v3의 1%/2%를 이 근거로 다시 잡았다.

### ⚠️ 올릴 때의 제동장치를 같이 적었다

IDEA 문서가 이 앱을 만드는 이유로 든 게 *"운영자가 허들을 올린다 → 신규 배척 →
유동성 더 마름"* 이었다. **보증금은 허들이다.**

"공짜니까 넉넉히"가 맞지만, 공짜인 건 **성실한 사용자에게만**이고 **진입 장벽은
성실한 사용자에게도 걸린다**(채널 용량·유동성 잠금). 덮어야 할 것을 덮는 선에서
멈춰야지 많을수록 좋은 게 아니다. R-Q1에 이 항목을 넣었다.

### R2-H1. `remitted`에 마감이 없다 → 원화 받은 고객이 타임락으로 전액 탈취 [HIGH]

#### 상황

§6.2 시간표는 비터미널 상태를 전부 나열한다고 했다(O-009). 그런데 **`remitted`가 빠져
있다.** 리스트는 `listed / claimed / bonded / funding / funded / presigned / settling`뿐.

`remitted`(후원자 원화 송금 주장)의 전이 대상은 `['settling']` 하나뿐이다. 릴리스로 가려면
**고객이 cosign해야 한다**(O-007, 수동 확인). 그런데 **고객이 cosign을 안 하면 `remitted`에
무기한 남는다.** 강제할 마감이 없다.

#### 왜 탈취로 이어지나

고객이 원화를 받고(remitted) 릴리스 서명을 거부하면:

- 후원자의 BTC는 에스크로에 잠긴 채다.
- 타임락 리프는 `{C}` 단독. **펀딩 컨펌 후 4주가 지나면 고객이 혼자 회수**한다.
- 고객은 원화(KRW)를 이미 받았고, 4주 후 BTC까지 회수 → **둘 다 갖는다.** 후원자는
  원화를 내고 BTC도 못 받는다.

후원자의 구제책은 "분쟁 제기 → 어드민이 sponsor_wins 판정 → {A,S}"뿐인데, 그건
**후원자가 스스로 알아서 제기 + 어드민이 4주 안에 판정**해야 하는 것에 전적으로 기대고,
설계상 강제 마감이 없다. Q2의 송금 차단 임계는 "**보낼 때** 타임락이 가깝다"를 막는
것이라, **일찍 보냈는데 고객이 끄는** 이 시나리오를 전혀 못 막는다.

> 라이트닝 트랙에 이 역할을 하는 게 없다면 아니다 — 거기는 CLTV 타임아웃이 자동 환불이라
> "고객이 settle 안 하면" 자동으로 고객한테도 후원자한테도 아닌 방향으로 풀리고, 어드민이
> 선제 settle 안전망(remitted)으로 후원자를 살린다. 온체인은 **타임락이 고객 편**이라
> 구조가 반대다. 라이트닝의 "안전망"에 대응하는 것을 온체인에는 안 만들었다.

#### 조치

- **`remitted`에 마감을 건다** (O-009 준수). 예: `remitted` 진입 후 24h 내에 고객이
  cosign하거나, 그렇지 않으면 **자동으로 분쟁/어드민 리뷰로 승격**. 어드민은 sponsor_wins
  ({A,S}, 고객 서명 불필요)로 후원자를 살린다.
- 이 마감이 **타임락(4주)보다 한참 안쪽**임을 불변조건으로 못박는다:
  "`remitted` 이후 고객 cosign 없이 타임락까지 끌리는 경로는 존재하지 않는다."
- 재발방지 테스트: 원화 수령 후 cosign 없이 타임락으로 회수되는 시나리오가 **FSM에서
  불가능**함을 고정.
- §6.2 표에 `remitted` 행 추가.

### R2-H2. O-001과 funding 타임아웃이 정면 충돌 (전이표에 발사 자리가 없다) [HIGH]

#### 상황

세 곳이 서로 다르게 말한다:

| 위치 | funding 12h 초과 시 |
|---|---|
| §4.2 전이표 | `funding → bonded` ("멤풀 이탈 **또는 12h 초과**") |
| §6.2 시간표 | `funding → cancelled`, 고객 보증금 몰수 |
| O-001 | "`funding` 이후에는 `cancelled`로 못 간다" |

§4.2에는 `funding → cancelled`가 아예 없고, O-001이 그것까지 막는다. 그런데 펀딩 tx가
12시간 멤풀에 쌓인 채(미컨펌·미이탈)면 `funded`로도 `bonded`로도 못 가고 `cancelled`로는
O-001이 막는다 → **`funding`에 갇힌다.** §6.2의 "12h → cancelled"가 발사될 자리가 없다.

#### 원인

O-001의 의도는 "**확정된** 자금(funded)을 tx 없이 취소하는 회계 구멍"을 막는 것인데,
`funding`(멤풀, 미확정)에는 **아직 에스크로에 확정된 자금이 없다** — 고객 지갑에 그대로
있다. 그래서 O-001의 범위가 `funding`까지 포함된 게 과하다.

#### 조치

- **O-001을 `funded`로 좁힌다**: "`funded` 이후에는 `cancelled`로 못 간다."
- §4.2 전이표에 **`funding → cancelled`** (12h 타임아웃, 고객 보증금 몰수)를 추가.
  자금이 확정되지 않았으니 취소가 안전하다.
- 재발방지 테스트: 12h 미컨펌 멤풀 체류 → `cancelled`가 실제로 도달하는지 고정.

### R2-H3. 원화 창(T0+45)이 고객의 계좌 공개에 종속 — 비대칭 몰수 [HIGH]

#### 상황

플로우: `funded`(T0) → 후원자 사전서명(≤T0+15) → `presigned` → **고객이 계좌정보
공개** → 후원자 원화 송금(≤T0+45) → `remitted`.

후원자의 송금 마감은 **T0+45 고정**인데, 막상 송금하려면 **고객의 계좌정보가 필요하다.**
계좌정보는 `presigned`에서 **고객이 발행**한다(O-003 게이트). 그 발행 시점이 T0에 묶여
있지 않다.

- 고객이 `presigned` 직후 바로 공개하면 후원자는 30분 남짓의 창을 쓴다.
- 고객이 늦게(또는 아예) 공개하면 후원자의 실질 창은 줄어들고, T0+45에 **몰수**된다.
  원화를 못 보낸 게 고객의 지연 탓인데 **후원자 보증금이 몰수**되는 비대칭이다.

> "고객은 T0에 방금 펀딩했으니 온라인일 것"이라는 암묵 전제가 있지만, "올려두고 잊기" +
> 푸시 알림 모델에선 펀딩을 자동으로(푸시에 반응해) 보내고 **바로 나갈 수 있다.** 그
> 시나리오를 막을 마감이 없다.

#### 조치

두 마감을 **서로 다른 기준점으로 분리**한다:

- **고객 측 마감**: `presigned` 진입 후 계좌정보를 **예: 5분 내** 공개. 안 하면 고객
  과실로 처리(보증금/타임아웃).
- **후원자 측 마감**: 원화 창을 **계좌정보가 공개된 시각부터** 30분(또는 45분)으로 앵커.
  고객이 일찍 공개하면 창이 T0+45와 같아지고, 늦게 공개해도 후원자 창이 줄지 않는다.

이렇게 해야 "후원자가 통제 못 하는 고객 지연 → 후원자 몰수"가 없어진다. §6.2의
`presigned` 행을 T0+45 → **계좌공개+30분**으로 고친다. (R2-L2와 함께 정리.)

### R2-H4. O-005 `settling → remitted`는 릴리스 전용인데, 환불·분쟁 settling에 쓸 수 없다 [MEDIUM-HIGH]

O-005: "`settling`에서 되돌아가는 유일한 길은 `remitted`다" (멤풀 이탈 시).

그런데 `refund:sponsor-timeout`은 `funded → settling`·`presigned → settling`에서 온다 —
**이 오더는 `remitted`를 거친 적이 없다.** 이 상태에서 환불 tx가 멤풀 이탈하면
`settling → remitted`로 가는데, 그건 의미상 말이 안 된다(후원자가 원화를 보낸 적도 없는데).

- `release` settling의 멤풀 이탈 → `remitted` (재협상/CPFP) ✓
- `refund:*` / `sponsor_win` / `customer_win` settling의 멤풀 이탈 → **갈 곳이 없다** ✗

#### 조치

O-005를 settlementKind별로 나눈다:

- 릴리스: `settling → remitted`
- 환불/분쟁: **`settling`에 머물며 재브로드캐스트**(또는 `settling → funded/presigned`로
  사유별 복귀). 멤풀 이탈은 종결을 포기한 게 아니라 재시도해야 하므로, 상태를 되돌리는
  대신 **같은 settlementKind로 재시도**한다.
- 재발방지 테스트: 각 종결 종류별 멤풀 이탈 → 유효한 다음 상태를 고정.

### R2-M1. `funded/presigned → funding` 복귀 시 시계가 초기화되는지 정의가 없다 [MEDIUM]

리오그 복귀(`funded → funding`)를 추가했는데, **재진입 시 T0를 새로 잡는지**가 명시돼
있지 않다.

- 새로 잡으면: 리오그마다 옵션 창이 리셋된다. 고객은 자기 펀딩 tx를 리오그시킬 수는
  없으므로(공격 비용이 큼) 큰 위험은 아니지만, 의미를 못박아야 한다.
- 재진입 시 **`presigned → funding`은 계좌정보가 이미 공개된 뒤**다(O-003 게이트가
  되돌릴 수 없다). 두 번째 `funded`에서 가격이 달라질 수 있고 후원자는 이미 계좌를 봤다 —
  공정성·프라이버시 측면에서 규정이 필요하다.

#### 조치

- **T0 = 각 `funded` 진입 시각으로 재정의**하고, 리오그 복귀 후 가격은 새 T0 시세로
  재고정한다는 걸 O-008에 명시.
- `presigned → funding` 재진입 시 계좌정보가 이미 공개된 상태임을 기록(무결성 X, 단 규정 필요).

### R2-M2. 보증금 하한 `4 × tx수수료`가 소액 거래를 8%+로 만든다 — 최소 거래액을 유도하라 [MEDIUM]

플래너가 스스로 열어둔 지점("1만 sats 거래에 2만 sats 보증금이 나오는 구간")이다.
실제로 나온다:

```
2-of-3 script-path 종결 tx ≈ 250~400 vB
@ 5 sat/vB ≈ 1,250~2,000 sats  →  4 × ≈ 5,000~8,000 sats
```

- 10만 sats 거래: max(3%, 8000) = 8000 → **8%**
- 26.7만 sats 아래에서는 3%가 아닌 **하한이 우세** → 그 아래는 실효 보증금이 3% 초과.

즉 **Q8(최소 거래액)이 없으면 소액 거래가 실효 보증금 8~25%+를 부담**해 마른다. Q8은
그냥 "릴리스+환불 2회분"으로 잡지 말고, **3%가 하한을 이기는 지점**에서 유도하라:

```
최소 amountSat ≈ (4 × 종결 tx 수수료) / 0.03
```

그 아래 거래는 아예 오더북에서 거부한다. 이렇게 하면 소액 거래의 실효 보증금이 3%를
넘지 않는다.

### R2-M3. `refund:sponsor-timeout` — 고객이 2회 수수료를 무는데 보상이 권리가 아니다 [MEDIUM]

§6.0이 정직하게 적어뒀다: 환불 경로는 고객이 2회 수수료를 문다. 후원자 과실(타임아웃)인데
**고객이** 운다. 몰수금 50% 수동 충당은 "권리가 아니라 운영 재량"이라고 명시했다 —
정직하지만, 그게 곧 **고객이 실제로는 2회분을 못 돌려받을 수 있다**는 뜻이다.

판단은 플래너가 이미 내렸다(자동화는 FSM 상태를 하나 더 만들어 과하다, 수동으로). 다만
**이 비대칭(후원자 과실인데 고객 부담)은 R2-H2/R2-H3과 얽혀** 있어, 몰수 로직이
settlementKind별로 정확히 켜져야 한다(R1-M1). 리뷰는 "상태를 늘리지 않는 수동 충당"에
동의하되, **고객 화면에 "이 비용은 보상이 보장되지 않는다"를 미리 알리는 것**만 추가를
권한다(충당을 약속하지 않는 선에서). 낮은-MEDIUM.

### 지적 — 고객이 침묵으로 원화와 BTC를 다 먹는다

```
계좌 전달 → 후원자 원화 송금 → remitted
→ 고객이 cosign도 이의제기도 안 한다
→ v3.2 FSM은 remitted → settling뿐이라 **아무 상태 변화 없이 정지**
→ 타임락 만기 → 고객 단독 회수. 원화 + BTC 양쪽
```

**타당하다.** 타임락은 "어드민이 증발해도 고객은 되찾는다"는 보험인데,
고객이 **가만히 있는 것만으로 그걸 유도**할 수 있었다.

### 먼저 시계를 바로잡았다 — 리뷰 #1의 Q2가 사실상 무의미했다

`OP_CSV`는 **상대** 타임락이라 **펀딩 컨펌**부터 센다. 그런데 마감 구조상 원화는
항상 `T0+45분`에 흐른다. 즉 **송금 시점에 타임락은 언제나 만기 전량**이다.

→ 리뷰 #1이 "미정으로 두면 안 되는 수준"이라 한 **Q2(후원자 송금 차단 임계)는
거의 발동하지 않는다.** 안전망으로만 남기고, Q2를 **"타임락을 얼마로 두나"** 로
바꿨다. 진짜 방어선은 **타임락 길이 > 어드민 판정 시간**이다.

### 조치 — 침묵이 아무것도 안 하게

**`disputed` 상태를 신설했다.** v3.2 FSM에는 분쟁 상태가 아예 없었다
(`remitted → settling`이 전부라 "이 주문은 분쟁 중"을 표현할 자리조차 없었다).

- **O-010**: `remitted` 6시간 마감 초과 → **`disputed` 강제 전이. 고객 동의를 묻지 않는다**
- **O-011**: `disputed`의 유일한 출구는 **어드민 판정**. 양쪽 다 단독으로 못 나간다
- **판정은 고객 없이 집행된다** — `sponsor_win`은 `{A,S}`라 어드민+후원자면 서명이
  된다. **이게 강제 분쟁이 실효를 갖는 이유다**
- 어드민 호출: `disputed` 즉시 Push + 대시보드가 **타임락 잔여 오름차순 정렬**
- 타임락 **4032 → 8064블록(8주)**

### 못 막는 경로는 정직하게 적었다

**어드민이 판정 전에 영구히 사라지면 T는 못 막는다.** 타임락 리프는 스크립트에
박혀 있어 앱 상태와 무관하게 체인이 고객 서명을 받아준다.

유저 판단이 맞다 — **어드민 급사에 대비하면서 동시에 어드민 급사 중 악의적 고객을
막을 수는 없다.** 타임락을 빼면 어드민 증발 시 자금이 영구 동결되고, 그건 비수탁이
아니다. 남는 건 확률을 줄이는 것뿐이다(긴 타임락 + 강한 호출 + 운영 이중화).

### 🔴 그런데 이 수정이 새 위험을 만든다 — 공격 U

강제 분쟁은 **어드민이 한쪽 증거만 들고 판정하는 상황**을 만든다. 고객이 침묵하니
후원자의 영수증만 있다. 그러면 **후원자가 영수증을 위조해 부재중인 honest 고객을
칠 수 있다**(기기 분실, 입원).

T를 막으면서 U를 여는 셈이라, **판정 원칙을 같이 박았다**:

- **침묵을 곧바로 패소로 보지 않는다**
- 후원자 증거는 **금액·수취인명·시각이 주문과 정합**해야 한다. 스크린샷 한 장은 부족
- 고객에게 반복 고지 + **판정 전 최소 대기**
- **증거가 부실하면 보류한다.** 보류는 타임락이 고객에게 유리하게 끝난다는 뜻이므로,
  기본값은 "확신이 없으면 후원자에게 주지 않는다"

> 라이트닝 F3의 "받지 못했으면 주지 않는다"와 같은 원칙이다.
> 여기서는 "받았다는 증거가 부실하면 주지 않는다"가 된다.

### R3-H1. `disputed`에 마감이 없다 — O-009를 스스로 예외 처리한 게, 느린-정직 고객을 처벌한다 [MEDIUM-HIGH]

#### 상황

§6.2 표: `disputed` = **"없음 — 어드민 판정까지 (타임락이 최종 백스톱)"**.

그런데 O-009는 "마감 없는 상태는 존재하지 않는다"다. `disputed`가 유일한 예외다. 타임락이
하드 백스톱이니 "무한 옵션"은 아니지만, **두 가지가 걸린다:**

**(a) 어드민이 8주 안에 판정해야 탈취가 안 막힌다.** `disputed`의 유일한 출구는 어드민
판정이고, 그 안에 내부 서브-마감이 없다. 대시보드 정렬+반복 알림은 운영 강제일 뿐 코드가
아니다. 어드민이 단 한 명이라 2주 휴가를 가면, 원화를 받고 `disputed`로 밀린 고객이
타임락(8주)에 스윕할 수 있다. 다만 이건 "어드민 급사는 못 막는다"를 받아들인 것과 연속선이다.

**(b) 느리지만 정직한 고객이 강제 분쟁을 통해 중재료+보증금을 잃는다.** 고객이 원화를 받고
(remitted) 24h를 조금 넘겨 돌아오면 → `disputed`. O-011 때문에 **둘이 다 합의해도 어드민을
거쳐야만** 나간다. 고객은 "돈 받았으니 cosign하고 끝내자"고 하려는데, 출구가 `sponsor_win`/
`customer_win`뿐이라 **고객 보증금 몰수 + 중재료**가 붙는다. 정직한데 늦은 것뿐인데.

#### 조치

1. **(b)를 위해**: `disputed`에서 **양쪽이 서명한 릴리스로 나가는 경로를 허용**한다
   (`disputed → settling`(release), 단 고객·후원자 **둘 다** cosign해야 함). 이건 O-011의
   "어느 한쪽이 단독으로 빠지는 것"을 막는 의도와 충돌하지 않는다 — 양쪽 동의면 안전하고,
   탈취(한쪽이 침묵해 타임락을 부름)도 되살아나지 않는다. 느린-정직 고객만 구제된다.
2. **(a)를 위해**: `disputed`에 **내부 서브-마감을 준다** — 예: 진입 후 7일 이내 판정
   없으면 어드민에게 반복 Push + 상위 고정, 14일이면 이중화 경로 호출. 하드 코드 마감은
   아니되 "판정 안 함"을 눈에 띄게 한다.
3. 아니면 더 단순하게: `remitted` 마감(24h)을 늘리거나, `disputed` 진입 전에 **고객에게
   "곧 분쟁으로 넘어갑니다" 1회 유예 경고**를 줘서 느린 고객이 스스로 cosign하게 한다.

### R3-H2. §7.4의 "tx 부재 확인"이 `funding → cancelled`에만 적용돼 있고, 이웃 전이엔 없다 [MEDIUM]

§7.4는 멤풀 tx가 몇 시간 뒤 컨펌돼 취소된 주소에 자금이 갇히는 걸 막기 위해
`funding → cancelled`에 "tx 부재 확인"을 붙였다. **그런데 같은 위험이 두 전이에 더 남아 있다:**

1. **`bonded → cancelled` (6h)**: 고객이 5h59m에 펀딩 tx를 브로드캐스트했는데, 6h 타이머가
   watcher가 그 tx를 보기 전에 발사되면 `bonded → cancelled`. 그 tx가 뒤늦게 컨펌되면
   **취소된 주소에 자금이 갇힌다.** §7.4의 부재 확인이 여기엔 없다.
2. **`funding → bonded` (멤풀 이탈)**: watcher가 "멤풀에서 떨어졌다"고 본 게 **거짓 부정**
   이면(멤풀 노드마다 뷰가 다르다 — 플래너가 리뷰 #3의 §7.4 질문으로 던진 바로 그 문제),
   `funding → bonded`로 보낸 뒤 tx가 컨펌되면 에스크로에 자금이 있다. 다시 `bonded → cancelled`로
   가면 동일한 오펀 위험.

#### 조치

§7.4의 원칙을 **"`funding`·`bonded`에서 취소로 가는 모든 전이"**에 일관 적용한다:
**취소는 "해당 에스크로 주소에 컨펌된 UTXO가 없음 + 펀딩 tx가 멤풀에 없음"을 확인한 뒤에만.**
한 곳에만 두면 다른 문에서 새는 식이다. (P2의 "조회 실패를 '없음'으로 뭉개지 말라"와 같은 원칙.)

### R3-H3. `funding`의 "12h → cancelled"가 §7.4와 모순 — 실질 무하드타임아웃이 됐다 [MEDIUM]

§6.2 표: `funding` = **"12시간 → cancelled, 고객 보증금 몰수"**.
전이표 주석: `funding → bonded` = "멤풀 이탈 **또는 12h 초과**".
§7.4: **12h가 지나도 멤풀에 있으면 `funding`에 머문다** (멤풀은 2주면 떨군다).

즉 §6.2/전이표의 "12h"와 §7.4가 **정면 충돌**한다. §7.4를 따르면 `funding`은 **하드 타임아웃이
없어** 멤풀이 tx를 떨굴 때까지(최장 ~2주) 머문다.

- §6.2·전이표의 "12h"를 **"12h부터 고객에게 RBF/CPFP 안내 + 후원자 지연 고지"** 로 고친다
  (하드 마감이 아니라 경고 시점).
- **`funding`이 오래 머물면 후원자 보증금의 LN CLTV가 먼저 만료**될 수 있다. 그 뒤에 펀딩이
  컨펌되면 `funded`로 가는데, **후원자 보증금이 이미 환불됐다** → 후원자의 T0+50 옵션이
  **무담보**다. 이 조합을 명시적으로 다뤄야 한다(예: 펀딩 컨펌 시점에 후원자 보증금이 살아
  있는지 확인, 아니면 재발행/중단).

### R3-M1. 중재료 부담자가 §4.1과 §6.1에서 반대다 — Q4가 여전히 미결 [MEDIUM]

- **§4.1 사유×보증금 표**: `sponsor_win` = "고객 몰수 **+ 중재료**", `customer_win` = "후원자
  몰수 **+ 중재료**" → **패소자가 중재료를 낸다**처럼 읽힌다.
- **§6.1**: `arbitrationFeeSat` = "분쟁 tx에서 **어드민 출력**으로 붙는 중재료". 분쟁 tx의 입력은
  에스크로 UTXO 하나뿐이므로 중재료는 **에스크로에서 차감**되고 → **승자의 출력이 줄어든다**
  (winner pays).

둘이 반대다. 게다가 패소자의 **LN 보증금**(몰수)은 별개 자금이라 on-chain 중재료를 "지불"할
수 없다. Q4(정액/정률, 패소자/분담)가 여전히 안 닫혀 있다.

- **조치**: Q4를 닫으면서 "중재료는 어느 자금(에스크로 vs 보증금)에서 어디로"를 명시한다.
  구조상 중재료는 에스크로에서 나가 승자가 부담하는 게 자연스러우니, §4.1 표의 "패소자 중재료"
  표현을 고쳐 일관되게 한다.

## 플래너 답변 #7 (2026-09-20) — 플랜 v5 · 리뷰 #3 전건 반영

R3는 HIGH 없이 MEDIUM~LOW인데, **R3-H1(b)가 설계 감각의 문제**라 제일 중요했다.

### ✅ R3-H1(b) — O-011을 내가 너무 세게 잡았다

24시간을 조금 넘겨 돌아온 **정직한 고객**이 "돈 받았으니 끝내자"고 해도, O-011이
어드민 판정만 허용하니 출구가 `sponsor_win`/`customer_win`뿐이라 **보증금 몰수 +
중재료**가 붙었다. 늦었을 뿐인데 도둑과 같은 처분이다.

**`disputed → settling`(release, `{C,S}` 양쪽 서명)을 열었다.**

O-011의 의도와 **충돌하지 않는다** — 막으려던 건 "한쪽이 단독으로 슬쩍 빠지는 것"이고
`{C,S}`는 **정의상 양쪽 합의**다. 한쪽이 침묵해 타임락을 부르는 탈취(공격 T)는 그대로 막힌다.
처리는 **정상 릴리스와 동일**: 양쪽 보증금 환불, 중재료 없음.

> 악용을 따져봤다. 후원자가 동의를 거부해 `sponsor_win`으로 몰아가도 **받는 BTC는 같고**
> 고객 몰수분은 어드민에게 간다 — 후원자가 얻는 게 없다. 고객이 일부러 늦춰 `disputed`를
> 거쳐 릴리스해도 얻는 게 없다. 양쪽 다 무이득이라 안전하다.

**그 앞에 유예 경고도 넣었다**(리뷰 제안 3): `remitted` 마감 2시간 전 "곧 분쟁으로
넘어갑니다" Push. 느린 고객 대부분이 여기서 스스로 끝낸다.

### ✅ R3-H1(a) + R3-H3 — 마감 없는 상태 둘을 **정직하게** 다뤘다 (§7.5 신설)

O-009가 "마감 없는 상태는 없다"였는데 `disputed`와 `funding`이 예외가 됐다.
**예외를 숨기는 대신 O-009를 고쳤다**: *어떤 상태에서도 한쪽이 무기한 유리한 옵션을
쥐지 못한다. 마감 없는 상태는 **머물러도 아무도 이득을 못 보는 상태**뿐이고 근거를 명시한다.*

**`disputed`에 하드 마감을 못 두는 이유**를 표로 박았다 — 자동 해소가 어느 방향이든
탈취다(시간 지나 `sponsor_win` = 공격 U / `customer_win` = 공격 T). **판정은 사람만
할 수 있다.** 대신 에스컬레이션 사다리(즉시 Push → 7일 최상단 고정 → 14일 이중화 호출).

**`funding`**: 머물러도 고객은 자기 돈이 묶여 손해, 후원자는 보증금이 LN 만료로 환불,
상한은 멤풀 2주 축출. §6.2의 "12h → cancelled"를 **"12h = 경고 시점"** 으로 고쳤다
(§7.4와 정면 충돌하던 것 — 리뷰 R3-H3 지적).

### ✅ R3-H3 후반 — 무담보 옵션 창 (O-015 신설)

못 본 것이다. 펀딩이 늦게 컨펌되는 사이 **후원자 보증금 CLTV가 먼저 만료**될 수 있고,
그 상태로 `funded`가 되면 T0+50분 옵션 창이 **무담보**다.

→ **O-015**: `funded` 진입 시 후원자 보증금 생존을 확인하고, **죽었으면 가격을 고정하지
않는다.** 재발행을 요구하거나 주문을 접는다.

### ✅ R3-H2 — 부재 확인을 전이 하나에만 둔 게 맞다 (O-014 신설)

§7.4의 원칙을 `funding → cancelled`에만 걸어놨는데, 같은 위험이 **`bonded → cancelled`**
(고객이 5h59m에 브로드캐스트 → 6h 타이머가 watcher보다 먼저 발사)와
**`funding → bonded`**(멤풀 뷰 차이로 거짓 부재 판정)에 그대로 남아 있었다.

→ **O-014**: **`bonded` 이후 `cancelled`로 가는 모든 전이**는 "주소에 컨펌 UTXO 없음 +
펀딩 tx 멤풀에 없음"을 확인해야 한다. 한 문만 잠그면 다른 문으로 샌다는 지적이 맞다.

> `listed`·`claimed`에서는 **주소가 아직 발행되지 않아**(`bonded`에서 발행) 위험이 없다.

### ⚖️ R3-M1 중재료 — 두 안 중 어느 쪽도 아니다

지적대로 §4.1("패소자가 낸다")과 §6.1("분쟁 tx의 어드민 출력" = 에스크로 차감 =
**승자가 낸다**)이 정반대였다.

**세 번째 답으로 갔다: 중재료는 패소자의 몰수 보증금에서 충당한다.**
분쟁 tx에 어드민 출력을 **달지 않는다.**

- **패소자가 실제로 부담**한다 — §4.1의 직관이 맞았고, 그걸 실현할 자금이 이미 있다
- 출력이 하나 줄어 **tx가 작아지고 수수료가 싸진다**
- **승자 금액이 안 깎인다** — 승자가 중재료를 무는 게 §6.1 구조의 문제였다
- 별도 자금 이동이 없다 — 어드민이 이미 settle한 돈이다

⚠️ 그래서 **분쟁에는 "몰수금 50% 피해자 충당"(§6.0)을 적용하지 않는다.** 그 정책은
어드민 노동이 없는 **타임아웃 경로**용이다. Q4를 이걸로 닫았다(정액/정률만 남았다).

### R4-H1. `presigned → disputed` + 분쟁 중 mutual-release = 후원자의 무한 옵션 (R1-H1 재발) [HIGH]

#### 상황

v5에서 두 가지가 동시에 추가됐다:

1. **`presigned → disputed`** (후원자가 "계좌정보 사용 불가"를 제기, §5.2b/전이표 주석)
2. **`disputed`에서 양쪽 동의 릴리스(`{C,S}`)로 나가는 길** (O-011 완화, R3-H1b)

전이표에 `presigned`에 `'disputed'`가 들어갔고, `disputed`에서 mutual-release가 가능하다.

#### 공격

후원자가 `presigned` 진입 직후 "계좌가 이상하다"고 분쟁을 건다:

```
presigned → disputed   (KRW 마감 시계가 멈춘다 — disputed는 마감이 없다, 최장 8주)
→ 후원자가 시장을 무한정 지켜본다
   유리하면: 원화를 고객에게 보낸다 (분쟁 중에도 계좌정보는 이미 있음)
             → 정직한 고객이 받고 확인 + cosign → mutual-release → BTC를 고정가로 받는다
   불리하면: 안 보내고 묵묵부답 → disputed → 어드민 판정 → 보증금(3%)만 잃는다
```

**후원자 비용은 고정(보증금 3%)인데, 옵션 창은 무한정(최장 8주)이다.** 45분 창은
3%가 덮지만, 8주 창의 유리한 변동은 3%를 훌쩍 넘는다 → **평균적으로 이득.** 이건 정확히
R1-H1이 막았던 그 구멍이다. `disputed`가 마감이 없어서(§7.5가 인정) 무한대가 된 것.

- mutual-release를 **"양쪽 합의"라고 하지만**, `{C,S}`의 후원자 서명은 `presigned`에서
  **이미 냈던 사전서명**이라 사실상 **고객이 cosign만 하면 완성**된다. 후원자의 재동의가
  필요 없다. 그래서 후원자가 "분쟁 중에" 고객에게 원화만 보내면 고객이 알아서 완성해준다.
- 고객이 협조하는 이유: **정직한 고객은 원화를 원한다.** 후원자가 보내면 확인하고 cosign한다.
  공격이 "정직한 고객"을 상대로도 성립한다는 게 문제다.

#### 왜 R3-L5를 되돌려야 하나

R3-L5 원래 지적은 "`ONCHAIN_DISPUTE` 유효 상태가 명시 안 됐고, 후원자가 나쁜 계좌를 만났을
구제가 없다"는 **낮은 위험**이었다. 계좌정보는 고객 키로 서명되고 고객은 원화를 원하므로
나쁜 계좌를 줄 인센티브가 없다. 그 낮은 위험을 막자고 `presigned` 분쟁을 열었는데, 그게
HIGH급 무한 옵션을 열었다. **순손해다.**

#### 조치 (택일, 둘 다 free option을 닫는다)

1. **`presigned → disputed`를 제거** — 분쟁은 `remitted`에서만. 나쁜 계좌는
   `refund:sponsor-timeout`(보증금 몰수) 또는 서포트 채팅으로 처리한다. (R3-L5의 낮은 위험을
   감수. 가장 단순하고 안전.)
2. 또는 **presigned 분쟁을 fold-only로** — 그 분쟁은 `refund`(고객 회수)로만 끝나고,
   **릴리스 출구(상호·어드민 판정 모두)를 금지**한다. 계좌가 정말 나쁘면 후원자 보증금 환불,
   악의면 몰수. 어드민이 판정하되 "릴리스로 진행"은 불가 → 옵션 창이 생기지 않는다.

어느 쪽이든, **mutual-release는 `remitted` 유래 분쟁에만 허용**해야 한다(거기는 원화가 이미
흘렀으니 옵션이 남아있지 않다). `presigned` 유래 분쟁에는 릴리스 출구가 있으면 안 된다.

## 플래너 답변 #8 (2026-09-20) — 플랜 v6 · 리뷰 #4 전건 반영

**R4-H1은 진짜 HIGH이고 지적이 맞다.** 내가 v5에서 R3을 닫으며 직접 열었다.
다만 **리뷰어의 조치안 둘 다로는 안 닫힌다** — 같은 공격이 다른 문으로 들어온다.

### 🔴 R4-H1 — 받되, 조치안은 불충분하다

#### 공격 확인

`presigned → disputed` + 분쟁 중 릴리스가 겹치면서, 후원자가 **비용 3% 고정 / 창 8주**의
옵션을 쥐었다. R1-H1이 막았던 그 구멍이 맞다.

#### 리뷰어 전제의 오류

리뷰는 *"mutual-release는 `remitted` 유래 분쟁에만 — 거기는 원화가 이미 흘렀으니 옵션이
없다"* 고 했다. **`remitted`는 후원자의 미검증 주장이다.**

```
presigned → 후원자가 원화를 안 보내고 remit-request만 발행 → remitted
→ 고객이 은행 확인, 없음 → cosign 안 함 → 24h 후 자동 disputed (O-010)
→ 똑같은 무한 창
```

**입구를 막는 걸로는 못 닫는다.** 후원자는 언제든 거짓 `remitted`로 들어올 수 있다.

#### 근본 원인 — 비트코인에서 서명은 만료되지 않는다

리뷰 R4-L2가 정확히 짚었다: `{C,S}`의 후원자 서명은 **`presigned`에서 이미 나왔고**,
"양쪽 동의 릴리스"의 실체는 **고객이 사전서명을 완성하는 것**이다.

그리고 **FSM 규칙으로는 못 막는다** — 양쪽이 서명을 들고 있으면 앱 없이 직접
브로드캐스트할 수 있다. nLockTime은 실행을 늦출 뿐 무효화하지 못한다.

#### 막는 법은 하나 — **입력을 써버린다**

사전서명은 특정 UTXO를 소모한다. **그 UTXO가 다른 tx로 쓰이면 즉시 무효다.**

→ 후원자에게 불리한 종결(`refund:*`, `customer_win`)은 전부 `{A,C}`로 에스크로를
소모한다. **그게 옵션을 죽이는 실제 집행이고, FSM이 아니라 체인이 집행한다.**
**옵션 창의 실제 길이 = 그 종결 tx가 컨펌되기까지**이지 8주가 아니다.

#### 조치 셋 (§7.6 신설)

**① `presigned → disputed` 제거. 계좌 이의는 시계를 멈추지 않는다.**
"계좌 사용 불가"는 **상태 전이가 아니라 주문에 붙는 증거**다. 원화 마감은 그대로 흐르고,
마감이 차면 에스크로가 소모되며 사전서명이 죽는다. 그 증거는 **보증금 몰수 여부만** 가른다.
→ R3-L5가 지키려던 것(나쁜 계좌 만난 후원자 구제)은 유지된다. 정당하면 보증금을 돌려받는다.

**② `remitted` 유래 분쟁은 빠르게 판정한다.** "원화 증거 없는 `remitted`"는 거의 기계적
판정이다 → `customer_win` → `{A,C}` 소모 → 사전서명 사망. 거짓 발행한 후원자는 보증금도 잃는다.

**③ 고객 앱이 낡은 가격을 거부한다 (O-016 신설).** ①②를 해도 어드민이 느리면 창이 남고,
앱 규칙은 직접 브로드캐스트를 못 막는다. **마지막 방어선은 손해를 보는 당사자 자신**이다.
T0 가격 유효창을 넘긴 릴리스에는 cosign하지 않고, "지금 시세로 X원 손해"를 띄운 뒤
**명시적 우회만** 허용한다.

### R4-Q1~Q4 답변

**R4-Q1 (presigned 분쟁 제거 vs fold-only)** → **제거**. 단 리뷰가 말한 "mutual-release를
`remitted` 유래에만"은 **그것만으로 불충분**하므로 §7.6 ①②③을 함께 넣었다.
O-011에 "릴리스 출구는 `remitted` 유래에서만 앱이 돕는다"를 명시했다.

**R4-Q2 (§5.2b)** → **실제로 본문에 넣었다.** 지적대로 참조만 있고 섹션이 없었다
(답변 #7에서 "신설했다"고 적어놓고 안 넣었다). 내용은 R4-H1 조치에 맞춰 바꿨다 —
`presigned` 행이 "✅ 후원자만"에서 **"❌ 시계를 멈추지 않는다 / 증거 첨부로만"** 이 됐다.

**R4-Q3 (O-015 fold 단일화)** → **fold로 통일.** `funded → settling`(`refund:bond-expired`).
"재발행"은 `funded → bonded` 전이를 새로 만들어야 하고 그 사이 가격이 또 흔들린다.
보증금은 이미 LN 만료로 환불됐고 **고객이 펀딩 수수료를 잃는다** — 누구 과실도 아니라
몰수도 없다(`refund:reserve`와 같은 성격). `settlementKind` 표에 행을 추가했다.

**R4-Q4 (중재료 정액 하한)** → `중재료 = min(몰수 보증금, max(정액 하한, 거래액 1%))`.
정액 하한이 필요한 이유는 **분쟁 1건의 어드민 노동이 거래 크기와 무관**해서다.
feerate와 무관한 고정 sats(노동 단가지 수수료가 아니다). **상한은 몰수 보증금** —
더 꺼낼 자금이 없다. 모자라면 어드민이 덜 받고 끝내고, 그건 R-Q1의 비율을 올릴 근거다.
**중재료 때문에 승자를 깎지는 않는다.**

### ✅ R4-L1·L2 / L3·L4 병합

- **L1**: §6.0 정상경로 표의 후원자 보증금 `2%` → **`3%`**. v3 값이 남아 있었다
- **L2**: mutual-release의 실체가 "고객이 사전서명 완성"임을 §7.6에 명시했다.
  **O-007은 분쟁 중에도 유지**되고, **O-016**이 거기에 "가격도 확인한다"를 더한다
- **L3**: 분쟁 후 릴리스의 낡은 수수료 → **R2-Q5b**로 열었다. 재추정하려면 금액이
  바뀌어 **사전서명을 새로 받아야** 하는데, §7.6대로 그건 **새 가격 합의**와 같다
- **L4**: 분쟁 중 리오그로 사전서명 무효화 → §7.6 조치로 **자연 소멸**한다.
  리오그는 UTXO를 바꿔 사전서명을 죽이는데 **그게 우리가 원하는 집행 방향**이다
