# 온체인 트랙 signet 드릴 런북

> PLAN-ONCHAIN-TRACK §11 P6. **매번 헤매지 말 것.**
>
> **대상은 데몬이다**(PLAN-DAEMON P4, 2026-09-24). 코드로 붙일 수 있는 건 다 붙였다 — 데몬 전 배선을 도는
> 시나리오 테스트가 `daemon/src/__tests__/oc-e2e.test.ts`에 있다(정상·이탈·분쟁·미펀딩·구조·계좌 이의 +
> 리뷰 #8 회귀. 가짜 릴레이가 지난 만료를 거절하고, 가짜 체인이 esplora처럼 소모된 UTXO를 뺀다. 서명은 진짜).
> 여기 적는 건 **그 테스트가 대신해줄 수 없는 것**뿐이다:
>
> - 진짜 지갑이 만드는 펀딩 tx (금액·수수료·RBF 플래그를 우리가 안 정한다)
> - 진짜 멤풀과 컨펌 (우리 vsize 추정이 맞는지, 수수료가 실제로 먹히는지)
> - 브라우저 두 개가 **서로 다른 키로** 도는 상황 (키 파생·주소 검증의 실전)
> - NIP-46 번커 왕복이 들어간 서명 지연
> - **노드 정책** — 유닛 테스트가 만든 tx가 실제로 멤풀에 들어가는지
>
> ⚠️ **2026-09-24 현재 체인에서 확인된 건 ① 릴리스뿐이다.** ②③④는 노드에 한 번도
> 안 들어갔다. 그리고 리뷰 #8이 **서명 순서를 바꿨다**(어드민이 마지막) — ①도 다시 돈다.

## 0. 준비

| | |
|---|---|
| 네트워크 | **signet** — 공개 `mempool.space/signet`, 코인 무료, 리오그 실험 가능 |
| 지갑 | signet을 지원하는 것 아무거나 (Sparrow가 편하다 — PSBT·RBF·CPFP를 다 보여준다) |
| 코인 | signet faucet |
| LN | 보증금용. 온체인 보증금은 LN 토글과 **무관하게 늘** 요구된다(§2.2). ⚠️ 보증금 CLTV가 **≈1,370블록**이라 결제하는 지갑의 CLTV 한도가 그보다 낮으면 경로를 못 찾는다 — **실제로 쓸 지갑으로** 확인 |
| 환불 주소 | 고객이 의뢰 때 낸다. signet 주소 하나를 미리 준비 |
| 브라우저 | **2개 프로필** — 고객·후원자가 서로 다른 키여야 한다 |

⚠️ **먼저 확인** (데몬) — **signet 드릴 전용 데몬을 따로 띄운다.** 운영 데몬은 그대로 둔다(유저에게 안 보인다):

```bash
cd ~/my-server && mkdir -p lnpay-data-signet          # 컨테이너 uid 1000이 쓸 수 있게
docker compose build lnpay-daemon && docker compose --profile signet up -d lnpay-daemon-signet
docker compose logs -f lnpay-daemon-signet             # "릴레이 … mode: dev, onchain: signet"
# 끝나면: docker compose --profile signet stop lnpay-daemon-signet
```

- compose의 `lnpay-daemon-signet`은 운영 데몬을 `extends`로 물려받는다(같은 이미지·비밀·LND). 다른 건 셋뿐:
  `LNPAY_MODE=dev`(태그가 `-dev`로 갈린다), `LNPAY_ONCHAIN_NETWORK=signet`, 장부 `lnpay-data-signet/`.
  공개 mempool.space가 막히면 `.env`에 `LNPAY_SIGNET_API`.
- **장부 하나 = 모드 하나 · 네트워크 하나** — 데몬이 부팅 때 본다(`daemon/src/guards.ts`). 운영 장부를 dev 모드로
  띄우거나, 진행 중 온체인 오더가 있는 채로 네트워크를 바꾸거나 끄면 **일부러 안 뜬다**. 그래서 운영 데몬의
  네트워크를 드릴 때마다 바꾸는 방식은 쓰지 않는다(옛 프론트 어드민의 네트워크 토글은 이 문제로 "진행 중이면
  막는다"는 호출부 가드에 기대고 있었다).
- 유저 앱·어드민은 **dev 빌드**로 붙는다 — `pnpm dev:customer`(5173), `pnpm dev:admin`(5175). dev 빌드는
  `-dev` 태그라 signet 데몬만 보고, 운영 데몬(`preview:*`, 4173·4174)과 동시에 띄워도 서로 안 섞인다.
- 어드민 앱(dev 빌드) 데몬 탭 → 운영 설정에서 **"온체인 새 의뢰 받기"**를 켠다(기본 꺼짐, 데몬마다 따로다).
- 보증금은 같은 LND로 만든다 — **보증금은 진짜 sats**다(소액, 정상 종결이면 환불). signet인 건 온체인 코인뿐.
  ⚠️ 라이트닝 드릴 때처럼 **이 노드 밖의 지갑**으로 낸다(같은 LND 셀프 결제는 거부된다).
- 판정·계좌 이의·구조는 어드민 앱 온체인 상세의 버튼(운영자 명령)이다. 어드민 키는 데몬이 시드에서 파생한다 —
  어드민 앱에는 키가 없다.
- 키 백업·복원 화면은 **지금 없다**(2026-09-24 — 키 교체·파기는 두 트랙을 같이 놓고 나중에 기획). 드릴 중에
  브라우저 저장소를 지우지 않는다 — 에스크로 키가 그 nostr 키에서 파생된다.

## 1. 드릴 5종

각 드릴은 **새 주문**으로 시작한다. 중간 상태에서 이어 붙이려다 헤매는 게
제일 흔한 실수다.

### ① 정상 완료

```
고객: 온체인 탭 → 팔기 → 수량 + **환불 주소** 입력 → 등록
  ↓ 보증금 인보이스가 온다. 결제
후원자: 온체인 탭 → 사기 → 사줄게 → 받을 주소 + feerate
  ↓ 보증금 인보이스 결제 (결제가 먼저 확인된 쪽이 가져간다)
고객: 에스크로 주소가 뜬다 — ✓ 배지를 확인하고 정확한 수량 송금
  ↓ N컨펌 대기 (금액별 1~3)
후원자: 앱이 자동으로 사전서명 (15분 안에 앱이 깨어 있어야 한다)
고객: 계좌 정보 전달 (15분)
후원자: 펀딩 체인 확인 ✓ · 타임락 잔여 확인 → 원화 송금 → 송금 완료
고객: 입금 확인 → 릴리스 서명
  ↓ 어드민이 사전서명을 옮겨 심어 완성 → outbox 기록 → settling → 브로드캐스트 → 컨펌
```

**볼 것**
- 에스크로 주소가 양쪽 화면에서 **같게** 뜨는가 (독립 파생이라 다르면 버그다)
- `releaseFeeSat`이 후원자가 낸 feerate에서 나온 값인가 — 다르면 후원자 앱이
  사전서명을 **거부**해야 정상이다
- 실제 종결 tx의 vsize가 **169 vB**인가 (P2TR 출력 기준). 다르면 수수료 추정이
  틀린 것이고, 그건 곧 멤풀 정체다
- 양쪽 보증금이 **환불**되는가 (몰수 0)
- 후원자 송금 버튼이 **펀딩 체인 확인**(outpoint · 주소 · 금액) 전에는 안 열리는가
- 제3자 키로 가짜 `account-info`를 쏴 보면 **후원자 화면에 안 뜨는가** (리뷰 #8 C1 — 브라우저 하나 더)

### ② 후원자 이탈

①에서 사전서명 단계에 **후원자 앱을 닫고** 15분을 넘긴다.

**볼 것**
- `refunding`(환불 진행 배지)으로 가고 고객에게 **서명 없는** 서명 요청이 오는가
- 후원자 보증금이 **그 순간**(고객 서명 전) 몰수되는가 — 결정 시점 집행
- 후원자 앱을 **다시 켜면** 사전서명이 거절되고 이유가 뜨는가 (리뷰 #8 R1 — 여기가
  원화와 BTC를 둘 다 가져가던 구멍이다)
- 서명 화면에 받는 곳이 **내가 낸 환불 주소**로 뜨는가. 다른 기기에서 열면 주소를
  다시 입력하라는 칸이 뜨는가
- 고객 서명 → **어드민 서명** → 브로드캐스트 → `refunded`. 출력이 환불 주소인가
- 어드민 화면에 "몰수금 처리 필요 → 50% 피해자 충당(재량)"이 뜨는가

### ③ 분쟁 (양방향)

①에서 송금 완료까지 간 뒤 고객이 **아무것도 안 한다.** 24시간을 넘긴다.

⚠️ 24시간을 실제로 기다리기 싫으면 브라우저 시계를 돌리지 말고 **주문을 하나
더 만들어** 어드민 화면에서 분쟁 판정 버튼을 직접 누른다. 시계를 돌리면
LN 인보이스 만료와 어긋나 엉뚱한 곳이 깨진다.

**볼 것**
- 고객 동의 없이 `disputed`로 넘어가는가 (O-010)
- 운영자 pubkey로 **NIP-17 DM**이 오는가 (어드민 설정에 운영자 pubkey)
- 분쟁 채팅이 **양쪽에서** 보이는가. 계좌 이의라면 후원자가 공개한 계좌에 커밋먼트 배지가 뜨는가
- 판정 화면에 §7.7 지침과 **양쪽 보증금 만료 추정**이 보이는가 — 기본 승자가 없다.
  판정 버튼이 확인창을 거치는가
- 후원자승: `{A,S}` — 고객 없이, **후원자 서명 → 어드민 마지막 서명**으로 집행되는가
- 고객승: `{A,C}` — **고객 서명이 필요**한가
- 패소자 보증금이 **판정 순간** 몰수되고 중재료 안내가 뜨는가

### ④ 타임락 회수

⚠️ **8064블록(≈8주)이라 signet에서도 못 기다린다.** 드릴에서는 타임락을
짧게(예: 10블록) 준 주문을 따로 만들어 스크립트 경로만 확인한다.

```
어드민 설정에서 timelockBlocks를 낮춰 주문 생성
  → 펀딩 → 어드민을 끈다 → 블록이 쌓이길 기다린다
  → 고객 앱의 회수 경로로 단독 서명 → 브로드캐스트
```

**볼 것**
- `nSequence`가 **블록 수 그 자체**로 들어가는가 (RBF 비활성이 아니다)
- tx version이 2인가 (BIP-68은 v2 이상에서만 동작한다)
- 증인이 `[서명, 스크립트, control block]`으로 **직접 조립**되는가
  (라이브러리 `finalize()`는 이 리프를 모른다 — `Unknown tapLeafScript`로 거부한다)
- 실제 vsize가 **146 vB**인가
- 고객 앱 **"비상 회수 · 환불금 꺼내기"**(`RecoveryPanel`)에서 남은 블록이 맞게 뜨고,
  차면 단독 회수 버튼이 열리는가
- 어드민이 다시 켜졌을 때 `swept`으로 **관측**하는가 (O-006 — 리뷰 #8 전에는 리오그로 읽었다)

### ⑤ 구조 (약정 밖 자금) — 리뷰 #8 신설

④처럼 기다릴 필요가 없다. 주문을 만들고 **펀딩 마감을 넘겨 취소시킨 뒤** 그 주소로
보낸다(또는 `bonded`에서 금액을 1 sat 다르게 보낸다).

**볼 것**
- 어드민 화면에 **구조 경보**가 뜨는가 (터미널 뒤 60일 · 10분 간격 감시)
- 구조 버튼 → 고객에게 `rescue` 서명 요청 → 고객 서명 → 어드민 마지막 서명 → 고객 환불 주소
- 진행 중인 거래의 에스크로는 구조 대상이 **아닌가**

## 2. 함정 (미리 적어둔다)

| 증상 | 원인 |
|---|---|
| 에스크로 주소가 양쪽에서 다르다 | 세 x-only 키 중 하나가 다르다. **오더 이벤트의 키가 내 파생 키와 같은지** 먼저 본다 |
| 사전서명이 거부된다 | `releaseFeeSat` ≠ 내 feerate 기준 계산값. 어드민이 다른 feerate로 고정했다 |
| 종결 tx가 안 잡힌다 | 후원자가 낮은 feerate를 냈다. **RBF가 꺼져 있으므로 CPFP뿐이다** |
| 펀딩이 컨펌됐는데 `funded`가 안 된다 | 금액이 **정확히** 일치하지 않거나 UTXO가 2개다 → 어드민 화면에 `anomaly` |
| 취소됐는데 주소에 돈이 들어왔다 | 마감 직후 컨펌. **구조 경보 → 구조**(⑤, §4.1c) |
| 보증금 인보이스가 안 만들어진다 | 의뢰 만료가 7일을 넘었거나 CLTV가 채널 상한 초과 |
| 보증금 인보이스 결제 경로를 못 찾는다 | 결제 지갑의 CLTV 한도 < ≈1,370블록 |
| 환불 서명이 "환불 주소가 아니다"로 막힌다 | 이 기기가 환불 주소를 모르거나 **다른 주소를 입력**했다. 의뢰 때 낸 주소를 입력한다 |
| 사전서명이 "마감이 지났다"로 안 나간다 | 정상이다 — 이미 환불이 결정됐다(O-017) |
| 상태 발행이 계속 실패한다 | 릴레이가 이벤트를 거절한다. 진행 중 이벤트의 `expiration`이 의뢰 만료로 나갔는지 확인(리뷰 #8에서 고쳤다) |
