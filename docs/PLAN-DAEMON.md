# §1. 왜 — 프론트 어드민이 막힌 지점

다기기 실험(PLAN-ONCHAIN-TRACK §9.1)을 끝까지 따라가 보니 구멍이 구조에서 나왔다
(2026-09-24 점검, 코드로 확인):

1. **집행 소유권이 라이트닝에 없다.** 요청 처리와 자동 승인이 열린 모든 탭에서 돈다. 두 기기가 같은
   클레임을 동시에 승인하면 에스크로 홀드 인보이스가 둘 생기고, 기기마다 자기 프리이미지만 쥔다 →
   "틀린 쪽" 기기만 켜져 있으면 입금 확인 뒤 settle 실패 → 후원자 손실.
2. **백업이 맵 통째 + 마지막 쓰기 승리 + 부팅 때만 병합.** 오래 켜둔 탭이 자기 맵을 올리는 순간 다른
   기기가 만든 프리이미지가 릴레이에서 지워지고(온체인 보증금 것까지), 지운 보증금 대기는 되살아나
   진행 중 오더를 덮어썼다.
3. **자동 처리가 탭 수명에 묶인다.** 온체인 15분 마감, 라이트닝 선제 settle 같은 시계가 "누군가
   어드민을 열어두고 있어야" 돈다.
4. **돈 되는 비밀이 브라우저에 있다.** LN 매크룬을 브라우저에서 풀고, 그걸 쓰려고 LND REST를
   인터넷에 노출했다.

1~2는 소유권·재동기화·항목별 백업으로 막을 수 있지만, **막을 대상 자체가 없는 구조**가 싸다.
3~4는 브라우저로는 못 푼다.

# §4. 데몬 내부

## §4.1 프로세스 모델

프로세스 하나, 쓰기 경로 하나. 모든 상태 변경은 **직렬화된 한 줄**로 들어간다:

```
① 수신     릴레이 이벤트 → inbox(id UNIQUE) → 처리 대기
② 디스패치 inbox 한 건 or 틱 한 번 → 핸들러(순수 판단) → 트랜잭션: 상태 + 의도
③ 워커     의도 → 외부 호출(LN·체인·발행·푸시) → 결과 기록 → (필요하면) 다음 전이
```

- 핸들러는 지금의 `decide.ts`처럼 **판단만** 한다. 네트워크를 부르지 않는다 — 테스트가 쉽고, 판단
  도중에 상태가 바뀌는 레이스가 없다.
- 외부 효과는 전부 **의도 → 실행 → 기록** 3단이다. 실행 전에 죽으면 재시작 뒤 의도를 다시 집는다.
  그래서 **효과마다 멱등**이어야 한다(§4.5).

## §4.2 저장 — SQLite

파일 하나, WAL. 스키마는 마이그레이션 번호로 관리한다(브리지와 같은 방식).

| 테이블 | 담는 것 | 비고 |
|---|---|---|
| `inbox` | 받은 kind 1111 원문, 처리 결과 | `id` UNIQUE (DM-004) |
| `ln_orders` | 라이트닝 오더 전 필드 + `version` | 발행 태그의 원천 |
| `oc_orders` | 온체인 오더 전 필드 + `version` | 〃 |
| `oc_meta` | 받을 주소·feerate·사전서명·환불 주소·원본 tx(outbox) 등 공개 안 하는 값 | 지금의 `escrow-meta-store` |
| `invoices` | 홀드 인보이스: `payment_hash` PK, 용도, 오더, 파생 경로(용도·시도 번호), 금액, 만료, CLTV, 관측 상태, HTLC 만기 높이 | 에스크로·보증금·온체인 보증금 전부 |
| `effects` | 효과 의도: 종류(settle/cancel/pay/create-invoice/broadcast/publish/push), 대상, 상태, 시도 횟수, 다음 시도 시각, 마지막 오류 | §4.5 |

| `commands` | 운영자 명령 원문·결과 | §5 |
| `alerts` | 사람이 볼 것 | 운영자 DM 중복 방지 |
| `push_subs` | 웹 푸시 구독 | |
| `kv` | 설정·릴레이 커서·시세 캐시 | |

**`version`은 오더가 바뀔 때마다 +1**이고 발행 `created_at`의 단조 증가에도 쓴다(§4.4).

## §4.3 받기

- 구독: `{kinds:[1111], '#p':[APP]}` 하나로 유저 요청과 운영 명령을 다 받는다. 트랙은 `t` 태그로 가른다.
- **커서**: 받은 것 중 가장 늦은 `created_at`에서 `lookback`(기본 6시간)만큼 되돌아가 다시 받는다 — 릴레이
  시계 차이·늦은 전파·오프라인이던 클라이언트가 한꺼번에 쏜 것까지. 겹치는 건 DM-004가 거른다. 첫 부팅은
  에포크(`LNPAY_EPOCH`, 없으면 부팅 시각)부터이고 에포크는 DB에 박힌다.
- **미래 시각 이벤트는 커서를 못 움직인다**(5분 넘게 앞서면). 안 그러면 누군가 먼 미래 `created_at`으로
  커서를 밀어 올려 재구독이 진짜 이벤트를 건너뛰게 만든다.
- **구독을 주기적으로(기본 5분) 새로 연다.** 오래 사는 구독은 에러 없이 조용히 죽는다(cliprelay에서 길게
  겪었다). 죽음을 탐지하려 애쓰는 대신 커서에서 다시 받는다 — 이 앱의 요청량이면 비용이 없다.
- **순서**: 같은 오더의 요청은 `created_at` 순으로 처리한다. 버퍼링 창을 짧게 둔다(몇 초) — 릴레이마다
  도착 순서가 달라도 판단이 흔들리지 않게.
- 발신자 확인(O-020)과 스팸 상한(후보 인보이스 5개 등)은 **디스패치 앞단**에서 한다.

## §4.4 보내기 — 발행 대기열

- 오더 이벤트는 **"오더 X를 발행하라"는 의도**로 쌓고, 워커가 발행 시점의 **최신 행**으로 이벤트를 만든다.
  같은 오더의 발행 의도가 여럿이면 하나로 합친다 — 중간 상태를 굳이 다 내보내지 않는다.
- `created_at = max(now, 직전 발행 created_at + 1)` — 같은 초 두 갱신에서 옛 상태가 남는 NIP-01 동률 문제를
  구조로 없앤다.
- NIP-40 `expiration`은 **보존 기간**이다(DM-009): 의뢰 대기 상태는 의뢰 마감, 진행 중은 `now + 보존 기간`,
  종결은 `+7일` 유예. 거래 마감은 별도 태그로 싣는다(§7 L-1).
- 실패하면 지수 백오프로 재시도한다. 발행 실패가 상태를 되돌리지 않는다 — DB가 진실이고 발행은 투영이다.
  (프론트 어드민의 "발행 실패 → 롤백" 곡예가 사라진다.)

## §4.5 외부 효과

| 효과 | 멱등하게 만드는 법 |
|---|---|
| 홀드 인보이스 생성 | 프리이미지가 `(용도, 오더, 시도 번호)`에서 결정되므로 **payment hash가 미리 정해진다.** 같은 해시로 다시 만들면 노드가 거절 → 조회로 확인 |
| settle | 먼저 조회: `settled`면 끝, `accepted`면 settle |
| cancel | 먼저 조회: `cancelled`면 끝 |
| 지급(pay) | 같은 bolt11 재결제는 노드가 payment hash로 거절. 결과는 조회로 확정 |
| 온체인 브로드캐스트 | 원본 tx를 먼저 기록(outbox) → 같은 바이트 재전송은 무해 |
| 발행 | 같은 이벤트 재발행은 무해 |
| 웹 푸시 | `(오더, 전이)`로 중복 방지 |

**LN 조회는 HTLC 만기 높이까지 본다.** LND 인보이스 조회는 `htlcs[].expiry_height`를 준다 — 에스크로가
**실제로** 언제 죽는지를 추정(생성 시각 + 24h)이 아니라 체인 높이로 안다(§7 L-3).

## §4.6 시계

- 틱 하나(기본 15초)가 마감·LN 상태 폴링·체인 폴링(온체인은 30~60초)·효과 재시도를 돈다.
- 마감은 **오더 행에 시각으로** 저장한다. 재시작하면 지난 마감을 한꺼번에 처리한다 — 그 순서가 결과를 바꾸지
  않게 핸들러가 이미 지금 시각 기준으로 판단한다.

| 비밀 | 어디에 | 비고 |
|---|---|---|
| **시드** (32바이트) | 비밀 파일(읽기 전용 마운트) | 종이 백업. 아래 전부의 뿌리 |

| VAPID 개인키 | 비밀 파일 | |

**파생** (DM-005):

```
프리이미지(용도, 오더, n)   = HMAC-SHA256(seed, "lnpay/preimage/v1/" ‖ 용도 ‖ "/" ‖ orderId ‖ "/" ‖ n)
온체인 어드민 키(오더)      = HMAC-SHA256(seed, "lnpay/onchain-admin/v1/" ‖ orderId)  (0 또는 ≥ n이면 카운터 붙여 재시도)
```

- DB를 잃어도 시드만 있으면 **알려진 payment hash에 대해 n을 올려가며** 프리이미지를 되찾고, 어드민 키는
  바로 다시 만든다. 프론트 시절의 키 저장소·프리이미지 백업·병합 코드가 통째로 사라진다.
- 시드는 외부에 보이는 값과 연결되지 않는다(HMAC 출력만 공개 해시·공개키로 쓰인다).

# §5. 어드민 명령 채널

## §5.1 운영자 키

어드민 앱은 **APP 키가 아니라 운영자 키**로 로그인한다(NIP-07 또는 NIP-46). 데몬 설정의 운영자 목록에
있는 pubkey의 명령만 받는다. APP 키로 로그인하면 어드민 앱이 데몬의 FSM을 우회해 아무 이벤트나 서명할 수
있다 — 그 자리를 없애는 게 이 전환의 요점이다.

**lnpay의 키는 둘이다** — 서명하는 키(APP = 데몬)와 명령하는 키(운영자). 하나로 합치면 "집행자는 데몬
하나"(DM-001)가 규칙으로만 남고 구조로는 안 지켜진다. 셋일 이유도 없다 — APP 키는 기존 것을 쓴다(§14 D9).

## §5.2 명령

```
kind 1111, p = APP, t = <CLIENT_TAG>-admin, expiration = now + 10분
content = NIP-44(운영자 → APP, { cmd, args, orderId?, expectVersion? })
```

- **만료 10분** — 폰에서 눌러놓고 한참 뒤 전달된 명령이 뒤늦게 집행되지 않게. 데몬도 `created_at`이
  10분보다 오래된 명령은 버린다.
- **중복**: 이벤트 id로 한 번만(DM-004).
- **버전 확인**(DM-006): 판정·강제 종결처럼 오더를 바꾸는 명령은 `expectVersion`을 실어야 하고, 다르면 거절한다.
- **결과**: `kind 1111, p = 운영자, e = 명령 id, action = admin-result`, NIP-44(APP → 운영자). 어드민 앱은 결과가
  올 때까지 버튼을 "처리 중"으로 둔다.

## §5.3 어드민 전용 상태

공개 오더 이벤트에 없는 것(인보이스 상태, 보증금 만료 추정, 지급 오류, 경보, 온체인 메타 등)은 데몬이
운영자에게 암호화해 발행한다:

| 이벤트 | 담는 것 |
|---|---|
| `kind 30078, d = lnpay-admin:<tag>:state` | 요약: 데몬 하트비트, 노드 상태, 경보 목록, 설정 |
| `kind 30078, d = lnpay-admin:<tag>:order:<orderId>` | 오더별 비공개 상세 (진행 중 + 종결 후 보존 기간) |

어드민 앱은 지금처럼 **스토어를 구독**하고(헌법), 서비스 레이어가 이 이벤트들을 받아 스토어에 넣는다.
하트비트가 끊기면 화면이 "데몬 응답 없음 · N분 전"을 띄운다.

## §5.4 분쟁 채팅 중계

분쟁 채팅은 **APP 키와 유저** 사이의 NIP-44다. 운영자 키는 그걸 못 읽으므로 데몬이 중계한다:

- 들어오는 메시지: 데몬이 복호화해 운영자에게 `admin-chat` 이벤트로 다시 암호화해 보낸다(메시지당 하나).
- 나가는 메시지: 운영자가 `chat.send` 명령 → 데몬이 APP로 `dispute-message`를 발행한다.
- 계좌 공개(라이트닝 `reveal`)·커밋먼트 대조(온체인 계좌 이의)도 데몬이 검증해 결과를 오더별 상세에 싣는다.

## §5.5 명령 목록 (초안)

| 트랙 | 명령 | 버전 확인 |
|---|---|---|
| 공통 | `ping` · `config.get` · `config.set` (자동 승인, 보증금 비율, 온체인 새 의뢰 받기) · `alert.ack` · `chat.send` | — |
| 라이트닝 | `ln.rule {winner}` · `ln.force-close` · `ln.revert-claim` · `ln.retry-payout` · `ln.deposit {settle\|cancel}`(예외용) | ✅ |

> 네트워크(mainnet/signet)·체인 API·LN 접속은 `config.set`에 없다 — 진행 중 거래가 있는데 바뀌면 안 되는
> 값이라 **배포 설정(데몬 환경변수)**으로 둔다. 운영 중에 바꾸는 값만 명령으로 바꾼다.
| 온체인 | `oc.rule {winner}` · `oc.account-dispute {verdict}` · `oc.resend` · `oc.rescue`(§14 D7이 수동이면) | ✅ |

그 오더의 채팅).

**epoch 컷.** 옛 프론트 어드민이 **같은 APP 키·같은 태그**로 낸 오더가 릴레이에 남아 있다(NIP-40을 안 지키는
릴레이도 있다). 그래서 데몬이 운영자 상태에 `epoch`(첫 부팅 때 고정된 `LNPAY_EPOCH`)를 싣고, 어드민은

지운다 — 지금 로그인 세션만 남긴다(`admin/src/legacy-storage.ts`. 옛 거래는 전부 종결·버린 테스트, VAPID 키는
`vapid.key`로 따로 백업됨 — 운영자 확인).

# §7. 라이트닝 트랙 — 옮기면서 고칠 것

라이트닝 FSM(`admin/src/state-machine.ts`)을 옮기면서 2026-09-24 점검에서 나온 것을 고친다. **FSM을
바꾸는 항목은 4종 세트**(전이 → 알림 문구 → 문서 → 진행도 → 배지)를 따른다.

| # | 무엇 | 어떻게 |
|---|---|---|
| **L-1** | **`order.expiration`이 쿠팡 가상계좌 기한이다** — 거래 마감과 이벤트 보존이 한 태그에 겹쳐 있었다(DM-009) | 거래 마감을 새 태그 `deadline`으로 옮기고, `expiration`은 §4.4의 보존 규칙만 따른다. 유저 앱은 카운트다운·오더북 필터에 `deadline`을 쓴다(§9) |
| **L-2** | 마감을 넘긴 거래가 통째로 사라졌다(정리 작업이 상태 무관하게 오더·프리이미지를 지움) | 데몬은 진행 중 오더를 지우지 않는다. **마감 뒤 규칙**: `remitted` 이전이면 가상계좌가 닫혀 원화가 갈 수 없으므로 유예 G(기본 1시간 — 마감 직전에 송금했는데 송금 완료·입금 확인이 늦게 오는 경우) 뒤 **자동 종결** + 에스크로 cancel(고객 즉시 환불). `remitted` 이후는 계속 진행한다 |
| **L-3** | 에스크로 마감을 "생성 + 24h"로 추정했다 | HTLC `expiry_height`로 실제 마감을 안다(§4.5). 선제 settle(비대칭 손실 원칙)은 이 실제 마감 기준 |
| **L-4** | `paid`를 settle 전에 발행하고 실패하면 재시도가 없었다 | DM-003: settle 성공 → `paid`. 실패는 효과 대기열이 재시도하고 오래 실패하면 경보 |
| **L-5** | 지급 실패는 수동 재시도, 지급 전 인보이스가 만료되면 재제출 불가 | 지급 자동 재시도(백오프). `disbursed` 전이면 `paid`·`sponsor_wins`에서도 **재제출을 받는다**(같은 금액 등식). 만료 임박이면 데몬이 후원자에게 재제출을 요청한다 |
| **L-6** | 방치된 `escrowed`/`invoiced`는 사람이 강제 종결해야 끝났다 | L-2의 자동 종결로 흡수. 보증금 처리는 §14 D4 |
| **L-7** | 선제 settle 뒤 `customer_wins`면 사람이 손으로 환불 | (선택, P3 후반) 고객에게 **환불 인보이스를 요청**하는 경로 — 후원자 인보이스와 같은 모양. 없으면 이 드문 경우만 수동으로 남긴다 |
| **L-8** | 이중 인보이스(다기기) | DM-001로 소멸. 추가로 `invoices`에 `(오더, 용도, 시도)` UNIQUE |
| **L-9** | 정리 작업이 LN 어댑터 없이 시작돼 만료 보증금 처리가 한 번도 안 돌았다 | 데몬 틱이 처리한다. 만료된 대기 보증금은 **즉시 cancel**(CLTV까지 묶어두지 않는다) |

- **온체인** `daemon/src/onchain/` — 순수 판단(`decide`·`funding`·`deposit`)과 알림 표(`notify-messages`)는

  **트랜잭션 안·네트워크 없이** 다시 짰다. 수수료는 워처가 틱 맨 앞에 받아 두고(`fees.ts`, 10분 지나면 모름)
  핸들러가 그 값으로 보증금·최소 거래액·릴리스 feerate 상한을 본다. 저장은 `oc_orders`(공개 필드 JSON +

- **바뀐 동작**:
  - outbox와 `settling`을 **한 트랜잭션에** 적고 뿌리는 건 효과다 — 리뷰 #8 R3("발행 실패 → 엉뚱한 쪽 몰수")가
    구조적으로 없어졌다. 브로드캐스트 실패는 효과가 8번까지 다시(같은 바이트), 멤풀 이탈은 워처가 다시 쌓는다.
  - 마감 확인은 **요청이 만들어진 시각**(`min(created_at, now)`)으로 — 데몬이 잠깐 꺼져 있던 사이 마감 안에 보낸
    사전서명·계좌·송금 주장이 늦게 처리돼도 정직한 쪽이 몰수되지 않게. 이미 결정된 거래는 상태 확인이 먼저 막는다.
  - 재시작 워밍업(2분) 동안 시계 행동(`cancel`·`settle`·`dispute`)을 미룬다(라이트닝과 같다).
  - 운영자 알림 = 경보(분쟁 진입·몰수금 처리·구조 대상·키 유출 의심 등). 고객 "마감 임박"은 송금 주장당 한 번.
  - 새 의뢰는 `onchain.acceptNewOrders`가 켜져 있어야 받는다(기본 꺼짐) — 네트워크(`LNPAY_ONCHAIN_NETWORK`)를
    안 적으면 트랙 자체가 없다.

  · 판정·계좌 이의 판정·서명 요청 재전송·구조 버튼 · 분쟁 채팅(두 트랙 공용 컴포넌트로 뺐다).

  어차피 멱등). 처음 돌렸을 때 8종이 살아남아 테스트를 조였다(제3자의 **유효한** 사전서명, 마감 뒤 사전서명,
