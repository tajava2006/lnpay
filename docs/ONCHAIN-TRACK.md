# 온체인 트랙 — 스크립트 · 상태 머신 · 규약 · 시간

non-KYC 비트코인 직거래다. **고객**이 BTC를 2-of-3 taproot 에스크로에 넣고, **후원자**가 고객 계좌로 원화를
보내면 BTC가 후원자에게 간다. (역할 이름은 쿠팡 대리결제 시절의 것이라 유저 화면은 "나 / 상대방"으로 말한다.)
라이트닝 트랙과 **FSM·태그·이벤트 보존 규칙이 전부 따로**다(`CLIENT_TAG_ONCHAIN = sajwo-tracker-onchain`).
보증금만 라이트닝 홀드 인보이스를 같은 기계(`daemon/src/hold`)로 쓴다.

**이 문서의 진실은 코드다.** 부등식은 `daemon/src/__tests__/timing-invariants.test.ts`가 확인한다.

## 1. 스크립트 · 키 · 주소

```
내부키(key path)   BIP-341 NUMS 점 — 아무도 못 쓴다

leaf 1  release        <C> CHECKSIGVERIFY <S> CHECKSIG     정상 완료 → 후원자
leaf 2  customer-win   <A> CHECKSIGVERIFY <C> CHECKSIG     환불 · 고객 승 · 구조 → 고객
leaf 3  sponsor-win    <A> CHECKSIGVERIFY <S> CHECKSIG     후원자 승 → 후원자
leaf 4  timelock       <8064> CSV DROP <C> CHECKSIG        어드민 부재 시 고객 단독 회수 (≈8주)
```

- **트리 모양을 못박는다** — `[[1,2],[3,4]]` 균형 트리. 라이브러리의 허프만 배치에 맡기면 버전이 바뀔 때 같은 키에서
  다른 주소가 나올 수 있다. 모든 리프 깊이가 2라 종결 tx 크기가 경로와 무관하게 같다.
- **MuSig2 키패스를 안 쓴다.** 논스 재사용 = 개인키 유출이고, 브라우저의 재시도·새로고침·다기기가 전부 재사용 경로다.
- **CSV(상대)다.** 펀딩 컨펌부터 세므로 어느 주문이든 보호 창이 같다.
- **세 키는 주문마다 새로 만든다.**
  - 고객·후원자: nostr 키에서 HMAC으로 결정론적 파생(`pairbuy-onchain/v1/` + 주문 id). nostr 키를 그대로 넣으면
    공개된 nostr 계정과 온체인 주소가 이어진다. 추가 백업 부담은 없다(nostr 키만 있으면 복원).
  - 어드민: 데몬 시드에서 주문마다 파생(DM-005). 시드만 있으면 언제든 같은 키가 나온다.
- 세 키는 **서로 달라야** 한다(같으면 2-of-3이 깨진다) — 파생 전에 검사한다.
- **주소는 유저 앱이 스스로 파생해 대조한 뒤에만 보여준다**(T-107). 오더에 실린 주소를 믿지 않는다.
- 종결 tx는 입력 하나·출력 하나다. 중재료는 몰수 보증금에서 나오므로 어드민 출력을 달지 않는다. nSequence는 final
  (타임락 경로만 CSV 값). **교체를 막는 건 nSequence가 아니라 2-of-3이다** — full-RBF에서 신호는 교체를 못 막는다.

## 2. 상태 머신

```
listed → bonded → funded → presigned → remitted → settling → released
            │        │          │           └──→ disputed ──┤    ├→ sponsor_wins
            │        └──────────┴──→ refunding ─────────────┘    ├→ customer_wins
            └──→ refunding (fold)                                └→ refunded
listed · bonded → cancelled        (펀딩 컨펌 이후 어느 상태든) → swept   (타임락 회수, 관측만)
```

`funding`(멤풀에 보임) 상태는 **의도적으로 없다.** 우리는 0-conf로 아무 결정도 안 하고(공격 D), 판정은 "마감 안에
이 **주소**로 약정 금액이 N컨펌 됐는가" 하나다. txid를 쫓으면 수수료를 올린 정직한 고객을 "사라졌다"로 읽는다.
멤풀 관측은 화면 힌트로만 쓴다.

### 전이와 방아쇠

| 전이 | 방아쇠 | 조건 |
|---|---|---|
| (없음) → `listed` | 고객 `onchain-order-request` → **고객 보증금 결제** | 새 의뢰 받기 켜짐(`onchain.acceptNewOrders`), 만료 ≤ 7일, 환불 주소가 이 네트워크 것, 최소 거래액 이상, reserve는 시세보다 3% 이상 아래, 보증금 CLTV ≤ 1500 |
| `listed → bonded` | 후원자 `onchain-claim` → **후원자 보증금 결제** | 자기 의뢰 아님, 받을 주소·feerate가 경계 안(`releaseFeerateProblem`). 결제 대기 후보는 의뢰당 5명까지, **먼저 결제한 쪽**이 가져가고 나머지는 취소. 이 순간 세 키가 정해져 주소가 나온다 |
| `listed → cancelled` | 고객 `cancel-request` / 워처(의뢰 만료) | 보증금이 잡힌 뒤엔 고객 혼자 못 내린다 |
| `bonded → funded` | 워처 | 주소에 약정 금액 UTXO가 정확히 하나, N컨펌. 후원자 보증금 살아 있음(O-015), 신선한 시세. **이 순간이 T0 — 가격 고정** |
| `bonded → refunding` (fold) | 워처 | 컨펌됐는데 시세 < reserve(`refund:reserve`) 또는 후원자 보증금이 죽음(`refund:bond-expired`) — 가격을 고정하지 않고 접는다 |
| `bonded → cancelled` | 워처 | 펀딩 마감까지 컨펌 안 됨. **주소에 컨펌된 UTXO가 없음을 확인해야** 한다(O-014, 조회 실패는 거부) |
| `funded → presigned` | 후원자 `onchain-presig` | 데몬이 직접 만든 릴리스 tx와 대조해 서명이 맞음(T-109). 마감 안 |
| `presigned` 안: 계좌 공개 | 고객 `account-info` | 계좌는 후원자에게만 암호화, 데몬은 시각·커밋먼트만. 이때부터 후원자 송금 시계(O-013) |
| `presigned → remitted` | 후원자 `remit-request` | 계좌를 받았고 송금 마감 안. **일방적 주장이다** — 릴리스 트리거가 아니다(O-007) |
| `funded·presigned → refunding` | 워처 | 마감 초과 — §4의 사유 |
| `remitted → disputed` | 워처(확인 마감) / 당사자 `onchain-dispute` | 고객 동의를 묻지 않는다(O-010) |
| `remitted·disputed → settling` | 고객 `onchain-cosign`(release) | 원화 확인 = 고객 서명. 데몬이 보관한 후원자 사전서명과 합쳐 브로드캐스트 |
| `disputed` 안: 판정 | 운영자 `oc.rule` | 사유가 박히고 **이긴 쪽**에 서명 요청 |
| `refunding·disputed → settling` | 이긴 쪽/고객 서명 | 데몬이 검증 후 **마지막에** 서명해 브로드캐스트(O-018) |
| `settling → 터미널` | 워처 | 종결 tx N컨펌 |
| `funded·presigned → bonded` | 워처(리오그) | 컨펌이 N 아래로. 가격 고정 폐기 + 마감 재발급(O-008) |
| `… → swept` | 워처 | 에스크로 소모 증인에 **타임락 리프**가 있을 때만(O-006) |

## 3. 서명 순서

**릴리스** (`{C,S}`, 어드민 키 0):
1. `funded`: 후원자 앱이 릴리스 tx(후원자 주소, 클레임 때 낸 feerate)를 만들어 서명해 보낸다. 데몬이 자기가 만든 tx와
   대조해 보관하고, **그 PSBT를 바로 고객에게 전달**한다.
2. 고객이 은행 입금을 확인하고 버튼을 누르면 고객 앱이 **자기 기록으로 tx를 다시 만들고**, 후원자 서명을 옮겨 심은 뒤
   자기 서명을 얹어 보낸다.
3. 데몬이 두 서명을 검증해 완성하고, 장부(outbox + `settling`)에 먼저 적은 뒤 뿌린다(O-019).
   양쪽 보증금은 **이 순간** 환불한다 — 완성된 릴리스를 막을 길은 어드민 서명 경로와 8주 타임락뿐이다.

고객은 `presigned`부터 완성 가능한 릴리스를 쥔다. 원화 확인 전에 뿌리면 자기 손해라 막지 않는다(체인에서 보면 장부가
따라간다).

**그 밖의 종결** (`{A,C}`·`{A,S}`): 데몬이 결정(사유·수수료)을 먼저 박고 **서명 없는** PSBT를 서명할 쪽에 보낸다.
받는 쪽은 그 PSBT를 믿지 않고 자기 기록(받는 주소·리프·수수료)으로 같은 tx를 다시 만들어 **txid까지 같을 때만**
서명한다(O-021). 데몬이 그 서명을 검증하고 **마지막에** 자기 서명을 얹는다 — 고객 손에 완성 가능한 환불 tx가 들리는
순간을 만들지 않는다(O-018). 서명 요청은 안 오면 6시간마다 다시 보낸다.

## 4. 종결 사유 → 보증금

**사유가 곧 처리다**(`OUTCOME_RULES`). `refunded` 하나에 보증금 처리가 정반대인 경우가 섞여 있어 상태만 보면 틀린다.
보증금은 **결정 시점**에 처리한다 — 종결 tx 컨펌 때 하면 몰수당할 쪽이 서명을 미뤄 HTLC 만료를 기다린다(공격 Z).

| 사유 | 종결 | 후원자 보증금 | 고객 보증금 | 몰수금 쓰임 |
|---|---|---|---|---|
| `release` | released | 환불 | 환불 | |
| `refund:reserve` | refunded | 환불 | 환불 | |
| `refund:sponsor-timeout` | refunded | **몰수** | 환불 | 50% 피해자 충당(재량) |
| `refund:customer-late` | refunded | 환불 | **몰수** | 50% 충당 |
| `refund:bond-expired` | refunded | (이미 만료) | 환불 | |
| `refund:account-disputed` | refunded | 보류 | 보류 | 운영자가 `oc.account-dispute`로 사유를 확정하면 집행 |
| `sponsor_win` | sponsor_wins | 환불 | **몰수** | 전액 중재료 |
| `customer_win` | customer_wins | **몰수** | 환불 | 전액 중재료 |
| `cancel:customer` | cancelled | — | 환불 | |
| `cancel:expired` | cancelled | — | 환불 | |
| `cancel:no-funding` | cancelled | 환불 | **몰수** | 50% 충당 |
| `swept` | swept | (만료) | (만료) | |

몰수금의 쓰임은 운영자가 손으로 한다(경보가 뜬다). 자동화하면 "인보이스 발행 대기"라는 상태가 하나 더 생긴다.

**계좌 이의**는 상태가 아니라 **증거**다. 후원자가 송금 마감 전에 "계좌를 쓸 수 없다"고 내면 시각만 박힌다. 상태로
받으면 원화 시계가 멈추고 그 순간 무한 옵션이 열린다. 마감이 차면 `refund:account-disputed`로 양쪽 보증금을 붙잡고,
운영자가 증거를 보고 고객 과실(`account-bad`)이나 후원자 과실(`sponsor-fault`)로 확정한다.

## 5. 수수료 · 금액

| 경로 | 수수료 부담 | feerate |
|---|---|---|
| 펀딩 | 고객 | 고객 지갑이 정한다 |
| 릴리스 | 후원자(출력에서 빠짐) | **후원자가 클레임 때 낸 값**. 경계: ≥ 1 sat/vB, ≤ max(100, 지금 fastest × 5), 수수료 ≤ 거래액 20%, 남는 출력 > dust |
| 환불·고객 승·구조 | 고객(출력에서 빠짐) | 결정 시점 시세 `halfHour` |
| 후원자 승 | 후원자(출력에서 빠짐) | max(후원자가 낸 값, 결정 시점 `halfHour`) |
| 타임락 회수 | 고객 | 고객이 정한다 |

- 막히면 **받는 쪽이 CPFP**한다(RBF 신호 없음). 안내는 받는 쪽에게만 간다. 유저 앱이 서명 전에 수수료율 상한
  (`MAX_SANE_SETTLEMENT_FEERATE` 1000 sat/vB)을 본다 — 악의적 어드민이 에스크로를 수수료로 태우는 것을 막는 마지막 줄.
- **요구 컨펌 수**(`requiredConfirmations`): < 10만 sats 1 · < 100만 2 · 그 이상 3. 펀딩 확정과 종결 확정이 같은 값을 쓴다.
- **보증금** = max(거래액 × 비율, 하한). 비율은 고정값이다 — 고객 1%, 후원자 3%(`daemon/src/onchain/deposit.ts`).
  하한 = 종결 tx 수수료 × 4(지금 `halfHour` 기준). 후원자가 버리면 고객은 수수료를 2회(펀딩·환불) 잃고, 몰수금의 50%로
  그걸 덮으려면 4회분이어야 한다.
- **최소 거래액** = 하한 ÷ 3%. 이 아래에서는 보증금이 3%를 넘어 억제가 아니라 허들이 된다. 고수수료 장세에서 폭등한다
  — 그때 소액은 라이트닝 트랙 몫이다.
- **reserve(최저가)**: T0 시세가 이보다 낮으면 무과실 환불. 시세보다 3% 이상 아래여야 받는다 — 바로 아래에 걸면 컨펌
  대기 동안의 공짜 풋옵션이 된다(완화일 뿐, RISKS 참고).
- 보증금이 옵션 창(최대 105분)의 가격 변동을 완전히 덮는지는 **따지지 않기로 했다**(운영 결정). 보증금은 스팸·이탈
  억제 장치다.

## 6. 시간

**마감 없는 상태는 없다**(O-009). 예외는 둘이고 둘 다 머물러서 이득 보는 쪽이 없다:
`disputed`(자동 해소는 어느 방향이든 탈취다) · `refunding`(고객 자기 돈, 보증금은 이미 처리됨, 최후엔 타임락).

```
listed ──의뢰 만료(≤7일)──────────────→ cancelled (고객 환불)
bonded ──2시간(컨펌까지)─────────────→ cancelled + 고객 몰수
funded(T0) ──15분──────────────────→ refunding (후원자 몰수)
   presigned ──1시간(계좌 공개)──────→ refunding (고객 몰수)
      계좌 공개 ──30분(원화 송금)────→ refunding (후원자 몰수 · 이의가 있었으면 보류)
remitted ──24시간(고객 확인)───────→ disputed   (2시간 전에 한 번 경고)
disputed ── 하드 마감 없음 ──────────  7일·14일 에스컬레이션. 판정 예산 24h 뒤엔 몰수를 못 할 수 있다
settling ──24시간────────────────→ 경고 + CPFP 안내 (하드 마감 아님)
```

- **마감은 자기가 통제 못 하는 지점에 앵커한다**(O-013). 사전서명·계좌 마감은 T0·`presigned`에, 원화 마감은 **계좌 공개
  시점**에 건다. 고객이 늦게 공개해도 후원자 창이 안 깎이고, 총 옵션 창은 **T0 + 105분**을 못 넘는다.
- 마감은 **데몬이 전이할 때 오더에 찍는다**(`*-deadline` 태그). 화면과 데몬이 같은 숫자를 본다. 데몬 창 길이는 운영자
  상태(`onchainWindows`)로도 나가고, 어드민이 자기 빌드 값과 다르면 경고한다(옛 이미지로 도는 데몬을 잡는다).
- **핸들러도 마감을 본다.** 워처(30초 틱)만 보면 틱 사이에 온 늦은 요청이 통과한다. 요청 시각은 요청이 **만들어진
  시각**으로 본다 — 데몬이 잠깐 꺼져 있던 사이 마감 안에 보낸 요청으로 정직한 쪽이 몰수되지 않게.
- 리오그로 `bonded`에 돌아오면 **펀딩 마감을 다시 찍는다** — 안 그러면 체인 사고로 정직한 고객이 몰수된다.

### 지켜야 할 부등식

```
① 보증금 CLTV 최대 (7d + 49h45m + 6h ≈ 1343블록)  ≤  CLTV_MAX (1500)
   └ 깨지면: 긴 의뢰는 보증금 인보이스를 못 만들어 등록 자체가 거절된다
② 보증금 CLTV  ≥  남은 의뢰 수명 + 최악 소요       (막바지 클레임도 판정까지 몰수가 산다)
③ 옵션 창 = 사전서명 + 계좌 + 송금 (105분) — 앞 두 마감이 T0에 묶여 합이 이걸 못 넘는다
④ 확인 창 (24h)  =  가격 유효창 (24h)             (O-016: 낡은 가격으로 체결 안 됨)
⑤ 확인 경고 (2h)  <  확인 창 (24h)
⑥ 타임락 (8064)  >  송금 차단 임계 (1008)  >  T0 → 원화 송금 최대 (105분 ≈ 11블록)
   └ 원화가 흐를 때 타임락은 거의 전량 남아 있다. 고객이 침묵으로 타임락까지 끄는 길은 없다(O-012)
⑦ 이벤트 보존 (70d)  >  타임락 (8064블록 ≈ 56d)    (거래 도중 릴레이가 발행을 거절하지 않게)
⑧ 수수료 유효 (10m)  >  수수료 갱신 (2m)             (갱신 한 번 실패로 요청이 전부 거절되지 않게)
```

⚠️ **블록 시간 가정.** 보증금 CLTV는 블록 = 600초로 환산한다. 블록이 빨리 나오면 6시간 여유가 먼저 깎이고, 그다음은
판정 예산이다. 분쟁 카드가 보여주는 **보증금 만료 추정치**가 판정을 재촉하는 실질 기준이다.

## 7. 불변조건

| ID | 조건 | 막는 것 |
|---|---|---|
| O-001 | `funded` 이후엔 `cancelled`로 못 간다. `bonded`에서는 주소에 컨펌된 UTXO가 없을 때만 | 확정된 자금이 tx 없이 "취소"되는 회계 구멍 |
| O-002 | `funded` 이전에는 계좌 정보가 안 나간다 | 에스크로 없이 원화가 오가는 것 |
| O-003 | `presigned` 이전에는 계좌 정보가 안 나간다 | 후원자가 사전서명 없이 계좌만 받고 튀는 것 |
| O-004 | 모든 터미널은 **컨펌된 txid**가 근거다(`cancelled` 제외) | 어드민이 tx 없이 상태만 발행하는 것 |
| O-005 | `settling`은 되돌아가지 않는다. 멤풀 이탈은 같은 tx 재브로드캐스트 | 종결이 앞 상태로 돌아가는 무의미한 전이 |
| O-006 | `swept`는 관측만 한다(증인에 타임락 리프가 있을 때만) | 어드민이 타임락 회수를 대신 주장하는 것 |
| **O-007** | **릴리스는 고객이 원화 수령을 확인해야만 나간다.** `remitted`는 트리거가 아니다. 자동화 금지(`canAutoRelease(): false`) | 후원자가 원화 없이 `remitted`만 내고 BTC를 가져가는 것(공격 Q) |
| O-008 | 가격은 N컨펌 위에서만 유효하다. 컨펌이 내려가면 `funded` 판정과 가격을 같이 폐기하고 마감을 다시 찍는다 | 사라진 펀딩 위에 가격만 남는 것 |
| O-009 | 마감 없는 상태는 머물러서 아무도 이득을 못 보는 상태뿐이다 | 한쪽이 무기한 옵션을 쥐는 것 |
| O-010 | `remitted` 마감을 넘기면 고객 동의 없이 `disputed` | 원화를 받고 침묵으로 버티다 타임락으로 회수하는 것 |
| O-011 | `disputed`에서 한쪽이 단독으로 나갈 수 없다 — 출구는 판정 또는 릴리스 | 분쟁을 건 쪽이 슬쩍 빠지는 것 |
| O-012 | 원화가 오간 뒤 고객 확인 없이 타임락까지 끌리는 경로가 없다 | 침묵으로 시간을 벌어 타임락을 부르는 것 |
| O-013 | 후원자 마감은 후원자가 통제할 수 있는 시점부터 센다 | 고객 지연 탓에 후원자가 몰수당하는 것 |
| O-014 | `bonded → cancelled`는 컨펌 UTXO 없음을 확인해야 한다. 조회 실패는 거부 | 취소 직후 컨펌된 자금이 아무도 안 보는 주소에 갇히는 것 |
| O-015 | `funded` 진입 시 후원자 보증금이 살아 있어야 한다. 죽었으면 가격을 고정하지 않고 접는다 | 무담보 옵션 창 |
| O-016 | 고객 앱은 가격 유효창(`remitted` + 24h)을 넘긴 릴리스에 경고 후 명시적 우회로만 서명한다 | 늦게 원화를 보내 낡은 가격으로 체결시키는 것 |
| O-017 | 환불이 결정되면(`refunding`) 거래는 앞으로 가지 않는다. 판정은 `canActOnSignRequest` 하나로 화면과 데몬이 같이 쓴다 | 환불을 쥔 채 원화를 받고 환불로 빠지는 것 |
| O-018 | 어드민은 언제나 마지막에 서명한다(릴리스는 어드민 키가 없다) | 고객 손에 완성 가능한 환불 tx가 들리는 것 |
| O-019 | 브로드캐스트 전에 raw tx와 `settling`을 한 트랜잭션에 적는다(outbox) | 뿌린 tx를 장부가 몰라 리오그로 읽고 엉뚱한 쪽을 몰수하는 것 |
| O-020 | 받은 이벤트는 전부 발신자를 본다 — 통지는 `APP_PUBKEY`, 계좌는 그 오더의 고객, 요청은 그 역할 | 제3자의 가짜 계좌·가짜 보증금 인보이스·가짜 서명 요청 |
| O-021 | 유저는 서명 요청을 자기 기록으로 다시 만들어 txid까지 같을 때만 서명한다 | 침해된 어드민이 "환불"을 자기 주소로 보내는 것 |

## 8. 체인 관측

- **펀딩 판정은 주소 기준**이다. 약정 금액 UTXO가 정확히 하나일 때만 `funded`. 금액이 틀리거나 여러 개면 `anomaly` —
  자동 진행도 자동 취소도 안 한다(취소하면 그 자금이 아무도 안 보는 주소에 남는다).
- **조회 실패는 "모름"이다.** 워처는 아무것도 안 하고 다음 틱에 다시 묻는다. "없음"으로 뭉개면 돈이 있는 주소를
  비었다고 보고 취소한다.
- 박아둔 펀딩이 UTXO 목록에서 빠지면 **소모됐는지, 어느 리프로 썼는지**부터 묻는다. 우리가 뿌린 종결 tx면 그대로
  진행하고, 장부에 없는 tx면 체인을 장부에 반영한다(릴리스 리프면 `release`, 타임락 리프면 `swept`, 그 밖은 어드민 키
  유출 의심 경보).
- 리오그: 가격 고정 뒤·원화 전(`funded`·`presigned`)만 `bonded`로 되돌린다. 원화가 흐른 뒤에는 되돌릴 곳이 없어 사람을
  부른다.
- **구조**(`oc.rescue`): 약정 밖의 자금(금액 틀린 펀딩, 이중 송금, 취소 뒤 늦은 펀딩, 확정 뒤 추가 입금)을 `{A,C}`로
  고객 환불 주소에 돌려준다. 진행 중 거래의 박아둔 펀딩은 대상이 아니다(후원자가 송금한 뒤 돌리면 탈취다).
  어드민이 응답하지 않으면 고객 앱의 "비상 회수"가 타임락으로 뺀다.
- 조회는 `LNPAY_ONCHAIN_API`(기본 공개 mempool.space) 하나에 기댄다. 막히면 전부 "모름"이 되어 안전하게 멈춘다.

## 9. 운영자가 하는 것

사람이 판단하는 건 셋뿐이다. 나머지는 워처가 한다.

| 명령 | 언제 |
|---|---|
| `oc.rule` | `disputed` 판정 (후원자 승 / 고객 승). 되돌리지 않는다 |
| `oc.account-dispute` | 계좌 이의 확정 (`account-bad` = 고객 몰수 / `sponsor-fault` = 후원자 몰수) |
| `oc.rescue` | 약정 밖 UTXO를 고객에게 |
| `oc.resend` | 서명 요청·릴리스 PSBT 재전송(유저가 기기를 바꿨을 때) |

판정 기준: 어느 쪽도 기본 승자가 아니다. **몰수를 면하려는 쪽이 증명한다**(입증책임). 은행 **입금 시각**이 송금 창
안이면 인정한다.
