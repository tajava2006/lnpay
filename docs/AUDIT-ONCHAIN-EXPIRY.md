# 온체인 트랙 만료 전수조사

> 2026-09-21. PLAN-ONCHAIN-TRACK §11 P6. 구현(P0~P5)이 끝난 시점에 시간 값들을
> 한 번 훑었다. 라이트닝 트랙의 [AUDIT-EXPIRY.md](AUDIT-EXPIRY.md)와 **같은
> 형식**으로 유지한다 — 두 트랙을 나란히 놓고 볼 수 있어야 한다.
>
> 등급 기준도 같다: **되돌릴 수 있는가.** 과지급은 운영자가 돌려주면 되지만,
> 억제 장치가 조용히 사라지는 건 사고가 난 뒤에야 안다.

## 시간 값 목록

| 값 | 정하는 주체 | 크기 | 위치 |
|---|---|---|---|
| 의뢰 만료 | 고객 | 1~**7일** | `OnchainOrderForm`, `MAX_ORDER_EXPIRY_SEC` |
| 보증금 인보이스 수명 | 어드민 | 의뢰 만료 전체 | `handleOnchainOrderRequest` |
| **보증금 CLTV** | 어드민 | `(남은 만료 + 55h + 6h) / 600` 블록 | `depositCltvBlocks` |
| 펀딩 마감 (컨펌까지) | 어드민 | 6시간 | `FUNDING_WINDOW_SEC` |
| 사전서명 마감 | 어드민 | T0+15분 | `PRESIGN_WINDOW_SEC` |
| 계좌 공개 마감 | 어드민 | `presigned`+5분 | `ACCOUNT_WINDOW_SEC` |
| 원화 송금 마감 | 어드민 | **계좌 공개**+30분 | `KRW_WINDOW_SEC` (O-013) |
| cosign 마감 = 가격 유효창 | 어드민 | 24시간 | `COSIGN_WINDOW_SEC` = `PRICE_VALIDITY_MS` |
| 종결 정체 경고 | 어드민 | 24시간 | `SETTLING_WARN_SEC` |
| 분쟁 에스컬레이션 | 어드민 | 7일 / 14일 | `DISPUTE_ESCALATION_SEC` |
| **타임락 (CSV)** | 스크립트 | 8064블록 ≈ 8주 | `DEFAULT_TIMELOCK_BLOCKS` |
| 후원자 송금 차단 임계 | 후원자 앱 | 잔여 1008블록 | `TIMELOCK_BLOCK_THRESHOLD` |

라이트닝과 달리 **우리가 통제 못 하는 외부 시계가 없다**(쿠팡 가상계좌 같은 것).
대신 **체인**이라는 통제 못 하는 시계가 생겼다 — 컨펌이 언제 될지는 우리 몫이 아니다.
그 불확실성은 "마감 안에 N컨펌"이라는 판정 하나로 흡수했다(§4.1c).

## 지켜야 할 부등식

```
보증금 CLTV      >  남은 의뢰 수명 + 거래 최악 소요(55h)     ← O-F1
보증금 CLTV      <  채널 상한 (보통 2016블록)                ← 7일 상한이 보장
타임락 잔여      >  분쟁 최장 소요                           ← §7 F
cosign 마감      =  가격 유효창                              ← 노브 하나 (§7.6 ③)
옵션 창 총합     ≤  T0+50분                                 ← 앞 두 마감이 T0에 묶임
payoutSat        >  dust(330)
```

테스트가 이 부등식들을 직접 단언한다 — `onchain-timing.test.ts`,
`onchain-deposit-lifecycle.test.ts`.

# 발견과 조치

## O-F1. 보증금 CLTV가 거래 전체를 안 덮었다 — **수정함**

| | |
|---|---|
| **유형** | 억제 장치 소멸 (조용히) |
| **등급** | **HIGH** — 사고가 나야만 드러난다 |
| **원인** | `depositCltvBlocks(expiration, now, graceSec = 86_400)` — **의뢰 만료 + 24시간**으로 잡았다. 의뢰 만료는 "후원자를 찾는 창"이지 "거래에 걸리는 시간"이 아니다 |

### 무엇이 터지나

의뢰 만료 **1시간 전**에 클레임이 붙는 경우를 보자:

```
보증금 HTLC 수명 = 1시간 + 24시간 = 25시간
거래 최악 소요   = 6h(펀딩) + 50m(옵션 창) + 24h(cosign) + 24h(settling) ≈ 55시간
```

**거래 도중에 보증금이 LN 타임아웃으로 환불된다.** 그러면:

- 후원자가 원화를 안 보내고 버려도 **몰수할 게 없다** — 억제가 0이 된다
- 고객이 펀딩을 안 해도 마찬가지다
- 분쟁에서 이겨도 **중재료를 충당할 몰수금이 없다**(§4.1)

그리고 아무도 모른다. 상태는 정상이고, 몰수를 시도하는 순간에야
`lookupHoldInvoice`가 `cancelled`를 돌려줄 뿐이다.

> O-015가 이 문제의 **일부만** 막고 있었다. `funded` 진입 시 후원자 보증금 생존을
> 확인해 죽었으면 접지만, 그 뒤(`presigned`·`remitted`·`disputed`)에 죽는 건 안 본다.
> 그리고 **고객 보증금은 아예 확인하는 자리가 없다.**

### 조치

```ts
CLTV ≥ (남은 의뢰 수명) + MAX_TRADE_DURATION_SEC(≈55h) + 6h 여유
```

7일 상한 덕에 채널 천장 안에 들어간다 — **7일 + 55h + 6h ≈ 9.5일 ≈ 1370블록 < 2016**.
§2.2가 온체인 의뢰 만료를 7일로 묶은 이유가 정확히 이 여유였고, 이번에 그 여유를
실제로 쓴 셈이다.

테스트 둘로 고정했다 — "만료 직전 클레임도 최악 소요를 덮는다", "최장 의뢰에서도
천장 안이다".

# 남은 것 (미조치)

## O-F2. 분쟁이 길어지면 보증금이 먼저 죽는다 — **수용**

`disputed`에는 하드 마감이 없다(§7.5 — 자동 해소는 어느 방향이든 탈취라서).
그런데 보증금 CLTV는 채널 상한(≈14일)을 넘을 수 없다.

**분쟁이 2주를 넘기면 몰수 지렛대가 사라진다.** 중재료도 못 걷는다.

막을 방법이 없다 — LN HTLC의 물리적 한계다. 대신 §7.5의 에스컬레이션(7일·14일)이
**정확히 그 전에** 사람을 부르도록 잡혀 있다. 14일 경보는 "이중화 경로 호출"인데,
**실제 의미는 "지금 안 끝내면 몰수를 못 한다"** 이다. 그 뜻을 경보 문구에 적어둘
가치가 있다(P7 후보).

## O-F3. 종결 tx가 무한 정체하면 같은 문제 — **수용**

`settling`은 되돌아가지 않고(O-005) 수수료가 모자라면 CPFP뿐이다. 그 사이
보증금이 죽을 수 있다. 다만 이때는 **이미 체인에 tx가 떠 있어** 결과가 정해져
있으므로, 보증금이 죽어도 거래 자체는 결국 끝난다. 잃는 건 "종결 후 몰수"뿐이고,
종결 사유가 `release`면 애초에 몰수가 없다.

## O-F4. 고객 보증금 생존을 확인하는 자리가 없다 — **수용(조건부)**

O-015는 후원자 보증금만 본다. 고객 보증금이 죽으면 `cancel:no-funding`에서
몰수를 못 한다. O-F1 수정으로 **정상 경로에서는 안 죽지만**, 분쟁이 길어지면
O-F2와 같이 죽는다.

`funded` 진입 시 양쪽을 다 보게 넓히는 건 어렵지 않다. 다만 **그 시점에 고객
보증금이 죽었다고 접으면 고객이 펀딩까지 마친 거래를 무과실로 되돌리는 것**이라,
득실이 O-015만큼 명확하지 않다. 실제로 겪은 뒤 정한다.

# 라이트닝 트랙과의 차이

| | 라이트닝 | 온체인 |
|---|---|---|
| 외부 시계 | 쿠팡 가상계좌 기한 (통제 불가) | **없음** — 대신 체인 컨펌 |
| 에스크로 만료 | 홀드 인보이스 CLTV | **타임락 리프(8주)** — 훨씬 길다 |
| 만료 시 결과 | HTLC 자동 환불 (후원자만 손해) | 고객 단독 회수 가능 (§7.3 T) |
| 보증금 CLTV | 의뢰 만료 + 24h (F1에서 7일 상한) | **의뢰 만료 + 거래 55h + 6h** (O-F1) |

가장 큰 차이는 **에스크로 만료가 8주로 길다**는 것이다. 라이트닝에서 시간 압박이
만든 사고(F2·F5)가 온체인에서는 거의 안 생긴다 — 대신 그 길이가 §7.3 T(고객이
침묵으로 버티는 경로)를 만들었고, 그건 `remitted` 24h 강제 분쟁으로 막았다.
