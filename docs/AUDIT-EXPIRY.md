# 만료 전수조사

> 2026-09-19. 장기 의뢰를 허용하면서 시간 값들이 서로 어긋날 여지가 커졌다.
> 라이트닝에서 만료는 사고가 제일 잘 나는 자리라 한 번 훑었다.
>
> 등급 기준은 **되돌릴 수 있는가**다. 에스크로가 유저에게 과지급하면 운영자가
> 돌려주면 되지만, 받지 못한 자금은 되돌릴 방법이 없다. 그래서 에스크로가 정산을
> 놓치는 경로를 가장 높게 본다 — 누구 편을 드는 게 아니라 복구 가능성의 차이다.

## 시간 값 목록

| 값 | 정하는 주체 | 크기 | 위치 |
|---|---|---|---|
| 의뢰 만료 | 고객 | 1일 ~ 3개월 | `OrderForm` `EXPIRY_OPTIONS` |
| 에스크로 인보이스 수명 | 어드민 | `min(의뢰만료, 24h)` | `escrowInvoiceExpiry` |
| 에스크로 CLTV | 어드민 | `(수명 + 48h) / 600` 블록 | `approveOrder` |
| 선제 settle 마진 | 어드민 | 10분 | `SETTLE_SAFETY_MARGIN` |
| 후원자 인보이스 최소 수명 | 어드민 | 6시간 | `MIN_INVOICE_LIFETIME_SEC` |
| 보증금 인보이스 수명 | 어드민 | `min(의뢰만료, 24h)` | 아래 F1에서 수정 |
| 보증금 CLTV 마진 | 어드민 | 24시간 | `DEPOSIT_CLTV_MARGIN` |
| **쿠팡 가상계좌 기한** | **쿠팡(외부)** | 약 1일 | `payload.expirationDate` |

마지막 줄이 특히 중요하다. **우리가 통제하지 못하는 유일한 시계**인데 돈이 실제로
오가는 경로에 있다.

## 지켜야 할 부등식

```
쿠팡 계좌 기한   >  후원자가 원화를 보내는 시점
에스크로 만료    >  후원자 원화 송금 + 고객 컨펌
후원자 인보이스 만료 > 지급 시점
에스크로 CLTV    >  분쟁 판정까지 걸리는 시간
```

# 발견과 조치

## F1. 보증금 인보이스가 장기 의뢰에서 생성 불가 — **수정함 (2026-09-20 재수정)**

| | |
|---|---|
| **유형** | 기능 정지 (보증금을 켜는 순간) |
| **원인** | `expiry = request.expiration - now`로 의뢰 만료를 그대로 썼다. 3개월이면 CLTV가 약 13,000블록이 되는데 채널 상한이 보통 2016블록이다 |
| **왜 안 터졌나** | **보증금이 꺼져 있어서.** 켜는 순간 장기 의뢰가 전부 막힌다 |
| **조치** | `depositInvoiceParams()`가 수명(7일 상한)과 CLTV를 **같이** 내놓는다 |

### ⚠️ 이 항목은 한 번 거짓으로 닫혔다

2026-09-19에 여기 "수정함"이라고 적었는데 **코드는 안 고쳐져 있었다.**
`escrowInvoiceExpiry`를 도입하면서 **에스크로만** 바꾸고 보증금 두 경로
(`service.ts`의 고객·후원자 보증금)는 `request.expiration - now` 그대로 두었다.

**회귀 테스트가 green이었던 이유가 더 나쁘다.** `expiry-chain.test.ts`의 보증금
단언이 **프로덕션이 부르지도 않는** `escrowInvoiceExpiry`를 직접 불러 검증했다 —
코드가 아니라 *"코드가 했어야 할 일"* 을 테스트한 것이다. 그래서 버그가 살아 있는
채로 통과했다. 온체인 트랙 플랜을 리뷰하다 발견했다.

### 재수정에서 바꾼 것

1. **보증금 전용 상한 `DEPOSIT_WINDOW_MAX_SEC = 7일`** — 에스크로의 24시간을 그대로
   쓰지 않았다. 보증금은 의뢰가 떠 있는 내내 살아야 몰수가 가능한데 24시간이면
   하루 뒤부터 무담보가 된다. 7일이면 CLTV 1152블록으로 상한에 여유가 크다.
2. **`depositInvoiceParams()`가 수명과 CLTV를 같이 낸다** — 호출부가 CLTV를 직접
   계산하던 게 이 버그의 형태였다. 이제 **클램프를 건너뛰고 CLTV만 구하는 경로가
   없다.** `DEPOSIT_CLTV_MARGIN`이 두 곳에 복붙돼 있던 것도 하나로 합쳤다.
3. **테스트를 프로덕션 함수에 묶었다** — 클램프를 제거하면 실제로 3건이 깨지는 걸
   확인했다(예전 테스트는 그래도 통과했다).

⚠️ **알려진 한계**: 7일을 넘는 의뢰는 8일째부터 보증금이 타임아웃 환불되어
무담보로 남는다. 등록 시점 스팸 차단은 그대로지만 **그 뒤 몰수는 불가능**하다.
라이트닝 채널 CLTV 상한이 있는 한 구조적으로 피할 수 없다 — 더 오래 담보하려면
보증금을 온체인으로 옮기거나 주기 갱신을 넣어야 하는데, 둘 다 과하다고 봤다.

## F2. 후원자 인보이스가 에스크로보다 오래 살지 않아도 통과 — **수정함**

| | |
|---|---|
| **유형** | **후원자 자금 손실** |
| **시나리오** | 에스크로가 2시간 남은 시점에 후원자가 6시간짜리 인보이스를 낸다 → 통과 → 계좌 받고 원화 송금 → 에스크로가 먼저 만료 → HTLC 타임아웃으로 고객에게 환불 → **후원자만 잃는다** |
| **원인** | 수명 하한(6h)만 보고 **남은 에스크로 시간을 안 봤다** |
| **조치** | 제출 시 `escrowDeadline`까지 남은 시간이 선제 settle 마진 이하면 거절 |

에스크로 창을 24시간으로 줄이면서 이 창이 좁아져 발생 확률이 올라갔다.

## F3. 정산 못 한 채 지급이 나가는 경로 — **수정함**

| | |
|---|---|
| **유형** | **어드민 자금 손실** (가장 치명적인 등급) |
| **시나리오** | `resolveDisputeSponsorWins`에서 프리이미지가 없으면 settle을 건너뛰고 `console.warn`만 남긴 뒤, 그대로 `sponsor_wins`를 발행하고 **후원자에게 지급**했다 |
| **도달 경로** | escrow-store가 아직 릴레이 백업에서 복원되지 않은 새 어드민 기기에서 판정하는 경우. 어드민을 폰과 PC에서 번갈아 쓰므로 가상 시나리오가 아니다 |
| **조치** | `CANNOT_SETTLE`로 실패 반환. 받지 못했으면 주지 않는다 |

`handlePaymentConfirm`(정상 완료 경로)은 원래부터 안전했다 — 지급이 settle 성공
분기 **안에** 있다. 분쟁 경로만 밖에 있었다.

## F4. 붙이기가 쿠팡 기한을 안 봤다 — **수정함**

| | |
|---|---|
| **유형** | 거래 실패 (자금 손실은 아님) |
| **시나리오** | 3개월짜리 의뢰에 쿠팡 주문을 붙이면 **의뢰 만료와 계좌 기한이 완전히 분리**된다. 앱은 3개월 남았다고 보는데 가상계좌는 하루면 죽는다 |
| **조치** | 붙일 때 기한을 확인. 지났으면 거부, 3시간 미만이면 경고 후 확인 |

자동 파싱을 **그대로 쓰는 경우**는 `expiration = 쿠팡 기한`이라 두 시계가 붙어 있어
이 문제가 없다. 붙이기가 만든 새로운 위험이다.

# 남은 것 (미조치)

## F5. `invoiced`에 선제 settle 안전망이 없다

| | |
|---|---|
| **유형** | 후원자 자금 손실 |
| **시나리오** | 후원자가 원화를 보내고 **"송금 완료"를 안 누른 채** 에스크로가 만료 → 고객 환불, 후원자 손실 |
| **왜 안 고쳤나** | 안전망은 `remitted`만 본다. `invoiced`로 확대하면 **"원화를 보냈다는 주장조차 없는데" 고객 BTC를 가져가는** 것이 된다. 비대칭 손실 원칙이 반대로 작동한다 |
| **권고** | 코드가 아니라 UI로 — 후원자에게 "송금했으면 반드시 버튼을 누르세요, 안 누르면 못 받습니다"를 송금 직전에 강하게 고지 |

F2를 막으면서 창이 좁아진 건 완화됐지만 근본 해소는 아니다.

## F6. 보증금 OFF가 만료와 겹쳐 만드는 것

보증금은 만료 로직과 직접 얽히진 않지만, **장기 의뢰와 곱해지면 성격이 바뀐다.**

| | 보증금 ON | 보증금 OFF (현재) |
|---|---|---|
| 스팸 의뢰 수명 | BTC를 걸어야 발행 | **최대 3개월간 오더북에 남는다** (예전엔 24시간) |
| 트롤 클레임 | 보증금 몰수로 억제 | 무료. 게다가 **자동 승인**이 켜져 있어 어드민이 볼 기회도 없다 |

두 번째가 더 아프다. 트롤이 클레임 → 자동 승인 → 고객이 에스크로 → 트롤이
인보이스를 영영 안 냄 → **고객 BTC가 24시간 묶였다가 환불**. 반복 가능하다.

오늘 변경으로 **진입 장벽이 낮아졌다**는 점은 정직하게 기록해 둔다. 예전에는
유효한 인보이스 + 유동성 프로빙 통과가 있어야 `verified`에 닿았다. 지금은
클릭 하나다.

**권고**: 보증금을 켜는 게 정답이다. 그전까지의 완화책으로는 `escrowed`에서
일정 시간 인보이스가 안 오면 클레임을 자동 철회하는 방법이 있는데, 그건
`escrowed → cancelled`를 여는 것이라 T-003을 다시 건드린다 — 신중해야 한다.

## F7. 의뢰 만료 자체는 어드민을 속이지 못한다

만료를 길게 잡는 것으로 어드민이 손해 보는 경로는 찾지 못했다. 금액은 `verified`
시점 시세로 확정되고(`payoutSat`), 에스크로 수명은 의뢰와 분리됐으며, 지급은
settle 성공에만 달려 있다. 의뢰가 오래 떠 있는 것 자체는 오더북 위생 문제지
자금 문제가 아니다.
