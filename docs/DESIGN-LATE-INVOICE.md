# 후원자 인보이스 늦게 받기 — 설계와 공격 분석

> 2026-09-18. 돈 경로 + FSM 변경이라 근거를 먼저 고정한다.
> 구현 후에도 이 문서가 "왜 이 순서인가"의 진실이다.

## 왜 바꾸나

지금은 후원자가 **클레임할 때** bolt11을 내야 하고, 어드민이 유동성 프로빙에
성공해야 `verified`로 넘어간다([ClaimCard.tsx](../admin/src/components/ClaimCard.tsx)
`canApprove`가 `liquidityVerified`를 요구).

이 배치에 문제가 셋 있다.

**① 후원자 사정이 고객을 막는다.** 프로빙 게이트는 `claimed → verified`에 걸려
있어서, 후원자 노드에 인바운드가 모자라면 **고객이 에스크로조차 못 건다.**
정작 유동성 부족으로 손해 보는 건 후원자 자신뿐인데 거래 전체가 선다.

**② 인보이스가 제일 오래 묵는다.** 클레임 시점에 받아 완료 시점에 쓰는데,
그 간격이 거래 전체 길이다. bolt11 기본 만료가 1시간인 지갑이 흔하고,
**어드민 쪽에는 만료 검사가 한 줄도 없다** — 조용히 지급이 실패한다.

**③ 보호 위치가 틀렸다.** 후원자의 되돌릴 수 없는 행동은 "원화 이체"고, 그건
계좌번호를 본 직후에 일어난다. 지금 구조는 그보다 한참 앞(클레임)에 게이트를
두고, 정작 계좌가 나가는 순간에는 아무 확인도 하지 않는다.

## 새 순서

```
claimed      후원자 확정 (인보이스 불필요, 선착순)
  ↓
verified     어드민이 시세 확정 → payout 공개 + 홀드 인보이스 발행
  ↓
escrowed     고객 결제 (BTC 잠김)
  ↓
invoiced     후원자가 payout 금액으로 인보이스 제출 → 어드민 검증 + 프로빙  ← 신규
  ↓          이 상태가 되어야 고객 앱이 계좌 정보를 발행한다
remitted     후원자가 원화 송금 후 통보
  ↓
paid         고객 컨펌 → settle → 보관해둔 인보이스로 지급
```

프로빙은 없어지지 않고 **자리를 옮긴다.** 원화 이체 직전으로 가니 후원자 보호라는
원래 목적에 맞고, 고객의 진행을 막지 않는다.

## 왜 플래그가 아니라 새 상태인가

`order.sponsorInvoice` 같은 필드 하나로도 되지만, 그러면 "인보이스 없이 remitted로
가는 것"을 막는 책임이 `handleRemitRequest` 안의 `if` 한 줄에 놓인다.

**그 방식은 이미 한 번 터졌다.** `handleAccountInfo`는 상태를 바꾸지 않아
`canTransition` 방어 밖에 있었고, 그래서 릴레이 재전송이 올 때마다 알림이
새어 나갔다(2026-09-17). 가드가 핸들러에 흩어지면 새 핸들러를 추가할 때마다
빠뜨린다.

상태로 두면 `canTransition(escrowed, remitted) === false`가 **구조적으로**
막는다. 앞으로 어떤 경로가 추가돼도 자동으로 이 순서를 지킨다. 돈 경로에서는
임기응변보다 구조가 낫다.

## 금액을 누가 정하나

**어드민이 `verified`에서 한 번 정하고, 그 뒤로는 아무도 못 바꾼다.**

```
payoutSat = round(price / spot × 1e8)      ← 후원자가 받을 금액. 오더 태그로 공개
escrowSat = ceil(payoutSat × 1.005)        ← 고객이 낼 금액. 여기서 파생
```

**파생 방향이 중요하다.** 에스크로를 먼저 정하고 후원자가 `÷1.005`를 하면
반올림이 1 sat 어긋나 검증이 깨진다. payout을 기준으로 두면 어드민 검증이
`decoded.amountSat === order.payoutSat` **정확 일치**가 된다.

`ceil`을 쓰는 이유: 마진이 최소 1 sat은 남아야 라우팅 수수료를 댄다.
`round`면 소액에서 마진이 0이 될 수 있다.

이로써 지금의 ±5% 범위 검사(`isInvoiceAmountValid`)는 **사라진다.** 그건 금액이
신뢰할 수 없는 출처(후원자)에서 오기 때문에 있던 방어였다. 출처가 어드민으로
바뀌면 방어할 대상 자체가 없다.

**전달 수단은 새 이벤트가 아니라 오더 태그다.** 양쪽 다 kind 30402를 이미
구독 중이라 새 구독도 새 파서 경로도 필요 없다. addressable 이벤트라 재전송
중복 걱정도 없다. 새 kind 1111 action을 늘리면 파서에 또 구멍이 난다
(2026-09-16에 `push-subscription`이 `a`-태그 검사에 걸려 통째로 버려졌다).

## 계좌 정보는 왜 "가리기"가 아니라 "발행 안 하기"인가

후원자 앱에서 계좌를 가리는 UI 게이트는 약하다. 이벤트는 이미 릴레이에 있고
후원자가 마음먹으면 직접 복호화할 수 있다.

대신 **고객이 `invoiced` 전에는 발행 자체를 하지 않게** 한다. 그러면 계좌 정보가
릴레이에 존재하지 않는다. 가려진 게 아니라 없는 것이다.

고객 앱에는 발행 경로가 **둘**이고 양쪽 다 막아야 한다:

| 경로 | 위치 |
|---|---|
| 수동 입력 | `buyer/components/OrderRow.tsx` `handleAccountSubmit` |
| **파싱 주문 자동 전송** | `buyer/nostr/service.ts` `autoSendAccountInfo` — `escrowed` 도달 시 자동 발동 |

자동 경로를 빠뜨리면 게이트가 무의미해진다. 지금 코드는 정확히 `escrowed`에서
쏘므로, 그대로 두면 새 설계에서 **항상** 게이트를 우회한다.

# 공격 분석

프론트엔드만 있는 구조라 **모든 클라이언트는 코드를 고칠 수 있다**는 전제로 본다.
어드민 FSM만이 신뢰 경계다.

## A. 고객이 계좌 정보를 미리 발행 (코드 수정)

| | |
|---|---|
| **할 수 있나** | 그렇다. kind 1111은 자기 서명이라 언제든 발행 가능 |
| **노리는 것** | 에스크로 전에 후원자가 원화를 보내게 유도 |
| **방어 1** | 어드민이 `escrowed` 이전의 `account-info`를 **무시**한다. 상태도 안 바꾸고 알림도 안 보낸다 |
| **방어 2** | 후원자 앱이 `invoiced` 이전에는 계좌를 표시하지 않는다 |
| **방어 3** | 애초에 `claimed` 전에는 후원자 pubkey를 모르므로 암호화 대상이 없다 — 표적 자체가 불가능 |
| **남는 위험** | 후원자도 코드를 고쳐 릴레이를 직접 읽고 송금하는 경우. **막을 수 없다** |
| **판단** | 후원자가 스스로 방어를 뜯고 에스크로 없는 거래에 송금하는 건 우리가 책임질 범위 밖. 기본 경로는 안전하고, 그게 보호 기능의 달성 가능한 최대치 |

## B. 후원자가 금액이 다른 인보이스 제출

| | |
|---|---|
| **노리는 것** | payout보다 큰 금액을 받아가기 |
| **방어** | `decoded.amountSat === order.payoutSat` **정확 일치**. 범위 검사가 아니라 등식 |
| **변형** | 검증 통과 후 더 큰 금액으로 재제출 → 재제출도 같은 등식을 통과해야 저장된다. 통과 못 한 인보이스는 저장되지 않으므로 지급 대상이 될 수 없다 |

## C. 제3자가 남의 오더에 인보이스 제출

| | |
|---|---|
| **방어** | `request.pubkey === order.sponsorPubkey` 확인. `handleRemitRequest`와 같은 패턴 |
| **주의** | `sponsorPubkey`가 없는 오더(미클레임)에는 애초에 `escrowed`가 없으므로 도달 불가 |

## D. 후원자가 에스크로 전에 인보이스 제출

| | |
|---|---|
| **노리는 것** | 순서를 건너뛰어 계좌 게이트를 미리 열기 |
| **방어** | `canTransition(state, 'invoiced')`가 `escrowed`에서만 참. `verified`에서 오면 FSM이 거부 |
| **왜 구조적인가** | 핸들러의 `if`가 아니라 전이 맵이 막으므로, 다른 경로가 추가돼도 자동 적용 |

## E. 옛 인보이스 이벤트 재전송

| | |
|---|---|
| **상황** | 어드민 부팅 때 릴레이가 과거 이벤트를 전부 재전송 |
| **방어 1** | 이미 `invoiced` 이상이면 `canTransition`이 거부 |
| **방어 2** | 만료 검사를 **매번** 다시 한다 — 옛 인보이스는 대개 만료돼 있다 |
| **방어 3** | 알림은 `claimNotification(eventId)`로 1회성 보장 |

## F. `escrowed → paid` 지름길

| | |
|---|---|
| **현행** | 존재한다. 고객이 후원자 통보 없이 바로 컨펌 가능 |
| **새 설계에서** | **제거해야 한다.** 인보이스가 없는 상태에서 settle하면 지급할 대상이 없어 BTC가 어드민에 묶인다 |
| **대체** | `invoiced → paid`를 허용한다. 같은 지름길이되 지급 대상이 확보된 뒤 |

## G. `escrowed`/`invoiced`에서 취소를 열어줘도 되나 — **아니오**

`escrowed`에서는 계좌가 안 나갔으니 후원자가 송금했을 리 없고, 따라서
`escrowed → cancelled`는 안전해 **보인다.** 실제로 T-003(선취적 취소)이
성립하지 않는 구간이 생긴다.

그런데 **A의 남는 위험과 겹치면 부활한다.** 고객이 계좌를 미리 뿌리고 후원자가
(코드를 고쳐) 송금한 뒤, 고객이 `escrowed`에서 취소하면 T-003 그대로다.

얻는 것은 "멈춘 거래를 고객이 일찍 접을 수 있다" 정도이고, 그건 CLTV 타임아웃이
이미 해결한다. **열지 않는다.** 현행 차단을 그대로 유지한다.

## H. 인보이스가 지급 전에 만료

| | |
|---|---|
| **상황** | `invoiced`에서 `paid`까지 계좌 전달 + 원화 이체 + 컨펌이 들어간다. 몇 시간~하루 |
| **방어 1** | 제출 시 잔여 수명 하한 검사 (최소 6시간). 미달이면 거부하고 이유를 알린다 |
| **방어 2** | 그래도 만료될 수 있다 → **재제출 경로**를 연다. `invoiced`에서 같은 후원자의 새 인보이스를 받아 교체 |
| **왜 둘 다** | 하한만으로는 못 막고, 재제출만 두면 빈도가 높아 운영이 시끄럽다 |

## I. 후원자가 인보이스를 영영 안 냄

| | |
|---|---|
| **결과** | `escrowed`에 머문다. 계좌가 안 나갔으니 아무도 원화를 잃지 않는다 |
| **해소** | 홀드 인보이스 CLTV 타임아웃 → 고객 BTC 자동 환불 (T-006과 같은 패턴) |
| **판단** | 교착이지만 손실 없음. 허용 |

## J. 시세 변동을 이용한 무료 옵션

| | |
|---|---|
| **상황** | `verified`에 시세가 고정되고 고객이 유리할 때까지 에스크로를 미룰 수 있다 |
| **현행 대비** | **변화 없음.** 지금도 클레임 시점에 금액이 고정되고 에스크로는 나중이다 |
| **한계** | 오더 만료(그리고 홀드 인보이스 만료)가 창을 닫는다 |
| **판단** | 이번 변경의 회귀가 아니므로 범위 밖. 문제가 되면 별도로 다룬다 |

## K. 시세 피드 부재

| | |
|---|---|
| **상황** | `verified` 시점에 가격을 못 읽으면 payout을 정할 수 없다 |
| **현행** | `handleClaim`이 가격 없으면 클레임을 버린다(조용히) |
| **새 설계** | 승인 버튼에서 명시적으로 실패시킨다. 조용히 버리지 않는다 |

# 불변조건 추가

기존 I-001~I-008에 더해:

### I-009. 계좌 정보는 `invoiced` 이전에 발행되지 않는다

| | |
|---|---|
| **보호 대상** | 후원자 KRW |
| **불변조건** | 고객 앱의 **모든** 발행 경로(수동·자동)가 `invoiced` 이상에서만 동작해야 한다. 어드민은 그 이전에 도착한 `account-info`를 무시한다 |
| **깨지는 경우** | 후원자가 에스크로도 안 된 거래에 원화를 보낼 수 있다 |

### I-010. 지급 대상 인보이스 없이 settle하지 않는다

| | |
|---|---|
| **보호 대상** | 고객 BTC (어드민에 묶임), 후원자 (못 받음) |
| **불변조건** | `paid`·`sponsor_wins`로 가는 모든 경로는 검증된 후원자 인보이스를 전제로 한다. `escrowed → paid`를 제거하는 이유 |

### I-011. 저장되는 인보이스는 항상 `payoutSat`과 정확히 일치한다

| | |
|---|---|
| **보호 대상** | 에스크로 마진 (라우팅 수수료 재원) |
| **불변조건** | 검증을 통과하지 못한 인보이스는 저장되지 않는다. 재제출도 같은 등식을 통과해야 한다 |

  조용히 CLTV 타임아웃까지 간다. 손실은 없지만 알려주는 편이 낫다.
- 어드민 화면에 `invoiced` 전용 표시 없음 — 상태 라벨로만 구분된다.

# 어드민 개입 전수조사 (2026-09-18)

"어드민이 뭘 하건 안 하건 진행되는가"를 확인한 결과.

## 자동으로 진행되는 것

| 전이 | 트리거 |
|---|---|
| → `requested` | `order-request` 수신 (보증금 켜면 납부 감지 후) |
| → `claimed` | `claim` 수신 |
| → `escrowed` | invoice-watcher 폴링이 홀드 인보이스 결제 감지 |
| → `invoiced` | `sponsor-invoice` 수신 + 검증 |
| → `remitted` | `remit-request` 수신 |
| → `paid` | `payment-confirm` 수신 → settle → **지급까지 자동** |
| → `cancelled` | `cancel-request` 수신, 또는 인보이스 만료 감지 |
| 보증금 환불·몰수 | 상태 전이에 딸려 자동 |

## 어드민이 눌러야 하는 것

| 액션 | 판단 필요? | 흐름을 막나? |
|---|---|---|
| `resolveDisputeSponsorWins` / `CustomerWins` | **그렇다** | 분쟁에서만 |
| `revertClaim` | 선택적 | 아니오 (예외 개입) |
| `disburseSponsor` | 아니오 | 아니오 (`paid`에서 자동 실행, 이건 재시도용) |
| **`approveOrder`** | **아니다** | **그렇다 — 평소 흐름 한가운데** |

유동성 검증이 이 단계에서 빠진 뒤로 `approveOrder`에는 어드민이 고를 게 없다.
조건(LN 어댑터 있음 + 보증금 납부)이 갖춰지면 누를 수밖에 없는 버튼이었다.

## 결론과 조치

**판단 없는 블로커는 정확히 하나였고, 자동화했다.** `auto-approve.ts` +
invoice-watcher Phase 1.5. 어드민이 접속만 해 있으면 거래가 완주하고, 멈추는
곳은 진짜 판단이 필요한 분쟁뿐이다.

판정은 `shouldAutoApprove` 순수 함수로 떼어 테스트로 고정했다 — 조건이 슬그머니
느슨해지면 승인이 남발되고, 그 결과(홀드 인보이스 발행·가격 확정)는 클레임
철회를 타야만 되돌릴 수 있다.

보증금 게이트는 자동화가 건너뛰지 않는다. 그건 스팸 방어라 건너뛰면 설정을
켜둔 의미가 사라진다.

헤더에 끄는 스위치를 뒀다(기본 켜짐). 돈이 걸린 경로라 "지금은 내가 보고
넘기겠다"가 가능해야 한다.

**여전히 어드민 탭이 열려 있어야 한다.** 롱러닝 데몬 없이 순수 프론트를
유지하는 선택의 비용이고, 이번 변경이 바꾸지 않는다.
