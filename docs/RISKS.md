# 위험 대장

**불안한 점은 전부 여기 모은다.** 공격 시나리오와 그 방어, 알면서 받아들인 위험, 아직 안 고친 것이 한 문서에 있다.
새로 발견하면 여기 추가하고, 고치면 "열린 것"에서 빼서 방어 표로 옮긴다. 과거 기록은 git 히스토리에 있다
(옛 `THREAT-MODEL.md`·`SECURITY-ROADMAP.md`·`AUDIT-*.md`·`PLAN-ONCHAIN-TRACK.md` §7·§14).

트랙별 규칙(불변조건 I-xxx · O-xxx)은 [LN-TRACK.md](LN-TRACK.md) · [ONCHAIN-TRACK.md](ONCHAIN-TRACK.md),
데몬 불변조건(DM-xxx)은 [ARCHITECTURE.md](ARCHITECTURE.md)에 있다.

## 1. 열린 것 — 먼저 볼 것

심각도: 🔴 자금 손실이 현실적 · 🟡 조건부 손실·운영 부담 · 🟢 위생

| # | 심각도 | 무엇 | 왜 불안한가 | 할 수 있는 것 |
|---|---|---|---|---|
| R-2 | 🔴 | **웹 앱 서빙 서버(VPS) 침해** | 유저 앱은 VPS nginx가 정적으로 준다. 서버가 뚫려 JS가 바뀌면 키 탈취, 에스크로 인보이스·계좌 정보 바꿔치기(후원자가 공격자 계좌로 송금), 주소 검증 우회가 전부 가능하다. 앱 안의 어떤 검증도 앱 자신이 바뀌면 소용없다 | VPS 접근 최소화(키 인증, 불필요 서비스 없음). 배포물 해시를 기록해 두고 주기 대조. (주입 스크립트·XSS 쪽은 유저 앱 CSP `script-src 'self'`가 막는다 — `customer/vite.config.ts`) |
| R-3 | 🟡 | **데몬·LND가 오래 죽으면 송금한 후원자가 잃는다** | 라이트닝 `remitted`에서 에스크로 HTLC가 만기에 가까워지면 데몬이 먼저 settle한다(선제 settle). 데몬이 그 시각을 넘겨 꺼져 있으면 LND가 홀드를 스스로 취소해 고객에게 돌아간다 — 원화를 보낸 후원자만 잃는다. 여유는 기한 뒤 약 48시간. 온체인은 타임락(8주)이 길어 같은 위험이 거의 없다 | **수용(2026-09-26 운영 결정)** — 데몬·LND 가동은 lnpay와 별개로 운영 PC에서 늘 관리한다. 그 위에 알림 둘: LND 불통은 데몬이 10분 뒤 DM, 데몬·운영 PC 멈춤은 VPS의 바깥 감시(`daemon/scripts/watchdog.mjs`, cron)가 DM — 설치는 DAEMON-DEPLOY §7 |
| R-4 | 🟡 | **지급 수수료 상한이 마진보다 크다** | 에스크로 마진은 payout의 0.5%(`FEE_RATE = 1.005`, 올림)인데 지급 수수료 상한은 `max(10 sats, 1%)`다. 라우팅이 비싸면 차액을 운영자가 문다. 소액은 더하다(1,000 sats 지급 → 마진 5 sats, 상한 10 sats) | **수용(2026-09-26 운영 결정)** — 가끔의 역마진은 감수한다. 실제로 라우팅 수수료가 마진을 넘을 일은 거의 없다(오히려 마진이 큰지 검토 중) |
| R-5 | 🟡 | **보증금이 켜져 있지 않으면 공짜 클레임 점유** | 보증금 비율 기본값은 0이고 자동 승인은 켜져 있다. 트롤이 클레임 → 자동 승인 → 고객이 에스크로 → 인보이스를 안 냄 → 고객 BTC가 기한 + 1시간까지 묶인다(최대 7일). 반복 가능 | 운영에서 보증금을 켠다(계획: 3%). 켜면 `expired:no-invoice`로 몰수된다 |
| R-6 | 🟡 | **라이트닝: 송금하고 "송금 완료"를 안 누르면 후원자가 잃는다** | `invoiced`에서 기한 + 1시간이 지나면 `expired:no-remit`으로 에스크로를 고객에게 돌려준다. 원화를 보냈다는 주장조차 없는 거래에서 고객 BTC를 가져갈 수는 없다(비대칭 손실 원칙이 반대로 작동) | 코드가 아니라 화면으로 — 송금 직전에 "보냈으면 반드시 버튼" 고지. 유예 1시간이 완충 |
| R-7 | 🟡 | **판정이 늦으면 보증금이 먼저 죽는다** | 보증금은 LN HTLC라 수명이 유한하다. 온체인은 분쟁 진입 뒤 24시간(`DISPUTE_RULING_BUDGET_SEC`)까지만 몰수가 보장되고, 라이트닝 후원자 보증금은 에스크로보다 24시간 더 산다. 그 뒤의 판정은 몰수를 못 할 수 있다. 블록이 빨리 나오면 더 짧아진다 | 분쟁 카드의 보증금 만료 추정치를 기준으로 판정을 서두른다. 물리적 한계라 코드로 못 없앤다 |
| R-8 | 🟡 | **선제 settle 뒤 고객 승이면 환불이 수동** | 에스크로를 이미 받았으므로 cancel할 수 없다. 경보가 뜨고 운영자가 고객에게 따로 LN 결제로 돌려줘야 한다(고객의 받을 인보이스를 받는 경로도 없다) | 드물다. 채팅으로 인보이스를 받아 수동 결제 |
| R-9 | 🟡 | **결제 지갑의 CLTV 한도** | 가장 긴 보증금 홀드는 최종 CLTV ≈ 1446블록(라이트닝, 기한 7일)·≈ 1343블록(온체인). 경로 델타가 붙으면 LND 기본 한도(2016)엔 들지만, 한도가 더 낮은 지갑은 결제를 거부할 수 있다 | 실측으로 확인한다. 거부가 잦으면 기한 상한(7일)을 줄인다 — `timing-invariants` 테스트가 관계를 지킨다 |
| R-10 | 🟡 | **공개 mempool.space 의존** | 온체인 워처의 모든 체인 조회가 한 API다(`LNPAY_ONCHAIN_API`, 기본 공개 인스턴스). 막히면(IP 차단 전례 있음 — fulmine) 조회가 전부 "모름"이 되어 안전하게 멈추지만, 그동안 마감 초과 환불 결정이 안 나고 펀딩도 확정되지 않는다 | 자체 인스턴스(mempool/electrs)를 붙인다 |
| R-11 | 🟢 | **reserve 공짜 풋옵션은 완화만** | 최저가가 시세보다 3% 이상 아래여야 받지만, 펀딩 컨펌 대기(최대 2시간) 동안 3% 넘게 빠지면 고객은 무과실 환불로 빠진다. 후원자는 시간만 잃는다 | 수용 |
| R-12 | 🟢 | **프라이버시: 한 키가 여러 거래를 묶는다** | 유저 nostr 키는 브라우저당 하나라 그 아래 거래가 서로 이어진다. 온체인 펀딩 tx 입력은 고객 지갑을 드러낸다. 라이트닝 공개 오더에는 후원자 지급 인보이스(`sponsor-invoice`)가 실려 후원자 노드가 드러난다. 거래가 끝나면 키째 지우는 "기록 파쇄"는 없다 | 키를 새로 만들어 거래마다 바꾸는 식으로 만든다. 진행 중 거래가 있으면 파쇄를 막아야 한다(키를 지우면 환불 서명이 불가) |
| R-13 | 🟢 | **유저스크립트 자동 감지는 쿠팡 페이지를 열어야 돈다** | 입금·취소 감지가 페이지 방문 때만 일어나고, 결과는 웹앱을 거쳐야 데몬에 간다. 쿠팡 앱(모바일)에선 안 돈다 | 수동 버튼이 있다. 주기 폴링은 미구현 |
| R-14 | 🟢 | **부분 발행을 성공으로 친다** | 릴레이 하나라도 받으면 성공이다. 유저가 그 릴레이를 안 보면 못 본다 | 수용 — 발행 대상은 NIP-65로 고른 읽기 릴레이다 |
| R-15 | 🟢 | **NIP-69 오더 모음에 우리 의뢰가 뜬다** | 오더가 NIP-69(38383)라 다른 P2P 오더 모음이 우리 의뢰를 목록에 띄울 수 있다. 공개되는 값은 원래 공개 오더에 있던 것뿐이다 | 수용 — 오히려 유입 경로로 쓴다: `source` 링크로 들어오면 우리 앱에서 바로 맡는다. 다른 곳에 안 뜨게 하려면 NIP-69 태그를 빼면 된다 |

## 2. 신뢰 모델 — 무엇이 뚫리면 무엇을 잃나

| 뚫린 것 | 할 수 있는 것 | 못 하는 것 | 막는 것 |
|---|---|---|---|
| **시드** (데몬 비밀) | 모든 온체인 주문의 어드민 키 → 후원자와 짜면 `{A,S}`로 에스크로 탈취. 라이트닝 프리이미지 전부 → 결제 경로상의 노드라면 에스크로 HTLC를 가로챌 수 있다 | 혼자서는 온체인 에스크로를 못 뺀다(2-of-3) | 파일 권한, 종이 백업 분리 보관 |
| **APP 키** (데몬 nostr) | 가짜 오더 상태 발행(후원자가 없는 에스크로를 믿고 송금), 가짜 에스크로 인보이스 싣기, 요청 복호화(환불·받을 주소) | 계좌 정보 복호화(후원자에게만 암호화됨) | 파일 권한. ⚠️ 교체하면 기존 데이터가 전부 끊긴다 |
| **운영자 키** (어드민 로그인, NIP-46) | 분쟁을 한쪽에 유리하게 판정, 강제 종결, 설정 변경(보증금 0·자동 승인) | 돈을 직접 옮기지 못한다 — 판정은 사유만 정하고 돈은 규칙대로 간다 | 번커 보안. 명령은 버전 확인(DM-006) |
| **LND 매크룬** | 노드 자금 이동(권한 범위 안) | 권한 밖(구운 매크룬: 인보이스·오프체인·정보만) | 최소 권한 매크룬, REST는 docker 게이트웨이에만 |
| **릴레이** | 이벤트 누락·지연·검열 | 위조(서명 검증) · 복호화 | 다중 릴레이. 누락은 보존 기간 안 재구독이 메운다 |
| **시세 소스** (업비트·빗썸·코인원) | 틀린 가격 → 틀린 금액 | 여럿이 한꺼번에 틀리지 않는 한 영향이 작다 | 여러 소스. 시세가 없으면 승인·가격 고정을 **미룬다**(0원으로 진행하지 않는다) |
| **mempool API** | 거짓 체인 정보(펀딩 있다/없다) | — | 유저 앱이 주소를 스스로 파생·대조(T-107), 서명 전 재구성 대조(O-021). 데몬 쪽은 자체 인스턴스가 답(R-10) |
| **VPS** | R-2 | 데몬에 닿지 못한다(데몬은 들어오는 포트가 없다, DM-007) | R-2 |

## 3. 공격 시나리오와 방어 — 라이트닝

| ID | 공격 | 방어 | 어디서 |
|---|---|---|---|
| T-001 | 고객이 유저스크립트의 자동 취소를 사칭해 에스크로 뒤에 취소 | 에스크로 뒤 `cancelled` 전이가 없다 | 전이 표 |
| T-002 | 고객이 에스크로 뒤 쿠팡에서 직접 주문 취소 → 환불금 착복 | 앱 안에서 못 취소한다. 후원자가 송금했으면 `remitted` → 판정. 미송금이면 기한 만료로 정리 | 전이 표, 분쟁 |
| T-003 | 후원자 송금 직전 고객의 선취적 취소 | 에스크로 뒤 일방 취소 없음(I-005) | 전이 표 |
| T-004 | 후원자가 원화 없이 "송금 완료" | 입금 확인은 고객만 누른다. 분쟁에서 송금 증거를 요구하고, 없으면 고객 승 → 후원자 보증금 몰수 | `payment-confirm` 보낸 사람 검사 |
| T-005 | 새 nostr 키로 반복 트롤 클레임 | 후원자 보증금 15분 결제창 — 안 내면 클레임이 풀린다. 보증금이 꺼져 있으면 R-5 | `claimed` 워처 |
| T-006 | 자기 의뢰를 자기가 클레임 | 데몬이 거부(I-007), 오더북도 `own`으로 판정 | `claim`, `sponsorRelation` |
| T-007 | 남의 오더에 지급처 인보이스를 꽂거나 남 대신 입금 확인 | 모든 요청은 보낸 사람을 본다(I-008) | `handlers.ts` |
| T-008 | 제3자가 후원자에게 가짜 계좌 정보 | 후원자 앱은 **그 오더의 고객**이 보낸 계좌만 받는다. 오더보다 먼저 온 건 잡아 뒀다 판정 | `sponsor/nostr/service.ts` |
| T-009 | 우리 인보이스(에스크로·보증금)를 지급처로 제출 | 거절 — 우리 돈으로 우리 홀드를 채우게 된다 | `sponsor-invoice` |
| T-010 | 에스크로가 곧 죽는데 인보이스를 받아 계좌 관문을 연다 → 후원자가 죽은 에스크로를 보고 송금 | 에스크로 잔여 108블록 미만이면 인보이스 거절, 72블록 미만이면 기한 전에 닫는다 | `INVOICE_ESCROW_MIN_BLOCKS`, `ESCROW_END_BLOCKS` |
| T-011 | 커밋먼트로 계좌번호 브루트포스 | 32바이트 솔트 | `account-commitment.ts` |
| T-012 | 분쟁도 아닌데 계좌를 운영자에게 공개시킴 | 공개 버튼은 `reveal-request`가 와야 열린다 | 유저 앱 |
| T-013 | 쿠팡 주문번호 노출·orderId 선점 | 오더 id는 랜덤. 유저스크립트는 자기 주소 채널로 받는다 | `order-id.ts` |
| T-014 | 이중 지급 | 지급 전에 결제를 추적, 같은 인보이스는 한 번. LND도 막는다 | `ln.payout` |

## 4. 공격 시나리오와 방어 — 온체인

## 5. 과거 사고에서 굳은 규칙

같은 실수를 다시 안 하려고 코드·테스트에 박아 둔 것들이다. 새 코드도 따른다.

- **상태 목록을 손으로 나열하지 않는다.** 터미널·배지·진행도 표는 전이 맵에서 유도하거나 `Record<State, …>`로
  못박는다 — `admin_closed`를 넣을 때 다섯 군데 중 둘만 고쳐 종결된 의뢰가 오더북에 남았다.
- **"모름"을 "없음"으로 뭉개지 않는다.** 조회 실패는 보류다. 모르는 마감은 지난 것으로 본다(`isPast`).
- **테스트는 프로덕션 경로를 탄다.** 프로덕션이 안 부르는 헬퍼를 검증하면 버그가 초록으로 남는다(보증금 CLTV가 그렇게
  한 번 거짓으로 닫혔다).
- **되돌릴 수 없는 효과가 확인되기 전에 그 결과를 발행하지 않는다**(DM-003) — `paid` 뒤 settle 실패로 후원자가 잃은 적이 있다.
- **이벤트 보존과 거래 마감을 섞지 않는다**(DM-009) — 기한 = 보존이던 시절 기한 직후의 송금 완료가 릴레이에서 거절됐다.
- **문구에 숫자를 박지 않는다.** 창 길이는 상수에서 가져온다(`durationText`) — 6시간이 앱 여섯 군데에 박혀 창을 바꿀 때 따로 놀았다.
- **FSM을 고치면 다섯 가지가 세트다:** 전이 맵 → 알림 문구 → 문서 → 진행도 → 상태 배지.
- **운영자가 알아야 할 일은 DM으로 보낸다**(`raiseAlert`·`notifyOperators`). 우리 이벤트는 전용 kind라 어떤 클라이언트도
  울리지 않는다 — 온체인 계좌 이의는 운영자 판정이 필요한데 경보가 없었다(2026-09-26 kind 전환 때 발견해 붙였다).
