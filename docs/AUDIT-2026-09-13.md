# A. 보안

## A-1. 계좌정보 commitment이 솔트 없이 공개된다 🔴 ✅

| | |
|---|---|
| **위치** | `customer/src/buyer/nostr/publish.ts` `publishAccountInfo()` |
| **상태** | ✅ 처리 — 공식을 `shared/account-commitment`로 모으고 32바이트 솔트 도입 |

같은 평문의 **NIP-44 암호문과 무솔트 SHA-256 해시가 같은 이벤트에 함께 공개**된다.

```ts
const plaintext = JSON.stringify(accountInfo);
const encrypted = nip44Encrypt(plaintext, sk, sponsorPubkey);  // 후원자만
const commitment = await sha256Hex(plaintext);                  // 전 세계
tags.push(['commitment', commitment]);
```

원상 공간이 작다 — 한국 은행 ~20개, 계좌번호는 은행별 고정 포맷·지점코드라 자릿수보다 엔트로피가
훨씬 낮고, 예금주는 한글 2~3자다. 은행과 예금주를 아는 공격자면 **GPU로 수 분~수 시간**이면
계좌번호가 복원된다. 릴레이를 읽을 수 있는 누구나 오프라인으로 돌릴 수 있으므로
**NIP-44 암호화가 사실상 무력화된다.**

**수정안** — 표준적인 솔티드 커밋먼트:

1. 32바이트 랜덤 salt 생성
2. `commitment = sha256(salt || plaintext)`
3. salt를 **암호화 페이로드 안에** 넣어 후원자에게만 전달
4. 분쟁 시 `publishAccountReveal`이 salt까지 공개

커밋먼트의 구속력(후원자가 받은 계좌를 나중에 바꿔 주장할 수 없음)은 그대로고 브루트포스만 죽는다.
`admin/src/components/CommitmentBadge.tsx` 검증 로직은 salt를 받는 것 외에 구조가 같다.
`admin/src/tests/commitment.test.ts`도 같이 갱신한다.

## A-3. 쿠팡 주문번호가 공개 태그로 나간다 🟢 ✅

| | |
|---|---|
| **위치** | `customer/src/buyer/components/ParsedOrdersSection.tsx` |
| **상태** | ✅ 처리 — **수정안 ①** 채택. 랜덤 orderId + 유저스크립트 자기주소 채널 |

파싱 주문은 sajwo orderId로 쿠팡 주문번호를 그대로 쓴다. 이 값이 `a` 태그
(`30402:APP_PUBKEY:18102892285466`)로 릴레이에 공개된다. 실세계 식별자라 상관관계 추적 여지가 있다.
수동 주문은 이미 랜덤값이므로 파싱 경로만의 문제다.

### dedup은 쉽다

지금 중복 방지는 `parsed-store.ts`의 `orders[payload.coupangOrderId]` 조회 하나에 걸려 있다.
`CustomerOrder`에 **발행되지 않는 로컬 필드** `coupangOrderId`를 두고 그걸로 찾으면 된다.
유저스크립트의 GM `processed-orders`는 이미 쿠팡 번호 키라 그대로 둔다.

### 진짜 걸림돌: 유저스크립트가 랜덤 id를 모른다

유저스크립트는 `payment-confirm` / `cancel-request`의 a-태그를
`30402:APP_PUBKEY:${쿠팡주문번호}`로 만든다(`userscript/src/nostr.ts`). 쿠팡 페이지에서 도는
물건이라 웹앱이 만든 랜덤 id를 알 방법이 없다. 둘이 갈라지면 **자동 입금감지가 죽는다.**

**수정안 ① 릴레이 경유 (추천)**

유저스크립트가 `parsed-order`와 같은 채널을 쓴다 — 자기 자신에게(`p=내 펍키`) NIP-44
자기암호화로 `{coupangOrderId, status}`만 보내고, 웹앱이 받아 로컬 매핑으로 진짜
`payment-confirm`을 발행한다.

프라이버시 외에 이득이 하나 더 있다. **유저스크립트에서 APP_PUBKEY 의존이 완전히 사라진다.**
2026-09-03 키 교체 후 6주간 자동 입금감지가 조용히 죽어 있던 원인이 정확히 "설치본의
APP_PUBKEY가 옛것이라 어드민 `#p` 필터에 안 걸림"이었다. 유저스크립트가 자기 자신에게만
보내면 **그 고장이 구조적으로 불가능해진다.** 쿠팡 번호도 암호문 안에만 남는다.

대가: 자동 컨펌이 "쿠팡 페이지에서 즉시"에서 **"웹앱을 다음에 열 때"**로 바뀐다.

**수정안 ② 매핑 내려주기**

웹앱이 `order-request` 발행 시 `{coupangOrderId}`를 자기암호화해 content에 싣고, 유저스크립트가
자기 이벤트를 조회·복호화해 매핑을 만든다. 즉시성은 유지되지만 APP_PUBKEY 의존이 남고
유저스크립트에 릴레이 읽기가 늘어난다.

> 즉시성보다 고장 안 나는 쪽이 값지다고 보아 **①을 권한다.**

옛 방식 이벤트를 계속 쏘는데, 그건 어느 오더에도 닿지 않는다. 순서:

1. `pnpm ship` (verify → 빌드)
2. customer 배포 → 웹앱이 `coupang-status`를 받을 수 있게 됨
3. 유저스크립트 재설치 (`@updateURL`이 붙은 뒤라 이후로는 자동 갱신)

기존 파싱 주문(쿠팡 번호 = orderId)은 그대로 둔다. 새로 올리는 것부터 랜덤 id다.
