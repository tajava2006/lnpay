# 온체인 전용 트랙 — 설계 검토

> 상태: **아이디어 / 미착수** (2026-09-19 제안)
>
> 라이트닝이 아니라 온체인 2-of-3 taproot 에스크로로 도는 별도 트랙.
> 착수 전 검토 결과를 남긴다 — 결론은 "할 만하다", 다만 밟으면 아픈 자리가 몇 개 있다.

## 왜

유저 피드백에서 나왔다. 쿠팡 결제가 아니라 **non-KYC 비트코인 거래**로 쓰고 싶다는 것.
그쪽 커뮤니티의 실제 문제는:

- 거래 상대를 찾기 어렵다
- 찾아도 믿을 수 없다 (사기 이력 → 거래가 마름)
- 운영자가 허들을 올린다 (신원·레벨제) → 신규 배척 → 유동성 더 마름

에스크로는 **상대방 리스크를 없애서** 그 악순환을 끊는다. 오더북에서 골라잡으면 되고,
파는 쪽은 올려두고 잊으면 된다.

라이트닝으로는 이 시장이 안 된다:

- 라우팅 수수료를 어드민이 대납 → 0.5%를 받아야 마진이 안 깨진다
- 거래소 대비 **미친 수수료**다. 메이커가 안 오면 테이커도 안 온다
- 요즘 온체인 수수료가 낮아 **5만 사토시만 넘어도 온체인이 더 싸다**
- 홀드 인보이스 관리로 어드민 역할이 커진다

온체인이면 수수료를 **0**으로 둘 수 있다. 인프라 비용이 사실상 없고(노드 슬롯도 안 씀),
happy path에서는 어드민이 아무것도 안 한다. 분쟁 때만 중재료를 받으면 된다.

# 스크립트 구성

## 조건은 2-of-3이다

제안된 소모 조건을 펼치면:

```
1. C & S              happy path
2. A & (C or S)   →   {A,C}, {A,S}
```

= `{C,S}`, `{A,C}`, `{A,S}` — **세 쌍 전부**. 표준 2-of-3이다.

## 권고: NUMS 키패스 + 리프 3개

```
내부키(key path)  BIP-341 NUMS 점 — 증명 가능하게 소모 불가
                  (아무도 스크립트를 우회할 수 없게)

leaf 1   <C> CHECKSIGVERIFY <S> CHECKSIG      happy
leaf 2   <A> CHECKSIGVERIFY <C> CHECKSIG      분쟁: 고객 승
leaf 3   <A> CHECKSIGVERIFY <S> CHECKSIG      분쟁: 후원자 승
leaf 4   <N> CSV DROP <C> CHECKSIG            타임락 탈출 (아래 참조)
```

**MuSig2는 v1에서 쓰지 말자.** happy path를 MuSig2(C,S) 키패스로 하면 수수료가 더 싸고
체인에서 일반 송금과 구분되지 않아 매력적이지만:

- 논스 교환이 2라운드 인터랙티브다
- **논스를 재사용하면 개인키가 그대로 유출된다.** 비동기 프론트 앱에서 라운드 상태를
  localStorage에 들고 가는 구조라 재시도·새로고침·다기기가 전부 재사용 위험이다
- 자금 전손 등급의 버그 클래스를 v1에 넣을 이유가 없다

스크립트 패스 2서명은 키패스보다 대략 40~80 vbyte 더 든다. 지금 수수료 수준에서
수십 원 차이다. 그 값에 이 위험을 사지 않는다.

## 타임락 리프는 **넣어야 한다**

빼도 되지 않을까 하셨는데, 넣는 쪽을 강하게 권한다. 이유는 하나다:

**어드민이 사라질 수 있다.** 어드민은 브라우저 탭이다. 기기 분실, 키 유실, 그냥 안 켬 —
전부 현실적이다. 그때 후원자마저 응답하지 않으면 `{C,S}`도 `{A,C}`도 불가능해져
**고객 돈이 영구히 잠긴다.**

타임락 리프는 "어드민이 증발해도 고객은 결국 되찾는다"는 보험이고, 이게 있어야
비수탁이라고 말할 수 있다. 라이트닝 버전에서 CLTV 타임아웃이 하던 역할이 정확히
이것이다 — 온체인에서는 이 리프가 그 자리를 대신한다.

값은 넉넉하게(예: 2016블록 ≈ 2주). 짧으면 분쟁 중에 고객이 일방 탈출할 수 있다.

# 밟으면 아픈 자리

## ① nostr 키를 그대로 쓰면 안 된다 — 추적됩니다

nostr 키는 secp256k1이라 그대로 비트코인 키로 쓸 수 있다. 맞다. **그런데 그러면 안 된다.**

오더북의 kind 1111·30402에 각자의 nostr pubkey가 **공개로** 박힌다. 그 키를 taproot에
그대로 넣으면 누구나 "이 nostr 계정 = 이 온체인 주소"를 잇고 자금 흐름을 따라갈 수 있다.
**non-KYC 거래앱에서 이건 치명적인 프라이버시 후퇴**다 — 정확히 이 앱을 쓰려는 이유를
무너뜨린다.

권고: **주문별 키를 nostr 키에서 파생**한다.

```
orderKey = HMAC-SHA256(nostrPrivkey, "pairbuy-onchain/v1/" + orderId)
```

- nostr 신원과 온체인이 연결되지 않는다
- 주문마다 새 키라 주소 재사용도 없다
- nostr 키 하나만 있으면 **결정론적으로 복원**된다 → 추가 백업 부담 0

어차피 키를 따로 만들어야 하는 어드민도 같은 방식으로 파생하면 된다. 다만 어드민은
NIP-46이라 개인키가 로컬에 없으므로, 주문별 키를 생성해서 **NIP-78 암호화 백업**에
넣는다 — 프리이미지·VAPID 키가 이미 쓰는 패턴이라 새 구조가 아니다.

⚠️ 어드민 주문별 키를 잃으면 **그 주문의 분쟁 중재가 영구 불가**해진다. 백업이 선택이 아니다.

## ② 0-conf를 믿으면 털린다

**공격**: 고객이 RBF를 켜고 펀딩 → 후원자가 멤풀에서 보고 원화 송금 → 고객이 같은
입력으로 자기 주소에 보내는 tx로 교체 → 후원자는 원화만 잃는다.

**방어**: 후원자에게 "원화를 보내도 된다"를 띄우는 조건은 **최소 1컨펌**이어야 한다.
멤풀 도착은 "확인 중"까지만. 0-conf를 허용하는 UI를 만들면 안 된다.

(RBF 미신호 tx만 받는 방법도 있지만 full-RBF 정책이 퍼진 지금은 신뢰할 수 없다.
컨펌을 기다리는 게 유일하게 확실하다.)

## ③ 주소 검증은 클라이언트가 스스로 해야 한다

고객이 돈을 보내는 주소가 **정말 자기 키가 들어간 2-of-3인지**를 앱이 독립적으로
확인해야 한다. 어드민이 알려준 주소를 그냥 믿으면, 어드민이 악의적이거나 침해당했을 때
전액을 잃는다.

→ 세 pubkey를 전부 오더 이벤트에 싣고, **각 클라이언트가 주소를 직접 파생해 대조**한다.
불일치면 진행을 막는다. 이건 타협 대상이 아니다.

## ④ 가격을 언제 고정하나 — 펀딩을 먼저 받는 쪽을 권한다

고객은 "얼마든 시세로 판다"이므로 금액은 sats로 정해지고 KRW는 나중에 정해진다.
문제는 **온체인 컨펌 지연 동안 시세가 움직인다**는 것.

라이트닝은 홀드 인보이스가 즉시라 간극이 작았지만, 온체인은 10분~수십 분이다.
`verified`에 가격을 고정하면 그 리스크를 후원자가 떠안는다.

**대안: 고객이 먼저 펀딩하고 오더북에 "펀딩 완료" 상태로 올린다.**

```
고객이 스크립트 주소에 입금 → 컨펌 → 오더북에 노출
→ 후원자가 클레임하는 **그 순간** 시세로 KRW 확정 → 원화 송금 → 릴리스
```

- 컨펌 간극이 가격 결정 **앞**으로 빠져 리스크가 사라진다
- 고객 스팸이 원천 차단된다 (이미 돈을 넣어야 오더북에 뜬다)
- "올려두고 까먹고 있으면 되는" 원하시는 사용감과도 맞는다
- 대신 **타임락 리프가 필수**가 된다 — 후원자가 영영 안 붙을 수 있으므로

## ⑤ 수수료 — 누가 내는지 명확해야 한다

에스크로 출력이 X면 릴리스 tx는 X를 쓰고 수수료 F를 내므로 **후원자가 받는 건 X − F**다.
즉 릴리스 수수료는 후원자 부담이다. 나쁘지 않지만 화면에 명시해야 한다.

- **수수료율 합의**: 고객이 서명하는 순간 출력 금액이 확정되므로, 후원자가 먼저
  {받을 주소, 수수료율}을 제시하고 고객이 그걸로 서명하는 순서여야 한다
- **막히면**: RBF를 켜두되, 재서명은 양쪽이 다시 붙어야 하므로 현실적으로는
  **후원자가 자기 출력으로 CPFP**하는 게 빠르다. 그 버튼을 주는 게 좋다
- **최소 거래 금액**: 수수료가 거래를 잡아먹지 않도록 하한이 필요하다

## ⑥ 후원자가 버리면 고객이 수수료를 잃는다

라이트닝에서는 스팸이 시간만 축냈지만, 여기서는 고객이 이미 **실제 수수료를 낸 뒤**다.
후원자가 클레임만 하고 사라지면 고객은 펀딩 수수료를 날리고 회수에 또 수수료를 쓴다.

→ 후원자 보증금을 그 손실을 **덮을 만큼** 잡아야 억제가 된다. 정률(%)만으로는
소액에서 억제력이 안 나오므로 **하한(최소 N sats)**을 같이 두는 게 맞다.

# 범위 — 무엇을 나누고 무엇을 공유하나

"완전 별도 트랙"이 편하다는 판단에 동의한다. 다만 **앱을 새로 만드는 수준은 아니다.**

| | 공유 | 새로 |
|---|---|---|
| nostr 전송·오더북·구독 | ✅ 그대로 | |
| 분쟁 채팅·히스토리 | ✅ 그대로 | |
| 알림(Web Push) | ✅ 그대로 | |
| 후원자 보증금 | ✅ 라이트닝 홀드 인보이스 그대로 | |
| FSM | | ⬜ 상태가 달라 별도 |
| 에스크로 | | ⬜ taproot 주소·PSBT |
| 릴리스 | | ⬜ 서명 교환 (settle 대신) |
| 체인 조회 | | ⬜ mempool.space |

**보증금에 라이트닝을 그대로 쓰는 건 좋은 판단이다.** 소액이고 몰수/환불이 즉시라
온체인으로 옮길 이유가 없다. 라이트닝이 잘하는 걸 계속 시키는 것.

PSBT 교환은 기존 kind 1111 + NIP-44에 그대로 태우면 된다 — 계좌정보가 이미 그 길로
다닌다. 새 전송 계층이 필요 없다.

# 미결 질문

1. **컨펌 수** — 1컨펌으로 충분한가, 금액별로 다르게 할 것인가
2. **타임락 길이** — 2016블록? 분쟁 최장 기간보다 확실히 길어야 한다
3. **중재료 징수 방법** — 분쟁 tx에 어드민 출력을 하나 더 다는 방식일 텐데,
   그러면 판정과 동시에 금액이 확정된다. 사후 청구는 불가능하다
4. **부분 체결** — 오더북에서 "0.01 BTC" 통째로만 거래하나, 쪼갤 수 있나.
   쪼개려면 펀딩 UTXO를 나눠야 해서 설계가 크게 바뀐다
5. **가격 피드 신뢰** — 어드민의 시세가 유일 기준인데, 온체인 트랙은 "시세로 판다"가
   상품의 본질이라 라이트닝 때보다 훨씬 민감하다. 피드가 틀리면 그게 곧 손해다

# 결론

**할 만하다.** 암호학적으로 새로 발명할 게 없고(표준 2-of-3), 전송·오더북·알림·보증금은
그대로 재사용되며, 정말 새로 짜는 건 에스크로와 릴리스 두 덩어리다.

제일 큰 위험은 taproot가 아니라 **운영 실수**다 — 주소 파생이 틀리거나, 어드민 키를
잃거나, 0-conf를 믿거나. 셋 다 자금 전손이고 셋 다 코드가 아니라 **절차와 검증**으로
막는 종류다. 라이트닝 트랙에서 배운 "불변조건을 코드에 단언으로 박는다"가 여기서
훨씬 더 중요해진다.
